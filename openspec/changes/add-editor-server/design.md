# Дизайн: протокол `ibcmd-rs serve --stdio`

Версия протокола **1.0**. Реализация: `src/server/` (транспорт, методы),
`src/stored_objects.rs` (дерево, строки объекта, выгрузка в память,
сверка с папкой), `src/commands/objects.rs` (то же из командной строки).
Тесты: `tests/editor_server.rs`.

## 1. Транспорт

- Редактор запускает `ibcmd-rs serve --stdio`, по одному процессу на окно.
  Окружение то же, что у командной строки (`IBCMD_RS_CONFIG`,
  `IBCMD_RS_PLATFORM`, `IBCMD_DB_PSW`, `IBCMD_RS_SQL_CONNECTIONS`, ...).
- Сообщения — JSON-RPC 2.0 в кадрах, как у LSP:

  ```
  Content-Length: <число байтов тела>\r\n
  \r\n
  <тело: JSON в UTF-8>
  ```

  Читается только `Content-Length`; `Content-Type` и другие заголовки
  принимаются и не читаются. Тело больше 64 МиБ, заголовок без
  `Content-Length` или с нечисловым значением — поток не восстановить:
  сервер завершается с кодом 1. Тело, которое не JSON, получает ответ
  `-32700` с `id: null`, сервер продолжает работу. Пакеты (batch, массив
  сообщений) не поддерживаются: `-32600`.
- `id` запроса — число или строка, возвращается в ответе как есть.
- stdout несёт только протокол. В stderr движок пишет свои служебные строки
  (`model export: ...`, предупреждения о платформе) — редактор показывает их
  в своём канале вывода.
- Запросы выполняются по одному, в порядке поступления (у выгрузки
  общее на процесс состояние: активная папка строк, представление таблицы,
  платформа выгрузки). `$/cancelRequest` и `exit` поток чтения обрабатывает
  сразу, не дожидаясь очереди.

## 2. Жизненный цикл

1. `initialize` — первым; любой другой запрос до него получает `-32002`.
   Повторный `initialize` — `-32600`.
2. Рабочие запросы.
3. `shutdown` — сервер закрывает базы и больше ничего не выполняет: любой
   запрос после него получает `-32600`.
4. Уведомление `exit` — процесс завершается: код 0, если до этого был
   `shutdown`, иначе 1. Конец stdin равносилен `exit`. Незавершённые запросы
   при этом отменяются.

Уведомления клиента, которых сервер не знает (`initialized`, `$/setTrace`),
пропускаются без ответа.

## 3. Совместимость версий

`protocolVersion` — строка `MAJOR.MINOR`. Сервер обслуживает клиента, когда
мажорные версии равны, а минорная версия клиента не больше серверной; иначе
`initialize` отвечает `-32010`, в `data` — `serverProtocolVersion` и
`serverVersion` (версия исполняемого файла). Правила развития:

- новый необязательный параметр, новое поле ответа, новый метод или
  уведомление — минорная версия +1;
- удаление, переименование, смена смысла поля или метода — мажорная +1.

Клиент пропускает поля ответа, которых не знает; сервер пропускает
неизвестные поля параметров. Расширение и исполняемый файл выпускаются
вместе: `serverInfo.version` позволяет расширению предупредить о паре из
разных выпусков, даже когда протокол совместим.

## 4. Базы

Сервер знает базы из двух мест; список отдаёт `infobases/list`.

1. **Настройки** — записи `[[database]]` файлов `ibcmd-rs.toml` (слои как у
   командной строки, см. `crate::settings`; верхний слой просматривается
   первым). Слой «текущий каталог» — `workspaceFolder` из `initialize`, если
   задан (проект может держать `ibcmd-rs.toml` в git); `settingsFile` читается
   вместо слоёв, как `IBCMD_RS_CONFIG`.
2. **`initialize.infobases`** — базы, которые добавляет редактор; запись с тем
   же `id` заменяет запись настроек.

Источник таблицы Config:

- `mssql` — база SQL Server: сервер записи, иначе `db-server` настроек
  (`IBCMD_RS_DB_SERVER`), иначе `localhost`; логин — из `infobases/connect`,
  иначе `db-user` настроек, иначе вход Windows;
- `rows-dir` — папка сохранённых строк `<FileName>__part<N>.bin` (сырой
  deflate, как их хранит таблица; формат `mssql-dump-config --rows-dir`).
  Ключ `rows-dir` записи `[[database]]` (относительный путь — от папки файла
  настроек) или поле `rowsDir` записи `initialize`. Только чтение: в такой
  папке нет ConfigSave.

`id` базы — `сервер/имя` или `имя`, если сервер не задан. Запись настроек с
маской (`name = "bsp_*"`) помечена `mask: true`: её открывает
`infobases/connect` с параметром `database`, и дальше база известна под своим
`id` (`sql02/bsp_demo`).

Платформа базы — из записи (`platform`), иначе по правилам настроек
(`IBCMD_RS_PLATFORM`, `platform` файла, папка исполняемого файла), иначе
8.3.27. Она задаёт формат XML (8.3.x — 2.20, 8.5.x — 2.21) и написание
мелочей конкретной сборки.

**Пароль** хранится в SecretStorage редактора и приходит только в памяти —
параметром `password` метода `infobases/connect`. Сервер не пишет его ни в
файлы, ни в ответы, ни в `log`; при закрытии базы буфер затирается. Без него
используется `IBCMD_DB_PSW`, как в командной строке.

## 5. Методы

Параметры и результаты — объекты; имена полей в camelCase. Полное имя
объекта — как в `ConfigDumpInfo.xml`: `Configuration`, `Catalog.Банки`,
`Catalog.Банки.Form.ФормаЭлемента`, `Subsystem.А.Subsystem.Б`. Пути файлов —
относительные пути выгрузки через `/`.

### `initialize`

```json
{"protocolVersion": "1.0",
 "clientInfo": {"name": "ibcmd-rs-vscode", "version": "0.5.0"},
 "workspaceFolder": "C:\\src\\erp",
 "settingsFile": null,
 "infobases": [{"name": "demo", "rowsDir": "C:\\rows\\demo", "platform": "8.3.27"},
               {"id": "erp", "name": "erp_prod", "server": "sql01"}]}
```

`protocolVersion` обязателен; остальное нет. Запись `infobases`: `name`
(обязательно), `id`, `server`, `rowsDir`, `platform`.

```json
{"protocolVersion": "1.0",
 "serverInfo": {"name": "ibcmd-rs", "version": "0.4.0"},
 "capabilities": {"methods": ["initialize", "shutdown", "infobases/list", "..."],
                  "notifications": ["progress", "log"],
                  "cancelRequest": true},
 "settingsFiles": ["C:\\src\\erp\\ibcmd-rs.toml"]}
```

Ошибки: `-32602` (нет `protocolVersion`, ошибка в записи `infobases`),
`-32010` (версия), `-32014` (не читается файл настроек).

### `shutdown`

Без параметров, результат `null`.

### `infobases/list`

```json
{"infobases": [
  {"id": "demo", "name": "demo", "source": "rows-dir", "rowsDir": "C:\\rows\\demo",
   "platform": "8.3.27", "xmlVersion": "2.20",
   "platformSource": "C:\\src\\erp\\ibcmd-rs.toml:5",
   "mask": false, "origin": "C:\\src\\erp\\ibcmd-rs.toml:5", "connected": false},
  {"id": "sql02/bsp_*", "name": "bsp_*", "server": "sql02", "source": "mssql",
   "platform": "8.5.1.1150", "xmlVersion": "2.21", "mask": true, "...": "..."}]}
```

`origin` — `<файл>:<строка>` записи настроек или `initialize`; `connected` —
открыта ли база.

### `infobases/connect`

```json
{"infobase": "sql02/bsp_*", "database": "bsp_demo", "user": "reader", "password": "..."}
```

Открывает базу с этим логином (заменяя открытую раньше) и читает первый
уровень дерева — это проверка логина и базы. `database` нужен для маски.

```json
{"infobase": "sql02/bsp_demo", "source": "mssql", "platform": "8.5.1.1150",
 "xmlVersion": "2.21",
 "configuration": {"id": "Configuration", "label": "БСП", "nodeType": "configuration", "...": "..."}}
```

Остальные методы открывают базу сами при первом обращении с логином по
умолчанию. Ошибки: `-32011`, `-32602` (маска без `database`, нет папки
строк), `-32014` (вход, база).

### `tree/children`

```json
{"infobase": "demo", "node": "Configuration/CommonForms"}
```

Дерево по уровням, по мере раскрытия. `node`:

| `node` | Дети |
|---|---|
| нет | узел конфигурации (`id: "Configuration"`) |
| `Configuration` | группы видов объектов в порядке конфигуратора: `Configuration/Catalogs`, ... |
| `Configuration/<Коллекция>` | объекты вида в порядке строки конфигурации |
| `<полное имя>` | группы принадлежащих объектов: `Catalog.Банки/Forms`, `/Templates`, `/Recalculations`, `/Subsystems` |
| `<полное имя>/<Коллекция>` | принадлежащие объекты |

```json
{"nodes": [
  {"id": "CommonForm.ФормаСлева", "label": "ФормаСлева", "nodeType": "object",
   "kind": "CommonForm", "fullName": "CommonForm.ФормаСлева",
   "uuid": "5b6f3a52-0c0e-4d0b-9d49-3f7f2f8e1a11",
   "path": "CommonForms/ФормаСлева.xml", "hasChildren": false}]}
```

Группа: `nodeType: "group"`, `kind` — вид её объектов, `count`. Ошибки:
`-32011`, `-32012` (нет такого узла).

### `objects/status`

```json
{"infobase": "demo", "sourceDir": "C:\\src\\demo", "objects": ["CommonForm.ФормаСлева"]}
```

Сверка базы и папки исходников файл за файлом: объекты выгружаются в память
и сравниваются с файлами папки побайтно. Файлы объекта — его описание
(`<Коллекция>/<Имя>.xml`) и всё в его папке (`<Коллекция>/<Имя>/`, вместе
с формами и макетами); у конфигурации — `Configuration.xml` и `Ext/`. Папки
с точкой (`.git`, `.ibcmd`) не смотрятся. Без `objects` — вся конфигурация
(выгрузка всей конфигурации в память, на больших базах — минуты) и объекты
верхнего уровня, которые есть только в папке.

```json
{"objects": [
  {"object": "CommonForm.ФормаСлева", "kind": "CommonForm", "status": "modified",
   "version": "a00112dce496adb0",
   "changed": ["CommonForms/ФормаСлева/Ext/Form/Module.bsl"],
   "baseOnly": ["CommonForms/ФормаСлева/Ext/Form.xml"],
   "localOnly": ["CommonForms/ФормаСлева/Ext/Extra.txt"]}]}
```

`status`: `same` (все файлы как в базе), `modified`, `notExported` (в папке
нет ни одного файла объекта), `notInBase` (объект есть только в папке).
`version` — отпечаток версий строк объекта из строки `versions`: меняется,
когда объект меняется в базе.

### `objects/export`

```json
{"infobase": "demo", "objects": ["CommonForm.ФормаСлева", "Configuration"],
 "targetDir": "C:\\src\\demo"}
```

Выгрузка выбранных объектов в папку исходников: файлы объекта пишутся так,
как их пишет полная выгрузка (тот же код и те же параметры, что у
`mssql-dump-config --rows-dir|--database ... --object ...`), файлы объекта,
которых выгрузка больше не пишет, удаляются, остальное в папке не трогается
(`ConfigDumpInfo.xml` пишет только полная выгрузка). Все объекты запроса
выгружаются одним проходом: индексы выгрузки строятся один раз.

```json
{"objects": [{"object": "CommonForm.ФормаСлева", "version": "a00112dce496adb0",
              "written": ["CommonForms/ФормаСлева.xml", "..."], "removed": [], "unchanged": 0}]}
```

### `objects/import`

```json
{"infobase": "erp", "sourceDir": "C:\\src\\erp", "objects": ["Catalog.Банки"],
 "confirm": true, "verify": true}
```

Загрузка выбранных объектов в ConfigSave — `mssql-stage-source-objects
--path-prefix <Коллекция>/<Имя>` (у конфигурации `Configuration` и `Ext`) с
проверкой загрузки (`verify`, по умолчанию да): перед записью конфигурация,
какой она станет, выгружается в памяти и сравнивается с папкой. Загрузка
**заменяет** содержимое ConfigSave, поэтому нужен `confirm: true`; применяет её
`ibcmd infobase config apply`. Объект может быть новым (его ещё нет в базе).
Результат: `{"report": <отчёт mssql-stage-source-objects>}`. Ошибки: `-32013`
(папка строк), `-32015` (нет `confirm`), `-32014`.

### `source/read`

```json
{"infobase": "demo", "path": "CommonForms/ФормаСлева/Ext/Form/Module.bsl"}
```

Файл объекта так, как его выгрузила бы база, без записи на диск (выгрузка
объекта в память, дальше из кэша).

```json
{"path": "CommonForms/ФормаСлева/Ext/Form/Module.bsl", "object": "CommonForm.ФормаСлева",
 "version": "a00112dce496adb0", "exists": true, "encoding": "utf-8",
 "content": "\ufeff&НаСервере\r\nПроцедура ..."}
```

Текст в UTF-8 отдаётся как есть, с BOM (`\ufeff`) и концами строк выгрузки;
двоичный файл (картинка) — `encoding: "base64"`. `exists: false` — выгрузка
такого файла не пишет. Ошибки: `-32602` (путь не относительный или не файл
объекта), `-32012`.

### `config/pending`

```json
{"infobase": "erp"}
```

Есть ли в ConfigSave неприменённые изменения и нужна ли для них
реструктуризация — проверка `mssql-apply-check` (только чтение).

```json
{"pending": true, "stagedRows": 12, "needsRestructuring": false, "conclusive": true,
 "summary": "Реструктуризация не нужна.\n...", "verdict": {"...": "..."}}
```

Ошибки: `-32013` (папка строк), `-32014`.

## 6. Уведомления сервера

- `progress` — ход долгого запроса:
  `{"requestId": 7, "message": "CommonForm.ФормаСлева", "done": 1, "total": 2}`.
  Сначала выгрузка (`"export of 2 objects (5 rows)"`, `done` 0, затем
  `total`), потом объект за объектом.
- `log` — сообщения для канала вывода:
  `{"level": "info", "message": "infobase demo: stored rows of ..."}`,
  уровни `error`, `warning`, `info`, `debug`.

## 7. Отмена

`$/cancelRequest` с `{"id": <id запроса>}`. Запрос в очереди не начинается;
выполняющийся останавливается на ближайшем шаге: перед чтением очередной
порции строк, перед разбором очередной строки, перед передачей очередного
файла на запись, между объектами сверки и выгрузки в папку
(`crate::cancel`). Ответ отменённого запроса — ошибка `-32800`. Отмена
неизвестного или уже выполненного запроса ничего не делает. Загрузка
(`objects/import`) и проверка ConfigSave отменяются только до начала.

## 8. Ошибки

| Код | Когда |
|---|---|
| -32700 | тело не JSON |
| -32600 | пакет сообщений, повторный `initialize`, запрос после `shutdown` |
| -32601 | нет такого метода |
| -32602 | неверные параметры (в том числе путь `source/read`, маска без `database`) |
| -32603 | сбой внутри сервера (паника), сообщение называет метод |
| -32002 | запрос до `initialize` |
| -32800 | запрос отменён |
| -32010 | несовместимая версия протокола (`data`: `serverProtocolVersion`, `serverVersion`) |
| -32011 | нет базы с таким `id` |
| -32012 | в конфигурации нет такого объекта или узла |
| -32013 | операции нужен SQL Server, а база — папка строк |
| -32014 | операция выполнилась с ошибкой (SQL Server, выгрузка, диск); `data.causes` — цепочка причин |
| -32015 | запись в базу без `confirm: true` |

## 9. Кэш и согласованность

Сервер держит открытые базы до `shutdown`. Для каждой базы:

- соединения встроенного клиента SQL Server (`IBCMD_RS_SQL_CONNECTIONS`,
  по умолчанию 4);
- опись: имена строк, строка `versions`, `root` и строка конфигурации (виды
  и объекты верхнего уровня, вложенные объекты конфигурации, под чьими id
  хранятся её `Ext`-тела), имена объектов — по видам, по мере раскрытия;
- выгруженные в память файлы объектов (до 256 МиБ на базу).

Каждый запрос сначала читает заголовки строк и `versions` (через
представление, которое видит выгрузка: строки активного динамического
обновления под своими именами). Если отпечаток `versions` изменился, опись и
кэш файлов сбрасываются: всё, что сервер отдаёт, соответствует базе на момент
запроса. Кэш файлов сбрасывается целиком, а не по объекту: выгрузка объекта
зависит и от других объектов (имена типов, состав конфигурации).
Отпечаток `versions` — единственный признак изменения: платформа пишет новую
версию каждой строке, которую записывает. Строка, переписанная в обход
`versions`, видна только после следующей смены `versions` (так проверяет
тест `serve_rereads_an_object_when_versions_changes`).

Объект хранится в строке описания `<uuid>`, строках тел `<uuid>.<n>` и
строках принадлежащих ему объектов (формы, макеты, перерасчёты, вложенные
подсистемы — по спискам в строке владельца); конфигурация — в своей строке и
строках своих вложенных объектов. Выгрузка только этих строк (выборка
`--file-name` у `mssql-dump-config`) пишет файлы объекта такими же, как
полная выгрузка: тест сравнивает каждый объект трёх офлайн-конфигураций с
`cf export`.

## 10. Командная строка

| Метод | Команда |
|---|---|
| `tree/children` | `ibcmd-rs objects tree [--node <узел>]` |
| `objects/status` | `ibcmd-rs objects status --source-dir <папка> [--object <имя>]...` |
| `objects/export` | `ibcmd-rs objects export --target-dir <папка> --object <имя>...`; в пустой каталог — `mssql-dump-config --object <имя>...` |
| `source/read` | `ibcmd-rs objects read --path <путь> [-o <файл>]` |
| `objects/import` | `mssql-stage-source-objects --path-prefix <путь>... --verify` |
| `config/pending` | `mssql-apply-check --database <база> --json` |

Источник у `objects` — `--rows-dir <папка>` или `--server/--database/--sql-user`
и `--platform`, как у `mssql-dump-config`.

## 11. Ограничения прототипа

- `objects/import` и `config/pending` подключены к функциям загрузки и
  проверки, но проверены только отказом на папке строк: SQL Server в тестах
  нет. Путь SQL Server у остальных методов — тот же код выгрузки, что у
  `mssql-dump-config --database`, но тоже без теста в этой задаче.
- На SQL Server каждый запрос читает заголовки всех строк Config и строку
  `versions` (ERP УХ: около 150 тысяч заголовков) — цена проверки
  согласованности. Дальше — хранить отпечаток строки `DynamicallyUpdated` и
  заголовок `versions`, чтобы перечитывать заголовки только при изменениях.
- Сообщения движка в stderr не превращаются в `log`.
- Запросы выполняются по одному: дешёвый запрос ждёт долгого (его можно
  отменить).
- Расширения конфигурации (ConfigCAS) сервер пока не показывает.
