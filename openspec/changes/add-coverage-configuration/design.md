# Дизайн: конфигурация покрытия

## Термины

- **Набор** — одна конфигурация для пары «класс метаданных и версия платформы»
  (например, справочники на 8.5.1.1150, XML 2.21).
- **Шаблон** — нативно выгруженный clean-room объект класса.
- **Вариант** — копия шаблона, в которой одно свойство принимает одно значение.
  Имя варианта — `Cov<Свойство>_<Значение>`, оно же идентифицирует кейс.
- **Пространство значений** — для каждого свойства класса список значений с
  источником каждого:
  - `boolean`: оба значения;
  - `observed`: значение встречено в нативной выгрузке названного корпуса;
  - `declared`: значение объявлено моделью EDT, после импорта пакета `mdclass`.

## Три вида исходников

Каждый вид доказывается своим нативным маршрутом и проверяется своим входом
`cf export`. Все три работают с `ibcmd` 8.5.1.1150 на Linux; на 8.5.1.1150 это
проверено вручную.

| Вид | Набор | Нативный маршрут | Наш вход |
|---|---|---|---|
| Конфигурация | один `.cf` на набор | `infobase create --import=<дерево>` → `config export` → `config save` → `infobase create --load` → `config export` | `cf export <.cf>` |
| Расширение | одно расширение на вариант в общей базе с базовой конфигурацией | `extension create --name --name-prefix --purpose` → `config import --extension` → `config export --extension` → `config save --extension` → загрузка `.cfe` в новую базу → `config export --extension` | `cf export <.cfe>` |
| Внешняя обработка и отчёт | один файл на вариант | `config import --out=<файл> <корневой.xml>` → `config export --file=<файл> <каталог>` (корневой XML ложится рядом с каталогом) → сборка заново из выгрузки → вторая выгрузка | `cf export <.epf/.erf>` |

Для `config import --out` и `config export --file` нужна база-контекст: годится
пустая файловая база.

Варианты расширений:
- свойства самого расширения (назначение, префикс, безопасный режим, защита
  от опасных действий, режим совместимости и т.п.);
- собственные объекты расширения (те же шаблоны классов, что у конфигурации);
- заимствованные объекты базовой конфигурации со своими реквизитами и
  контролем свойств;
- формы с изменениями и перехватчики методов (`&Перед`, `&После`, `&Вместо`,
  `&ИзменениеИКонтроль`).

Варианты внешних обработок и отчётов:
- свойства корня;
- по одному варианту на каждый вид дочернего объекта: реквизит каждого
  примитивного типа, табличная часть, форма, макет каждого типа (табличный
  документ, текст, двоичные данные, СКД, HTML), команда;
- у отчёта дополнительно основная схема компоновки, формы настроек и
  хранилища вариантов.

## Входы и генерация

Входы коммитятся в `tests/fixtures/coverage/<версия>/<класс>/input/`:
- шаблон объекта;
- минимальное дерево конфигурации;
- `values.json`: пространство значений.

`tools/coverage/generate.py` строит из них XML-дерево набора. Генерация
детерминирована: uuid объекта и пары сгенерированных типов выводятся как
UUIDv5 от id варианта, порядок объектов фиксирован, при тех же входах дерево
получается байт в байт тем же.

Входы нового набора создаёт `tools/coverage/new_set.py`:
- основа — нативная выгрузка пустой базы;
- шаблон — объект, который платформа дописывает из минимальной затравки (имя,
  сгенерированные типы по образцу объекта того же класса в корпусе);
- пространство значений — `tools/coverage/observe_values.py` по нативной выгрузке
  корпуса. В репозиторий
попадают только сами значения свойств и имя источника, но не объекты корпуса.

## Нативный эталон

`tools/coverage/native_round_trip.py` (Python; Linux и Windows, файловая база;
SQL Server — на лабораторном runner-е) делает следующее:

1. `ibcmd infobase create --import=<дерево>` в новую базу. Если платформа
   отвергает набор, отвергнутые варианты находятся бисекцией и записываются
   статусом `platform_refused` с первой строкой её сообщения. Остальные
   загружаются заново.
2. Нативная выгрузка (раунд 1), `config save` в `.cf`, новая база из этого `.cf`
   и вторая выгрузка (раунд 2). Деревья раундов должны совпасть, без учёта
   `ConfigDumpInfo.xml`, как в `add-fast-parity-evidence`.
3. Запись `manifest.json`:
   - сборка платформы и sha256 `ibcmd`, версия XML, коммит генератора, sha256 входов;
   - для каждого варианта: свойство, значение, статус и список нативных файлов
     с размером и sha256.

## Что коммитится

Наборы расширений лежат в `tests/fixtures/coverage/<версия>/extensions/<набор>/`,
внешних файлов — в `…/external/<набор>/`. Вместо `configuration.cf.b64` там
лежат файлы вариантов (`<вариант>.cfe.b64`, `<вариант>.epf.b64`) и нативное
дерево каждого варианта.

`tests/fixtures/coverage/<версия>/<класс>/`:
- `input/`;
- `configuration.cf.b64`;
- `native/` — дерево раунда 2;
- `manifest.json`;
- `baseline.json` — варианты, которые у ibcmd-rs совпадают.

Все объекты созданы генератором и названы по кейсам. Данных прикладных
конфигураций в наборе нет.

## Офлайн-проверка

`tests/coverage_corpus.rs` для каждого набора:
- проверяет хеши входов и `.cf` по манифесту;
- выгружает `.cf` маршрутом `cf export` без платформы и сверяет каждый файл
  варианта с нативным.

Итог по варианту: `equal`, `different` (с первым расходящимся файлом) или
`refused` (с сообщением ibcmd-rs).

Тест падает, если вариант из `baseline.json` перестал быть `equal`, или если
манифест расходится с фикстурой. Новые совпадения он печатает, чтобы их можно
было внести в `baseline.json`. Счёт покрытия по набору (сгенерировано,
доказано платформой, отвергнуто платформой, совпадает, отличается, отвергнуто
нами) печатается в выводе теста.

## Три уровня проверки

1. Наборы с вариантами: быстрый офлайн-тест в каждом PR, точное место ошибки.
2. Сводная конфигурация (`tools/coverage/combine.py`): все подтверждённые
   варианты всех наборов конфигурации одной платформы в одной конфигурации,
   доказанной платформой. UUID объектов перевыпускаются с учётом класса,
   потому что имена вариантов повторяются в разных классах. Офлайн-тест
   проверяет её как набор и следит, чтобы она не отстала от исходных наборов.
   На лабораторном runner-е по ней идёт сквозной прогон через базу: загрузка,
   выгрузка, применение.
3. Типовые конфигурации: приёмка и поиск неизвестного. Найденное расхождение
   становится вариантом уровня 1 (навык `coverage-case`) до исправления.

## Сочетания

Связанные значения (платформа отвергает одно без другого) задаются вариантом-
сочетанием в `values.json` (`combinations`). Вид `xml` заменяет вложенный
элемент целиком.

## Порядок развития

1. Справочники на 8.5.1.1150, файловая база (VPS).
2. Остальные классы метаданных той же версии.
3. 8.3.27.2214 и 8.5.1.1529, SQL Server и файловая база, на лабораторном runner-е
   (`docs/lab/runner-requirements.md`).
4. Расширения и внешние обработки и отчёты на 8.5.1.1150.
5. Формы: типы элементов и их свойства по пакету `com._1c.g5.v8.dt.form.model`;
   затем макеты, СКД, диаграммы.
6. Импорт `mdclass` из EDT существующим импортёром и пространство `declared`.
7. Слой старых форматов: объекты, созданные на старых платформах, которые есть
   у владельца, и перенесённые без пересохранения. У варианта записывается
   версия платформы, которая его создала.
8. Цикл с типовыми: класс расхождения, найденный на типовой конфигурации,
   ужимается до варианта одного из наборов.

## Чем не является

- Не доказательство полного паритета: комбинации свойств покрываются только
  там, где известна их взаимозависимость (порядок, хвосты записи).
- Не замена типовых конфигураций: они находят неизвестные форматы.
- Не источник правил разбора: правило остаётся доказанным только нативным
  эталоном, а не генератором.
