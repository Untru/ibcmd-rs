# Физические строки конфигурации PostgreSQL и SQL Server

Исследование [#367](https://github.com/Untru/ibcmd-rs/issues/367), 24 ноября 2026.
Нативные `ibcmd` 8.3.27.2342 и 8.5.1.1529, PostgreSQL 17.2-4.1C x64,
SQL Server 2025 Standard Developer 17.0.1155.3. Первичные прогоны начинались с отдельных пустых баз. Для повторной попытки БСП с XML 2.20 использованы те же базы после отказа на XML 2.21. Один каталог
XML подавался обеим СУБД. Создание базы, импорт, загрузку CF и применение выполнял штатный `ibcmd`.

**Основной результат.** Для одного поставочного CF БСП 3.1.11.309
штатная загрузка в `configsave` на каждой сборке создала одинаковые
7 212 физических ключей в PostgreSQL и SQL Server. Из них 7 211 имели
одинаковые хранимые байты. Отличалась только `versions`, при совпадающих
длине, DataSize и Attributes внутри каждой пары. Сравнение двух сборок
внутри каждой СУБД также оставляет одно различающееся тело `versions`.
После применения CF все четыре команды вернули −1 с ошибкой SDBL на
реструктуризации (быстрая вставка без удаления индексов). В каждом
случае в активной таблице оказалось 7 212 строк, стадия опустела.
В каждой паре активных таблиц снова совпало 7 211 тел, отличалась
только `versions`. Оба XML-импорта той же версии БСП на 8.5 завершились успешно, но дали
разные наборы ключей и тел. Способ загрузки входит в условия сравнения.

## Как повторить измерение

1. Подготовить пустую MSSQL-базу с collation `Cyrillic_General_CI_AS`
   и отдельный экземпляр PostgreSQL для 1С. Для записи SQL в журнале
   частного экземпляра задать `log_statement=all`,
   `log_parameter_max_length=0`, префикс с базой и PID. Сырые журналы
   остаются на стенде. Во время длительных прогонов на одноразовом PG включили асинхронное подтверждение фиксации (`synchronous_commit=off`, `fsync=on`). Измерялись видимые после команд строки, время выполнения и устойчивость к сбою питания не измерялись.
2. Задать общие аргументы `--dbms=<PostgreSQL|MSSQLServer>`,
   `--db-server=<server>`, `--db-name=<new-db>`, `--data=<unique-dir>`.
   Для PG передать локальные реквизиты подключения, для MSSQL использовалась
   встроенная аутентификация Windows. Выполнить три отдельные команды:

   ```text
   ibcmd infobase create <common> [--create-database]
   ibcmd infobase config import <common> <source-directory>
   ibcmd infobase config apply <common> --force
   ```

   `--create-database` нужен здесь при создании PG-базы. После возврата
   каждой команды зафиксировать её код и снимок всех четырёх таблиц до
   следующего вызова. При ошибке снять фактическое состояние и остановить
   эту последовательность.
3. Повторить следующие запросы для `config`, `configsave`, `params`, `files`
   в покоящихся тестовых базах. Колонки и их порядок сверить с
   `information_schema.columns` по `ordinal_position`, для PG уточнить
   пользовательский тип через `udt_name`.

   ```sql
   -- PostgreSQL
   SELECT filename::text, partno, attributes, datasize, octet_length(binarydata),
          encode(sha256(binarydata), 'hex') FROM config;
   -- SQL Server
   SELECT FileName, PartNo, Attributes, DataSize, DATALENGTH(BinaryData),
          LOWER(CONVERT(varchar(64), HASHBYTES('SHA2_256', BinaryData), 2)) FROM Config;
   ```

   Сопоставить строки по точному имени и номеру части. Для общих ключей
   сопоставить SHA-256 хранимых байтов, отдельно размер и атрибуты.
   Creation и Modified характеризуют отдельный запуск и не входят в
   сравнение. Нулевые таблицы учитываются. Публичные результаты содержат
   только агрегаты.

Деревья XML идентифицировались следующим отпечатком. Отсортировать файлы
по относительному пути с разделителем `/` в порядке Unicode. Для каждого
добавить в SHA-256 его путь в UTF-8, нулевой байт и 32 байта SHA-256 файла.
Включать `ConfigDumpInfo.xml`, если он присутствует.

| Вход | Файлов | SHA-256 дерева |
|---|---:|---|
| tiny-xml-2.21 | 4 | `bb30cc7bbd06a5597d971ac638a4b4acb1f2cec1e13ecbf3536f1beee5a2f158` |
| empty-xml-2.20 | 3 | `1790dbacedf1450db2fbe792eb52636d17b7717bf3383a10a4a746d0ddaa7645` |
| bsp-xml-2.20 | 9 157 | `98d6e63315b94540abf044a4fa9c382162d56450682caeed2d98e32bf2e1936b` |
| bsp-xml-2.21 | 9 156 | `75900d720d91e059e0198905835101a48e0fca066183abd7b777efa7bb008a4f` |

## Таблицы и ключи

У таблиц `config`, `configsave`, `params` и `files` одинаковый набор и
порядок колонок внутри каждой СУБД. Все семь колонок обязательны.
Индекс каждой из четырёх таблиц уникален по паре имя файла, номер части.

| PostgreSQL | Тип | SQL Server | Тип |
|---|---|---|---|
| filename | mvarchar(128) | FileName | nvarchar(128) |
| creation | timestamp without time zone | Creation | datetime2(0) |
| modified | timestamp without time zone | Modified | datetime2(0) |
| attributes | integer | Attributes | smallint |
| datasize | bigint | DataSize | bigint |
| binarydata | bytea | BinaryData | varbinary(max) |
| partno | integer | PartNo | int |

В PostgreSQL длину пользовательского типа имени показывает
`format_type(pg_attribute.atttypid, pg_attribute.atttypmod)`.
В SQL Server максимальная длина `-1` в каталоге соответствует `max`.
Для проверки порядка ключей используются `pg_indexes.indexdef` и
`sys.index_columns.key_ordinal`.

## Как читать агрегаты

[rows.tsv](rows.tsv) содержит по строке на сборку, вход, фазу и таблицу.
`pg_rc` и `ms_rc` — коды нативного процесса (Windows 0xffffffff
записан как −1). Прочерк означает отсутствие снимка этой фазы,
ноль — измеренное нулевое значение. `shared_keys` — число общих пар
имя/часть. Вычитание его из `pg_rows` или `ms_rows` даёт число ключей
только на соответствующей стороне. `equal_sha256` считает совпавшие
тела среди общих ключей. Последняя колонка группирует остальные по
известным служебным именам и классу `other`. `unequal_length` относится
к фактической длине BinaryData, `unequal_datasize` — к колонке DataSize.

| Вход | Идентификация |
|---|---|
| tiny-xml-2.21 | `tests/fixtures/file-infobase/tiny-source`, 4 файла |
| empty-xml-2.20 | `tests/fixtures/file-infobase/empty-xml-8.3.27` |
| bsp-xml-2.21 | БСП 3.1.11.309, режим совместимости 8.3.24, 9 156 файлов |
| bsp-xml-2.20 | БСП 3.1.11.309, режим совместимости 8.3.24, выгрузка 8.3.27.2214 |
| bsp-cf | БСП 3.1.11.309, поставочный CF, 67 167 823 байта, SHA-256 `4ded13b6b6b5c74f11c544e6be442cbea6f49eb8dede3424841b4bd6af4b4448` |

Для `bsp-cf` на шаге загрузки выполнить
`ibcmd infobase config load <common> <file.cf>`. Для прогона
`bsp-xml-2.20` использованы базы после отказа 8.3 на XML 2.21:
повторный снимок перед импортом подтвердил пустые `config` и
`configsave`. Фаза `before_retry` обозначает этот исходный снимок. Для неё `n/a` в колонках кода означает, что команда в этот момент не запускалась.

Исходный [протокол создания MSSQL-баз](../../../../../docs/apply/native-infobase-create.md)
содержит DDL, порядок инициализации и повторные запуски с различными
служебными значениями для 8.3.27.2214 и 8.5.1.1150. В
[протоколе ERP УХ](../parity-8327-20260919.md) измеряли выгрузку
конфигурации 3.3.3.3 на MSSQL с 8.3.27.2214. Для ERP УХ 3.3.5.1 ниже приведены пары CF на обеих сборках и отдельный нативный XML-контроль 8.3.27.2342 на PostgreSQL. У проверенных локальных деревьев ERP WE и «Управление холдингом»
другие имена конфигурации. Их результаты в матрицу ERP УХ не включены.

24.11.2026 в [карточке релиза ERP УХ 3.3.3.3](https://releases.1c.ru/version_files?nick=ERP_UH33&ver=3.3.3.3)
проверена позиция «Полный дистрибутив» от 19.06.2026. Поставщик указывает
архив `ERP_UH_3_3_3_3_setup1c.zip`, 3 462 262 855 байт и минимальную
платформу 8.3.27.1989. Карточка релиза и начатая загрузка сами по себе не подтверждают измерение строк. Совпадения номера релиза недостаточно для отождествления с деревом исторического замера на 140 709 файлов.

## Служебные строки и части

Из 7 209 логических имён в стадии загрузки CF 7 207 занимали одну
физическую строку, одно — две, ещё одно — три. `partno` начинается
с нуля. Полные части этих двух файлов занимали 10 000 000 байт.
Во всех четырёх итоговых снимках после применения CF у всех 7 209
логических имён в `config` склеенные части дали ровно один полный поток
raw DEFLATE. В `params` этот тест прошли 17 из 23 имён, в `files` — 0 из 4.
Для воспроизведения группировать по имени, склеивать бинарные данные
в порядке `partno`, использовать `zlib.decompressobj(-15)`, проверять
конец потока и отсутствие `unused_data` и `unconsumed_tail`. Последние
два счётчика относятся к конкретному состоянию БСП.

Во всех четырёх таблицах по сохранённым фазам отсутствовал ключ
`DynamicallyUpdated` (сверка имени без учёта регистра). Динамическое
обновление работающей базы в этот сценарий не входило.
В четырёх CF-стадиях присутствовали `root`, `version`, `versions`,
отсутствовал `deleted`. В успешно построенной XML-стадии БСП на PG
присутствовали все четыре. После применения маленькой конфигурации
на PG остались `root`, `version` и `versions`.

В паре `empty-xml-2.20` оба применения вернули 0. В активной таблице
PG оказалось пять строк, в MSSQL — три. На MSSQL из трёх перечисленных
служебных имён присутствовала только `versions`. Случай показывает,
почему код завершения фиксируется отдельно от содержания таблицы.

## Что показал импорт XML

В состоянии после импорта БСП 3.1.11.309 формата 2.21 на 8.5.1.1529
обе команды вернули 0. В PG оказалось 7 213 физических строк стадии,
в MSSQL — 6 954. Все 6 954 ключа MSSQL нашлись в PG. Для 5 609 общих
ключей совпала SHA-256 хранимых байтов. Среди остальных 1 345 ключей
один принадлежал `versions`. На обеих сторонах по три физических строки
имели ненулевой номер части. У штатного применения этой MSSQL-базы
проверка метаданных завершилась ошибкой целостности, активный `Config`
остался пуст.

На 8.3.27.2342 обе СУБД отказали при чтении XML 2.21 (неизвестная
версия формата). После повторного импорта БСП из XML 2.20 в PG появились
7 213 строк `configsave`, включая `root`, `version`, `versions` и `deleted`.
MSSQL отклонил ссылку на предопределённый элемент и сохранил семь строк,
ни один из этих семи ключей не совпал с ключами успешной стадии PG.

### Разбор 1 345 различающихся тел XML-стадии БСП на 8.5

После сортировки и склейки частей по номеру для каждого из этих имён
проверили SHA-256 всех частей против снимка импорта. Для анализа
использовались только тела с совпавшими исходными хешами: в PG их
удалось прочитать из опубликованной конфигурации, в MSSQL — из
сохранившейся стадии. Один полный поток raw DEFLATE (zlib с окном −15)
успешно распаковался с обеих сторон для каждого из 1 345 имён.
У всех 1 345 распакованные байты тоже различались.

| Класс имени | Число | Результат сравнения |
|---|---:|---|
| UUID с суффиксом | 1 343 | Распакованные тела имеют одинаковую длину. Внутри находятся контейнеры V8 формата 15. У каждой пары совпадают порядок и имена элементов, данные каждого элемента и байты заголовка элемента начиная со смещения 16. |
| UUID без суффикса | 1 | Различная длина распакованных тел |
| `versions` | 1 | Различная длина распакованных тел |

Проверка контейнера следует [чтению формата 15](../../../../../crates/ibcmd-v8/src/format15.rs):
прочитать адресную таблицу, для каждой записи собрать блок заголовка и
данных по цепочке страниц. Сопоставить последовательности троек
`(name, raw_header[16..], data)`. Это объясняет, почему для 1 343
физически различных строк совпали данные вложенных элементов. Сырые
хеши в TSV вычислены до распаковки и такого сравнения.

## Какие запросы выполняла платформа на PG

В журнале частного экземпляра выделяли интервал от начала до возврата
нативной команды и фильтровали по имени её базы. Ниже число записей
`statement` или `execute`, SQL которых начинается с соответствующего
`INSERT INTO`, `UPDATE` или `DELETE FROM` и имени таблицы. Одна запись
может затронуть ноль или много строк. Параметры запросов и содержимое
строк в агрегат не входят.

| Корпус и фаза | Таблица | INSERT | UPDATE | DELETE |
|---|---|---:|---:|---:|
| tiny, 8.5, XML import | configsave | 8 | 9 | 10 |
| tiny, 8.5, apply | config | 10 | 9 | 23 |
| tiny, 8.5, apply | configsave | 0 | 0 | 2 |
| БСП, XML import, обе сборки¹ | configsave | 7 213 | 7 216 | 7 215 |
| БСП, apply после XML, обе сборки¹ | config | 7 211 | 7 210 | 14 426 |
| БСП, apply после XML, обе сборки¹ | configsave | 0 | 0 | 2 |
| БСП, apply после XML, обе сборки¹ | params | 19 | 38 | 40 |
| БСП, apply после XML, обе сборки¹ | files | 3 | 4 | 4 |
| БСП, load одного CF, обе сборки | configsave | 7 214 | 14 423 | 14 424 |

¹ На 8.3 использовался XML 2.20, на 8.5 — XML 2.21. В каждой строке
указан счётчик отдельного прогона, одинаковый на двух сборках.

В трассе импорта tiny видны вставка нулевой части, удаление старших
частей по имени, обновление `modified, datasize, binarydata` по
`(filename, partno)` и изменение имён стадии через
`substr(filename, 1, length(filename) - 4)`. При применении встречаются
`INSERT INTO config (SELECT … FROM configsave WHERE filename = …)`,
обновления по имени и части и очистка строк стадии по маске. Это
разные операции с активной таблицей и стадией, включая повторные
записи одного ключа.

## ERP УХ 3.3.5.1 на 8.5.1.1529

На Microsoft SQL Server и PostgreSQL 17.2-4.1C использован один
поставочный CF с SHA-256
`ff27cf72694b66c776211b9f23d1829096432268ed6be87d4eddd32b7468dd59`.
Команды `infobase create`, `config load` и итоговый `config apply --force`
на обеих СУБД вернули 0. PostgreSQL использовал `Russian_Russia.1251`
и `synchronous_commit=off`. Снимки сопоставлены по `(FileName, PartNo)`,
равенство тел проверено по SHA-256 физического `BinaryData`.

| Фаза | Таблица | Строк PG | Строк MSSQL | Общих ключей | Одинаковых тел |
|---|---|---:|---:|---:|---:|
| create | config | 0 | 0 | 0 | 0 |
| create | configsave | 0 | 0 | 0 | 0 |
| create | params | 6 | 6 | 6 | 3 |
| create | files | 1 | 1 | 1 | 1 |
| load | config | 0 | 0 | 0 | 0 |
| load | configsave | 118 440 | 118 440 | 118 440 | 118 439 |
| load | params | 6 | 6 | 6 | 3 |
| load | files | 1 | 1 | 1 | 1 |
| apply | config | 118 440 | 118 440 | 118 440 | 118 439 |
| apply | configsave | 0 | 0 | 0 | 0 |
| apply | params | 25 | 25 | 23 | 18 |
| apply | files | 10 | 10 | 10 | 7 |

В `configsave` после `load` и в `config` после `apply` отличается только
тело `versions`. Атрибуты и `DataSize` совпадают по всем общим ключам.
В каждой из этих таблиц 49 физических строк с ненулевым `PartNo`.

Первый PostgreSQL `apply` прервался при остановке сессии. После
восстановления WAL в `config` и `configsave` было по 118 440 строк.
Повторили только `apply` на той же базе. В итоговом снимке
`configsave` пуста. Снимок после `load` снят до остановки сессии.

По PostgreSQL SQL-журналу во время CF load зафиксировано 118 442
INSERT, 236 810 UPDATE и 236 788 DELETE для configsave. В успешном
повторе apply для config зафиксировано 118 392 INSERT, 118 392 UPDATE
и 236 788 DELETE, для configsave — 2 DELETE. Это число журнальных
записей запросов, включая повторные обращения. Счётчики apply
начинаются после восстановления и не включают прерванную попытку.

## ERP УХ 3.3.5.1 на 8.3.27.2342

Для того же поставочного CF штатные `create`, `load` и `apply --force`
на PostgreSQL 17.2-4.1C и Microsoft SQL Server вернули 0.
Все 12 пар счётчиков строк, общих ключей и одинаковых тел совпали

## Нативный XML-контроль ERP УХ из #370

Штатный `ibcmd` 8.3.27.2342 прочитал этот XML 2.20 в пустой базе
