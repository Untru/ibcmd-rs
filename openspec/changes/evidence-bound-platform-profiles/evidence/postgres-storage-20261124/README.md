# Физические строки конфигурации PostgreSQL и SQL Server

Исследование [#367](https://github.com/Untru/ibcmd-rs/issues/367), 24 ноября 2026.
Нативные `ibcmd` 8.3.27.2342 и 8.5.1.1529, PostgreSQL 17.2-4.1C x64,
SQL Server 2025 Standard Developer 17.0.1155.3. На каждую комбинацию
сборки, корпуса и СУБД создавалась отдельная пустая база. Один каталог
XML подавался обеим СУБД. Создание базы, импорт, загрузку CF и применение выполнял штатный `ibcmd`.

## Как повторить измерение

1. Подготовить пустую MSSQL-базу с collation `Cyrillic_General_CI_AS`
   и отдельный экземпляр PostgreSQL для 1С. Для записи SQL в журнале
   частного экземпляра задать `log_statement=all`,
   `log_parameter_max_length=0`, префикс с базой и PID. Сырые журналы
   остаются на стенде.
2. Задать общие аргументы `--dbms=<PostgreSQL|MSSQLServer>`,
   `--db-server=<server>`, `--db-name=<new-db>`, `--data=<unique-dir>`.
   Для PG передать локальные реквизиты подключения, для MSSQL использовалась
   встроенная аутентификация Windows. Выполнить три отдельные команды:

   ```text
   ibcmd infobase create <common> [--create-database]
   ibcmd infobase config import <common> <source-directory>
   ibcmd infobase config apply <common> --force
   ```

   `--create-database` нужен здесь при создании PG-базы. После возврата
   каждой команды зафиксировать её код и снимок всех четырёх таблиц до
   следующего вызова. При ошибке снять фактическое состояние и остановить
   эту последовательность.
3. Повторить следующие запросы для `config`, `configsave`, `params`, `files`
   в покоящихся тестовых базах. Колонки и их порядок сверить с
   `information_schema.columns` по `ordinal_position`, для PG уточнить
   пользовательский тип через `udt_name`.

   ```sql
   -- PostgreSQL
   SELECT filename::text, partno, attributes, datasize, octet_length(binarydata),
          encode(sha256(binarydata), 'hex') FROM config;
   -- SQL Server
   SELECT FileName, PartNo, Attributes, DataSize, DATALENGTH(BinaryData),
          LOWER(CONVERT(varchar(64), HASHBYTES('SHA2_256', BinaryData), 2)) FROM Config;
   ```

   Сопоставить строки по точному имени и номеру части. Для общих ключей
   сопоставить SHA-256 хранимых байтов, отдельно размер и атрибуты.
   Creation и Modified характеризуют отдельный запуск и не входят в
   сравнение. Нулевые таблицы учитываются. Публичные результаты содержат
   только агрегаты.

## Предыдущие протоколы и входные деревья

- [#478](https://github.com/Untru/ibcmd-rs/pull/478) и
  [протокол 22 октября](../../../../../docs/evidence/postgres-storage-20261022.md)
  сравнивали XML-выгрузку PG и файловой базы на 8.5.1.1529. Для БСП было
  8 710 совпадений из 9 156 с нативной выгрузкой, 446 различий оказались
  общими для двух backend. После ошибки реструктуризации в PG осталось
  7 212 строк в `config`. Этот результат относится к тому запуску.
- [#482](https://github.com/Untru/ibcmd-rs/pull/482) проверял загрузку XML в
  `configsave`, включая `deleted`. [#494](https://github.com/Untru/ibcmd-rs/pull/494)
  проверял другой вход, загрузку CF. Для пустой базы у неё отсутствовал
  `deleted`, а платформа переписывала `versions`. Эти операции нужно
  воспроизводить по отдельности.
- При сверке сохранённых деревьев `pg-tiny-native` и `ms-t4` все четыре
  прикладных файла совпали с `tests/fixtures/file-infobase/tiny-source`.
  У пары `pg-imp2-x/y` все четыре файла совпали друг с другом, в сравнении
  с исходной фикстурой различался только текст общего модуля.
  `ConfigDumpInfo.xml` различался между выгрузками в каждой паре.
  Это сверка файлов на диске, физические строки измеряются отдельно.

## Таблицы и ключи

У таблиц `config`, `configsave`, `params` и `files` одинаковый набор и
порядок колонок внутри каждой СУБД. Все семь колонок обязательны.
Индекс каждой из четырёх таблиц уникален по паре имя файла, номер части.

| PostgreSQL | Тип | SQL Server | Тип |
|---|---|---|---|
| filename | mvarchar(128) | FileName | nvarchar(128) |
| creation | timestamp without time zone | Creation | datetime2 |
| modified | timestamp without time zone | Modified | datetime2 |
| attributes | integer | Attributes | smallint |
| datasize | bigint | DataSize | bigint |
| binarydata | bytea | BinaryData | varbinary(max) |
| partno | integer | PartNo | int |

В PostgreSQL длину пользовательского типа имени показывает
`format_type(pg_attribute.atttypid, pg_attribute.atttypmod)`.
В SQL Server максимальная длина `-1` в каталоге соответствует `max`.
Для проверки порядка ключей используются `pg_indexes.indexdef` и
`sys.index_columns.key_ordinal`.

## Как читать агрегаты

[rows.tsv](rows.tsv) содержит по строке на сборку, вход, фазу и таблицу.
`pg_rc` и `ms_rc` — коды нативного процесса (Windows 0xffffffff
записан как −1). Прочерк означает отсутствие снимка этой фазы,
ноль — измеренное нулевое значение. `shared_keys` — число общих пар
имя/часть. Вычитание его из `pg_rows` или `ms_rows` даёт число ключей
только на соответствующей стороне. `equal_sha256` считает совпавшие
тела среди общих ключей. Последняя колонка группирует остальные по
известным служебным именам и классу `other`. `unequal_length` относится
к фактической длине BinaryData, `unequal_datasize` — к колонке DataSize.

| Вход | Идентификация |
|---|---|
| tiny-xml-2.21 | `tests/fixtures/file-infobase/tiny-source`, 4 файла |
| empty-xml-2.20 | `tests/fixtures/file-infobase/empty-xml-8.3.27` |
| bsp-xml-2.21 | БСП 3.1.11.309, режим совместимости 8.3.24, 9 156 файлов |
| bsp-xml-2.20 | БСП 3.1.11.309, режим совместимости 8.3.24, выгрузка 8.3.27.2214 |
| bsp-cf | БСП 3.1.11.309, поставочный CF, 67 167 823 байта, SHA-256 `4ded13b6b6b5c74f11c544e6be442cbea6f49eb8dede3424841b4bd6af4b4448` |

Для `bsp-cf` на шаге загрузки выполнить
`ibcmd infobase config load <common> <file.cf>`. Для прогона
`bsp-xml-2.20` использованы базы после отказа 8.3 на XML 2.21:
повторный снимок перед импортом подтвердил пустые `config` и
`configsave`. В этой серии фаза `create` обозначает этот исходный снимок.

Исходный [протокол создания MSSQL-баз](../../../../../docs/apply/native-infobase-create.md)
содержит DDL, порядок инициализации и повторные запуски с различными
служебными значениями для 8.3.27.2214 и 8.5.1.1150. В
[протоколе ERP УХ](../parity-8327-20260919.md) измеряли выгрузку
конфигурации 3.3.3.3 на MSSQL с 8.3.27.2214. Для ERP УХ остаётся
получить парные снимки на PostgreSQL и MSSQL с обеими указанными здесь
сборками. У проверенных локальных деревьев ERP WE и «Управление холдингом»
другие имена конфигурации. Их результаты в матрицу ERP УХ не включены.

24.11.2026 в [карточке релиза ERP УХ 3.3.3.3](https://releases.1c.ru/version_files?nick=ERP_UH33&ver=3.3.3.3)
проверена позиция «Полный дистрибутив» от 19.06.2026. Поставщик указывает
архив `ERP_UH_3_3_3_3_setup1c.zip`, 3 462 262 855 байт и минимальную
платформу 8.3.27.1989. Карточка релиза и начатая загрузка сами по себе не подтверждают измерение строк. Совпадения номера релиза недостаточно для отождествления с деревом исторического замера на 140 709 файлов.

## Что показал импорт XML

В состоянии после импорта БСП 3.1.11.309 формата 2.21 на 8.5.1.1529
обе команды вернули 0. В PG оказалось 7 213 физических строк стадии,
в MSSQL — 6 954. Все 6 954 ключа MSSQL нашлись в PG. Для 5 609 общих
ключей совпала SHA-256 хранимых байтов. Среди остальных 1 345 ключей
один принадлежал `versions`. На обеих сторонах по три физических строки
имели ненулевой номер части. У штатного применения этой MSSQL-базы
проверка метаданных завершилась ошибкой целостности, активный `Config`
остался пуст.

На 8.3.27.2342 обе СУБД отказали при чтении XML 2.21 (неизвестная
версия формата). После повторного импорта БСП из XML 2.20 в PG появились
7 213 строк `configsave`, включая `root`, `version`, `versions` и `deleted`.
MSSQL отклонил ссылку на предопределённый элемент и сохранил семь строк,
ни один из этих семи ключей не совпал с ключами успешной стадии PG.
