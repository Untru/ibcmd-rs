# Platform 8.5.1.1150 BSP baseline

## Isolation

- Source: cluster/RAS `localhost:3541/3545`, infobase `bsp`, UUID
  `44c05fe0-b4a4-4746-acda-0cd3b4b4da38`.
- Source operation: `BACKUP DATABASE ... COPY_ONLY, COMPRESSION, CHECKSUM`;
  no source configuration, registration, session, job, or worker mutation.
- Clone database: `ibcmd_rs_85_bsp_lab_20260830`.
- A separate user-mode cluster/RAS was tested at `localhost:4541/4545`, UUID
  `b6925f6e-5cd7-44ff-a377-8005d0f15db4`, but could not obtain a server
  licence. Its exact processes were stopped before continuing.
- The clone was then registered temporarily in the licensed 8.5 cluster as
  UUID `4836916a-9b0c-4438-9969-5174b9476219`, with scheduled jobs denied and
  reserved working processes enabled. The source registration was unchanged.
- Scheduled jobs were denied at registration. A scoped random SQL login exists
  only for the clone and is retained in memory until teardown.
- Pristine clone backup passed `RESTORE VERIFYONLY ... CHECKSUM`.

## Native/custom read evidence

Native `ibcmd config export` completed in 30,638 ms and produced 12,336 source
files. The current custom full export stopped after 9,524 ms on an independently
known managed-form conditional-appearance coverage rejection. Before stopping
it produced 5,035 comparable files:

- 3,184 byte-identical;
- 1,851 different, all configuration/metadata/form/template XML or MXL;
- 1,220 overlapping BSL modules were byte-identical;
- no overlapping BSL module differed.

This proves the module body codec on the observed cohort, but not full XML/form
parity. Native XML 2.21 does not select the platform storage profile.

Native extension inventory returned three extensions. The custom registry
decoder returned the same names, order, versions, active flags, purposes,
scopes, distribution flags, and active CAS roots. Its report incorrectly labels
the result `mssql-extensions-info-8.3.27`. That legacy value remains unchanged
in schema v1 for consumer compatibility; a platform-neutral codec identifier
requires a future report schema bump.

## SQL and native mutation oracle

`Config`, `ConfigSave`, `Params`, `ConfigCAS`, and `ConfigCASSave` retain the
seven-column layout used by 8.3.27. The observed extension registry envelope is
readable by the current decoder; 8.5 BSP adds configuration-specific separation
columns to registry/restruct tables, which direct activation must leave intact.

On the clone only, native `ibcmd` removed support, imported one managed-form
module, and applied it dynamically:

- support disable: 4,959 ms;
- partial module import: 5,621 ms;
- staged `ConfigSave`: 6 rows;
- native dynamic apply: 9,372 ms;
- post-apply `ConfigSave`: 0 rows.

The activation snapshot shows the same service grammar as the 8.3.27 oracle:
ordinary `Config` gained `DynamicallyUpdated`, `_dynupdate_<generation>` aliases
and the changed descriptor/body cohort; `Params` gained its dynamic marker; the
new generation was `32ba7efa474ee74d9c4708b391b0801600000000`.

The raw laboratory artifacts were retained through comparison and then removed
during teardown; this scrubbed evidence summary is the committed record.

## Exact profile gate and live result

The write entry points now require a closed `--platform-profile` and verify it
against `rac agent version`, the target database's infobase registration on the
same RAS endpoint, and a read-only live SQL fingerprint before reading source
or staging data. The observed identity was:

- RAC agent build: `8.5.1.1150`;
- `IBVersion=7`, `PlatformVersionReq=80313`;
- exact ordered columns, SQL types, lengths, precision, scale, nullability and
  ordinals for `Config`, `ConfigSave`, `Params`, `ConfigCAS` and
  `ConfigCASSave`;
- canonical schema SHA-256:
  `49ab07a8ddb8c87ae1bdc47b1b5342dc2341dbf99cc777ede57ad8ec539bc0a3`.

A final read-only CLI preflight against the source `bsp` registration used its
exact cluster/infobase UUIDs and `Administrator` with an empty password. RAC
returned `dbms=MSSQLServer`, `db-server=localhost`, `db-name=bsp`; the live SQL
probe passed and the command then stopped at the intentional 8.5 write gate,
before source or staging access.

The first custom managed-form-module activation completed successfully at the
SQL level in 37,325 ms: bounded active export 34,435 ms, classification 18 ms,
staging 1,339 ms and activation 1,230 ms. A second run took 40,088 ms, of which
36,750 ms was active export. This isolates the current latency problem: source
compilation and SQL publication are already about 2.6-2.8 seconds, while the
three-process active-form fetch dominates wall time.

The SQL-table shape was compatible, but the activation semantics were not:

- the already-open observer stayed on `native-85-client-v1|native-85-server-v1`;
- a native partial import plus dynamic apply took 6,605 + 6,774 ms and a fresh
  session observed `native-85-client-v3|native-85-server-v3`;
- after the custom v4 activation, a fresh session still observed native v3.

The native diff explains the mismatch. In addition to
`Config/Params.DynamicallyUpdated` and `_dynupdate_` aliases, native 8.5 apply
changed two generation-selection `.ui` rows in `Params`
(`789702c6-d272-4008-9e55-db6f10687ae0.ui` and
`97f2c291-1aa3-4d96-8266-82a958c7dfaf.ui`). The current custom protocol does
not rewrite those rows. Therefore 8.5 writes remain fail-closed even though the
schema fingerprint matches; treating table compatibility as activation support
would be unsafe.

Reserved processes did not yield a fully isolated client worker in the shared
cluster: clone client connections also appeared on the process serving the
source and other infobases. Worker mode correctly rejected the handoff before
SQL mutation (`observed 3`) and no shared process was stopped. Turning off one
separately proven clone-only reserved process did not change the open session's
generation. Same-session 8.5 validation remains pending a licensed isolated
worker or an evidenced `.ui` generation-selection codec.

The laboratory clone, its SQL login, cluster registration, database files,
backups, staging files and temporary native/custom export trees were removed
during teardown after the measurements above were recorded. Final checks found
the source client process alive, the `bsp` database `ONLINE/MULTI_USER`, the
source registration present, and no clone database, login, registration or
database files remaining.
