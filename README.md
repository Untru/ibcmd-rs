# ibcmd-rs

Быстрая замена штатного `ibcmd` для выгрузки, загрузки и применения
конфигурации 1С между XML-файлами и базой на Microsoft SQL Server. Утилиту
можно положить вместо `ibcmd.exe`: у команд `infobase config export`,
`infobase config import`, `infobase config apply` и `infobase config save` тот
же синтаксис, тот же вывод и те же коды возврата, а на выходе тот же XML, что
у штатного `ibcmd`.
Утилиты SQL Server (`sqlcmd`, `bcp`) не нужны.

> **Внимание.** Проект в стадии активной доработки. Рабочим для повседневного
> использования он станет только к версии 1.0; до тех пор это эксперимент для
> исследований и обучения. Команды, которые пишут в базу, запускайте только на
> копиях баз. Что сделано и что впереди — в
> [майлстоунах](https://github.com/Untru/ibcmd-rs/milestones).

**Доступность `cf bootstrap --base-free`.** Этот режим есть в сборке из
исходников `master` после [PR #422](https://github.com/Untru/ibcmd-rs/pull/422).
В опубликованных архивах [v0.4.0](https://github.com/Untru/ibcmd-rs/releases/tag/v0.4.0)
ключа `--base-free` у `cf bootstrap` нет. Для этой команды ниже нужна сборка
соответствующего checkout исходников; скачанный v0.4.0 её не поддерживает.
Без этого ключа `cf bootstrap` использует прежний компилятор с ограниченным
набором поддерживаемых деревьев XML. Он сохранён для этих деревьев; при
отказе нового полного дерева см. [пояснение в справочнике](docs/COMMANDS.md#файлы-cf-и-конвертация).

## Что дальше

Версия 1.0 — это полная замена штатного `ibcmd` для конфигурации. Путь к ней

- **0.4** — своё применение конфигурации (`config apply`) без платформы;

- **0.6** — файлы CF: выгрузка базы в CF, загрузка CF в базу, CF ↔ XML;

  и загрузка;

- **0.10** — файловые базы;
- **0.11** — расширение для VS Code.

Ход работ по каждой версии — задачи в её
[майлстоуне](https://github.com/Untru/ibcmd-rs/milestones), с доказательствами

## Что нужно

- Windows x64.
- Microsoft SQL Server (вход Windows или логин SQL Server).
- Штатная платформа 1С той же версии, что и база, нужна только для создания
  пустой базы (`infobase create`) и для того, что применение отправляет на
  штатный `config apply` (см. [Применение конфигурации](#применение-конфигурации)).
  Выгрузке, загрузке и обычному применению она не нужна.

Скачайте архив `ibcmd-rs-<версия>-x86_64-pc-windows-msvc.zip` со страницы
[Releases](https://github.com/Untru/ibcmd-rs/releases) и распакуйте его.

## Как подменить ibcmd

Скопируйте `ibcmd-rs.exe` под именем `ibcmd.exe` в отдельную папку и
запускайте выгрузку и загрузку из неё, как штатный `ibcmd`:

```
ibcmd infobase config export --dbms=MSSQLServer --db-server=localhost ^
  --db-name=MyBase C:\export\MyBase

ibcmd infobase config import --dbms=MSSQLServer --db-server=localhost ^
  --db-name=MyBase C:\export\MyBase
```

Без `--db-user` утилита входит в SQL Server от имени пользователя Windows.
Для логина SQL Server добавьте `--db-user` и `--db-pwd`, как у штатного
`ibcmd`:

```
ibcmd infobase config export --dbms=MSSQLServer --db-server=sql01 ^
  --db-name=MyBase --db-user=sa --db-pwd=Secret C:\export\MyBase
```

Чтобы пароль не попадал в историю команд, передайте его через `-W` (из
стандартного ввода) или переменную окружения `IBCMD_DB_PSW`.

Штатный `ibcmd.exe` платформы не удаляйте: `infobase create` и то, что
применение отправляет на штатный `config apply`, выполняет он. Если положить
утилиту в папку платформы (`...\1cv8\8.3.27.2214\bin\`), версию платформы
она возьмёт из имени папки.

Вывод такой же, как у штатного:

```
[INFO] Экспорт конфигурации в XML...
[INFO] Экспорт конфигурации в XML успешно завершен
```

**Параметры.** Принимаются все общие параметры штатного `ibcmd` в обоих
написаниях (`--db-server` и `--database-server`, `--x=значение` и
`--x значение`):
- `--dbms=MSSQLServer`, `--db-server`, `--db-name`, `--db-user`, `--db-pwd`;
- `-W` — пароль СУБД из стандартного ввода;
- `-c/--config` — файл настроек штатного `ibcmd`, из его раздела `database:`
  берутся сервер, база, логин и пароль;
- `--data`, `--temp`, `--user`, `--password`;
- у выгрузки `--threads`; `--force` принимается, но непустой каталог, как и у
  штатного, не перезаписывается;
- у выгрузки `--base=<ConfigDumpInfo.xml>` (выгрузить только изменённые с той
  выгрузки объекты) и `--sync` (удалить из каталога то, чего нет в полной
  выгрузке): обновление выгрузки по версиям строк конфигурации, см.
  [docs/COMMANDS.md](docs/COMMANDS.md#инкрементальная-выгрузка---base---sync).

Свои параметры утилиты:
- `--platform` — версия платформы, см. ниже;
- `--report <файл>` — подробный отчёт в JSON;
- `--sqlcmd <путь>` — работать через `sqlcmd` и `bcp`, как версия 0.2 (у
  применения не поддерживается);
- у применения ещё `--exclusivity`, `--recovery-backup` и `--i-have-a-backup`,
  см. [Применение конфигурации](#применение-конфигурации).

**Загрузка в пустую базу.** Отдельного ключа не нужно: если в таблице Config
базы нет строк этой конфигурации (база только что создана `ibcmd infobase
create`), конфигурация собирается целиком из XML.

**Чего пока нет.** Остальные команды и режимы штатного `ibcmd` (`infobase
create`, `config load`, расширения, `server` и другие), файловые базы
(`--db-path`) и СУБД кроме MSSQLServer отвечают сообщением «не
поддерживается в этой версии ibcmd-rs» с кодом 1. Штатный `ibcmd` вместо них
не запускается.

**Коды возврата:**

| Код | Когда |
|---|---|
| 0 | успех |
| 2 | ошибка в командной строке: неизвестный параметр, нет значения, неполная команда (как у штатного) |
| −1 | операция завершилась с ошибкой (как у штатного; в bash видно как 255) |
| 1 | команда или параметр не поддерживаются в этой версии ibcmd-rs; у применения ещё «требуется штатный config apply» и отказ без резервной копии ([коды применения](#коды-возврата-применения)) |

## Применение конфигурации

```
ibcmd infobase config apply --dbms=MSSQLServer --db-server=localhost ^
  --db-name=MyBase --force --dynamic=disable
```

Переносит загруженную конфигурацию (таблица ConfigSave) в действующую
(Config) монопольно, одной транзакцией: при сбое база остаётся как была.
Платформа не нужна. Синтаксис, вывод и коды возврата те же, что у штатной
команды; все параметры — в
[docs/COMMANDS.md](docs/COMMANDS.md#применение-конфигурации). Что можно
проверить заранее, ничего не применяя: `ibcmd-rs mssql-apply-check --database
MyBase`.

### Что применяется само

**Без резервной копии** - всё, что не меняет таблицы базы:

- модули, формы, макеты, картинки и справка любых объектов;
- новые формы и макеты существующих объектов (только 8.3.27);
- свойства описаний, которые не влияют на хранение: синоним, комментарий,
  представления, формы по умолчанию и подобные (полный список - в
  [docs/apply/restructuring-check.md](docs/apply/restructuring-check.md));
- удаление формы, макета или модуля (строка `deleted`).

**С согласием на резервную копию** - реструктуризация таблиц (S1) на
справочниках и документах, в той же транзакции:

- добавить реквизит (любого простого типа: строка, число, дата, булево и
  другие);
- удалить реквизит;
- увеличить длину строки переменной длины;
- включить или выключить индексирование реквизита, в том числе с
  дополнительным упорядочиванием;
- добавить табличную часть; добавить реквизит существующей табличной части.
- добавить справочник или документ.

Каждый случай проверен на двойнике против штатного применения: данные
перестроенных таблиц и строки Config совпадают, штатный
`config apply` после нашего отвечает «не требуется», штатная выгрузка
совпадает. Нужен доступ к базе без других сеансов; для нескольких изменений в
одной загрузке отказ по любому из них останавливает всё, ничего не пишется.
Размер перестраиваемых таблиц ограничен: по умолчанию 10 миллионов строк
и 2 ГиБ расчётной записи в журнал по всей загрузке. Выше предела — отказ
с отсылкой к штатному `config apply`; настройки и измерения — в
[docs/COMMANDS.md](docs/COMMANDS.md#предел-собственной-реструктуризации-s1-j-406).

### Резервная копия как согласие

Реструктуризация удаляет старые таблицы объекта внутри транзакции, а
артефакт восстановления, который применение оставляет рядом, хранит строки
Config и кэши, но не таблицы. Поэтому путь назад - резервная копия SQL
Server. Её нужно назвать, и это же согласие на реструктуризацию:

- `--recovery-backup=<файл>` (рекомендуется): перед транзакцией применение
  само делает `BACKUP DATABASE ... WITH COPY_ONLY, COMPRESSION` в этот файл
  (путь, куда может писать служба SQL Server; файл не должен существовать) и
  называет его в отчёте;
- `--i-have-a-backup`: вы подтверждаете, что копия у вас есть; это записывается
  в отчёте.

Без одного из них загрузка, которой нужна реструктуризация из списка выше, не
применяется: сообщение по-русски называет оба параметра, код 1, база не
тронута. Для загрузки без реструктуризации ни тот, ни другой не нужен. У
штатного `ibcmd` резервной копии нет, здесь она обязательна.

### Что остаётся за штатным `config apply`

Ответ `требуется штатный config apply: <причины>`, код 1, ничего не записано.
В причинах названы строки и правило. Это:

- любая другая реструктуризация: другие свойства объектов (длина и тип кода,
  иерархия, история данных и подобные), реквизиты ссылочного и составного
  типа, смена типа, регистры, планы, общие реквизиты, предопределённые
  элементы, значения перечислений, удаление объектов с таблицами;
- объект, который заимствует расширение (в причине названо расширение);
- загрузка, удаление в которой проверка не может безопасно разобрать;
  загрузка штатного `ibcmd`, которую проверка не может разобрать;
- база с недоделанной операцией: в этом случае ответ `требуется штатный config
  repair`;
- динамическое обновление (`--dynamic=force`), расширения (`--extension`),
  серверный режим (`--pid`, `--remote`): «не поддерживается», код 1.

Изменение дерева → `ibcmd infobase config import` → `ibcmd infobase config apply`
работает целиком без платформы для перечисленных операций S1. Загрузка
переносит изменённые описания, новые объекты и удаления в ConfigSave, сохраняя
нетронутые строки базы. Перед записью защита сравнивает полученную
конфигурацию с деревом и отменяет загрузку при любом расхождении.
Удаление отдельного модуля или картинки из дерева пока отклоняется;
удаление формы или макета переносится.

### Платформа 8.5 и ERP УХ

- **8.5:** применение без реструктуризации работает и проверено на БСП 8.5
  (Config совпадает со штатным, штатная выгрузка совпадает, новый сеанс в
  кластере видит изменение); новые формы и макеты на 8.5 отклоняются с
  ответом «требуется штатный config apply». Реструктуризация (S1) проверена на
  БСП 8.5 так же, как на 8.3.27: добавление и удаление реквизитов, увеличение
  длины строк, переключение индексирования; данные перестроенных таблиц, Config
  и DBSchema совпадают со штатным применением, штатная выгрузка совпадает
  (12 337 файлов), штатный `config apply` после нашего отвечает «не требуется».
- **ERP УХ 8.3.27:** применение без реструктуризации проверено (300 модулей,
  Config совпадает строка в строку). Реструктуризация (S1) проверена на двух
  случаях: удаление и добавление реквизитов, увеличение длины строк (строки
  Config, таблицы, колонки и индексы, записи DBSchema и DBNames совпадают со
  штатным применением, штатная выгрузка совпадает — 140 709 файлов, штатный `config
  apply` после нашего отвечает «не требуется»). Резервная копия УХ содержит
  только конфигурацию, таблицы в ней пусты: проверена работа со структурой
  большой конфигурации, а не копирование данных таблиц; на больших таблицах и
  на УХ 8.5 реструктуризация не проверялась. Порядок таблиц DBSchema отдельно
  подтверждён после исправления на свежей копии УХ: все шесть перестроенных
  таблиц занимают штатные позиции, остальные сохраняют порядок;
  [свидетельства](docs/apply/evidence/restructuring/s1-mix-release-20261001.txt).

### Коды возврата применения

| Код | Когда |
|---|---|
| 0 | применено; применять нечего («не требуется») |
| 1 | `требуется штатный config apply` (или `config repair`); реструктуризация без `--recovery-backup` и `--i-have-a-backup`; параметр или платформа, которые не поддерживаются; к базе подключены сеансы и указан `--session-terminate=force` или `prompt` |
| 2 | ошибка в командной строке, слова штатного `ibcmd` |
| −1 | операция не выполнена: к базе подключены другие сеансы, у логина нет права `VIEW SERVER STATE`, файл резервной копии уже есть, ошибка SQL Server; база не тронута |

### Где утилита строже штатной

- **Сеансы.** Штатный `ibcmd`, запущенный на базе, других сеансов не видит и
  применяет; в режиме `--pid`/`--remote` отменяет с предупреждением и кодом
  0. Здесь при подключённых сеансах отказ с их списком и кодом −1 (скрипт не
  примет «не применено» за успех). Без права `VIEW SERVER STATE` укажите
  `--exclusivity=assumed`, если знаете, что в базе никого нет.
- **Реструктуризация.** Штатный `ibcmd` выполняет любую и резервной копии не
  просит; здесь только та, что в списке, и с резервной копией.
- **Загрузка штатного `ibcmd`** на это применение не рассчитана: она
  принимается, только если проверка разобрала каждую её строку (различия
  формата записи, которые делает штатная загрузка, проверка доказывает как
  безвредные), иначе отказ.
- **Параметры** `--dynamic=force`, `--extension`, `--sqlcmd`, `--pid`,
  `--remote` не поддерживаются.
- Мягче штатной в одном: проверку корректности метаданных (`Проверка
  корректности метаданных...`) применение не выполняет; загрузка проверила
  свой вход при записи в ConfigSave.

Подробности, измерения штатной команды и сообщения:
[docs/apply/dropin-apply.md](docs/apply/dropin-apply.md); что применение не
пишет и чем отличается от штатного: [docs/apply/own-apply.md](docs/apply/own-apply.md).

## Как указать платформу

**Платформа базы** задаётся параметром `--platform`: выпуск (`8.3.27`,
`8.5.1`) или точная сборка (`8.3.27.2214`, `8.5.1.1150`). Она определяет
формат XML:

| Платформа | Формат XML | Как узнать по выгрузке |
|---|---|---|
| `8.3.27` | `2.20` | `version="2.20"` в первой строке `Configuration.xml` |
| `8.5.1` | `2.21` | `version="2.21"` там же |

При выгрузке это формат, в котором будет записан XML. При загрузке — формат
загружаемых файлов: утилита проверяет, что он совпадает. Неизвестная версия
отклоняется со списком известных.

Без `--platform` платформа берётся по порядку:

1. запись `[[database]]` для этой базы в `ibcmd-rs.toml`;
2. переменная `IBCMD_RS_PLATFORM`;
3. `platform` в `ibcmd-rs.toml`;
4. каталог утилиты `...\1cv8\<версия>\bin`; при загрузке — `version` в
   `Configuration.xml`; при выгрузке режим совместимости 8.5 означает 8.5.1;
5. иначе 8.3.27 с предупреждением.

Файлы `ibcmd-rs.toml` читаются рядом с утилитой, в `%APPDATA%\ibcmd-rs\` и в
текущей папке (более поздний побеждает) или один файл из `IBCMD_RS_CONFIG`:

```toml
platform = "8.3.27.2214"        # для баз, которых нет в списке
db-server = "sql01"

[[database]]
server = "sql02"                # необязательно: без него — любой сервер
name = "bsp_*"                  # имя базы или маска со *
platform = "8.5.1.1150"
```

`ibcmd-rs settings show --db-server sql02 --db-name bsp_test` показывает
итоговые значения и откуда взято каждое.

**Режим совместимости конфигурации** указывать не нужно, он берётся из
`Configuration.xml`. Например, ERP УХ для 8.5 выгружается в формате `2.21`,
но с режимом совместимости 8.3.27; сама база не отличает 8.3.27 от 8.5,
поэтому такую базу привязывают к 8.5.1 записью `[[database]]`.

## Подключение к SQL Server

Утилита подключается к SQL Server сама, по протоколу TDS; `sqlcmd` и `bcp`
не нужны.

- **Сервер:** `localhost`, `сервер\экземпляр` (или `сервер/экземпляр`, как
  пишет штатный `ibcmd`), `сервер,порт`. Только TCP; для `np:` и `lpc:`
  укажите `--sqlcmd`.
- **Вход:** по умолчанию Windows. Для логина SQL Server укажите `--db-user`, а
  пароль передайте `--db-pwd`, через `-W` или в переменной `IBCMD_DB_PSW`.
- **Шифрование** включено; сертификат сервера принимается без проверки, как у
  `sqlcmd -C`.
- **Соединения:** выгрузка читает базу по нескольким соединениям, их число
  задаёт `IBCMD_RS_SQL_CONNECTIONS` (по умолчанию 4).

Сервер и логин без параметров берутся из переменных `IBCMD_RS_DB_SERVER` и
`IBCMD_RS_DB_USER`, из `db-server` и `db-user` в `ibcmd-rs.toml` или из
раздела `database:` файла `--config`. Пароль в `ibcmd-rs.toml` не хранится.

## Команды самой утилиты

Кроме синтаксиса `ibcmd`, у утилиты есть свои команды с подробными
параметрами (`ibcmd-rs --help`):

```
ibcmd-rs mssql-dump-config --database MyBase --extract-metadata-xml ^
  --extract-module-text --no-binary-rows --platform 8.3.27 -o C:\export\MyBase

ibcmd-rs mssql-stage-source-objects --database MyBase ^
  --source-root C:\export\MyBase --platform 8.3.27 ^
  --replace-config-save --allow-non-lab [--base-free]

ibcmd-rs source-diff -o diff.json C:\export\native C:\export\ours

ibcmd-rs cf export C:\cf\MyConf.cf C:\src\MyConf --index
ibcmd-rs cf load C:\src\MyConf C:\cf\MyConf-new.cf --base C:\cf\MyConf.cf
```

`cf export` выгружает файл `.cf`, `.cfe`, `.epf` или `.erf` в XML без базы
(штатному `ibcmd` для этого нужна база). `cf load` собирает новый файл с
правками дерева, выгружает его обратно и сверяет с деревом; при расхождении
файл не пишется. Подробнее — в
[docs/COMMANDS.md](docs/COMMANDS.md#cf-export-и-cf-load--файлы-cf-cfe-epf-erf--xml-без-базы).

У них сервер задаёт `--server`, логин — `--sql-user`, пароль — `--sql-pwd` или
`IBCMD_DB_PSW`. `mssql-dump-config --rows-dir` выгружает XML без сервера, из
сохранённых строк таблицы Config. В `diff.json` будут итоги (`unchanged`,
`different`, `left_only`, `right_only`) и список расхождений по файлам.

## Ограничения

- Только Microsoft SQL Server.
- Создание базы (`infobase create`) выполняет штатная платформа 1С. Из
  реструктуризации утилита делает только перечисленное в разделе
  [Применение конфигурации](#применение-конфигурации), остальное отправляет
  на штатный `config apply`; реструктуризация проверена на БСП 8.3.27 и 8.5 и на ERP УХ 8.3.27 (на пустых таблицах).
- Проверено на БСП и ERP УХ, платформы 8.3.27.2214 и 8.5.1.1150. Другие
  конфигурации и версии платформы могут дать расхождения.
- `ibcmd -v` печатает версию утилиты, а не платформы.
- `cf load` пока проверен на правках модулей, описаний объектов и форм;
  большой файл (ERP УХ) собирается 5–15 минут и требует до 20 ГБ памяти.
- Остальные команды (`ibcmd-rs --help`: расширения, CF, аудит) —
  исследовательские и проверены меньше.
