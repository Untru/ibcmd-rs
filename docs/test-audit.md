# Аудит тестов: дубли и прогон сводной конфигурации покрытия (#674)

Замер 2026-11-01 на master `8ee67bc0`, Linux x86-64, 4 ядра, отладочная
сборка с `CARGO_PROFILE_DEV_DEBUG=line-tables-only`, как в офлайн-матрице.
Здесь итог, порядок замера и план. Сырые данные (время каждого теста,
покрытие каждого кластера и каждого теста) в репозиторий не входят: их
пересобирает порядок замера ниже.

## Итог

Избыточность мала.

- **Время.** Тесты, все строки которых покрывает остальной набор и которые
  не проверяют отказ или текст ошибки, занимают 86 с процессорного времени из
  833 с (10,4 %). Половина из них приходится на один дубль шага CI
  (`coverage_checkout`, 41 с). Удаление кода `mssql_dump/tests.rs` и
  `form_body/tests.rs` сэкономило бы не больше 22 с (2,7 %).
- **Код.** По тому же критерию лишними выглядят не больше 43 тыс. строк
  тестового кода из 254 тыс. (17 %). Это верхняя граница: строковое покрытие
  необходимо, но не достаточно. Из 7 мутаций, которые набор `ibcmd-dump`
  ловит сейчас, одну после такого удаления не поймал бы ни один
  оставшийся тест (M8 ниже).
- **Сводная конфигурация** не заменяет модульные тесты. Прогон корпуса
  через писатели ibcmd-rs достигает 2 880 строк, которых не достигает ничто
  другое. Но во всём наборе лишними из-за него становятся лишь
  4 144 строки уникального покрытия, и почти все они размазаны по
  кластерам, у которых остаются и свои уникальные строки. По строкам он
  поглощает два теста, и это кандидаты, а не доказательство.
- **Время уходит не на дубли.** Бинарник `integration` (124–148 с из 375 с
  всего прогона) упирается в процессор. Больше всего берут наборы
  `coverage_*` (198 с процессора, из них `coverage_corpus` — 112 с в
  одном потоке) и `edt_conversion_cli` (54 с).

Поэтому по правилу аудита удаления не делаются. PR 1 добавляет офлайн-тест
сводной конфигурации и этот документ. Дальше предлагаются три изменения
без удаления тестов и одно удаление дубля по решению мейнтейнера (раздел
«План»).

## Покрытие

`cargo llvm-cov` 0.9.1, инструментированная отладочная сборка, вендорный
morph1c не инструментируется. Строки тестов (`tests/`, `*tests.rs`,
`#[cfg(test)]`) из подсчёта исключены.

- Инструментировано 312 881 строка рабочего кода, весь набор покрывает
  250 404 (80,0 %).
- Набор разбит на 278 кластеров: интеграционный набор корня, модуль
  крейта, отдельный бинарник `tests/*.rs`. Большие файлы разбиты по теме:
  `mssql_dump/tests.rs` на 10 частей, `form_body/tests.rs` на 3.
  Каждый кластер запускался со своим профилем.
- **Уникальные строки кластера** — строки, которые не покрывает ни один
  другой кластер. Столько строк теряет набор без этого кластера.

Без `ibcmd-edt` у 39 кластеров уникальных строк нет. Это 160 тестов,
4 443 строки и 117 с.
Но по строкам удалять их нельзя:

- `root/lib/cli` (61 тест) сверяет разбор аргументов и текст `--help`;
- `descriptor_read`, `platform_oracle_boundary`, `extension_adopted*`
  проверяют отказы;
- `scratch_*` и `every_suite_file_is_built` проверяют сам тестовый харнесс.

Тесты `ibcmd-edt/tests/*.rs` проверяют вендорный morph1c, который не
инструментирован. Поэтому нулевое покрытие у них ложное. По `AGENTS.md`
каждая одобренная адаптация morph1c должна иметь положительный тест и
тест на отказ.

жадный алгоритм выбрал наименьший набор тестов, который сохраняет все
строки, не покрытые остальным набором.

### Мутации

Восемь мутаций в коде, который покрывают тесты из «лишних» `ibcmd-dump`.
Каждая выбрана так, что эти строки покрывают ещё один-два «оставляемых»
теста. После каждой мутации запускались все тесты `ibcmd-dump`.

| Мутация | Падает тестов | Из них «лишних» | Из «оставляемых» |
|---|---:|---:|---:|
| M1 `refs.rs`: литерал `.Template.` → `.Templates.` | 9 | 5 | 4 |
| M2 `upgrade.rs`: условие дописывания членов обращено | 2 | 1 | 1 |
| M3 `selected.rs`: `template_refs` не запрашивается | 6 | 5 | 1 |
| M4 `role_rights.rs`: фильтр административных прав обращён | 7 | 5 | 2 |
| M5 `form_body_entry.rs`: форма 8.5 читается без понижения | 7 | 6 | 1 |
| M6 `ibcmd-form-body/dcs.rs`: отбор настроек СКД теряется | 0 | 0 | 0 |
| M7 `ibcmd-moxel`: `<templateMode>` не пишется | 3 | 2 | 1 |
| M8 `ibcmd-moxel`: `<empty>true</empty>` пустой строки не пишется | 7 | 7 | 0 |

- M8 после жадного удаления не поймал бы никто. Значит, у «лишних» по
  строкам тестов бывают уникальные проверки значений: тесты
  `formats_moxel_*` проверяют вывод частичными `contains` на разных
  фикстурах.
- M6 не ловит ни один тест `ibcmd-dump`. Строки отбора исполняются, но его
  результат не сверяется. Это пробел, а не избыточность.

Итог: верхняя граница в 17 % кода для удаления непригодна. Каждый кластер
до удаления нужно проверить мутациями, как требует #674. Ожидаемый
выигрыш от этого заметно меньше 15 %.

## Офлайн-тест сводной конфигурации (PR 1)

`tests/coverage_round_trip.rs` прогоняет нативный XML наборов корпуса через
писатели ibcmd-rs и сравнивает результат с тем же XML вариант за вариантом.
Сравнение побайтное, без `ConfigDumpInfo.xml`, как у `coverage_corpus`.
Маршруты:

- XML → CF → XML: `cf bootstrap`, затем `cf export`;
- XML → файловая база → XML: `infobase config import --no-verify` в
  пустую базу платформы, затем `infobase config export`.

**Порядок прогона.**
- Сначала идут наборы «всё в одном»: `combined` каждой сборки, а для
  расширений и внешних файлов — наборы `combined*`.
- Сводные 8.3.27.2214, 8.5.1.1150 и 8.5.1.1529 оба маршрута сейчас
  отвергают целиком: компиляция без базы называет 44, 57 и 164 файла.
  Отвергнутый вывод не сравнивается.
- Поэтому для отвергнутой сводной маршрут XML → CF → XML дальше идёт по
  классовым наборам, из которых она собрана. Набор, который входит в
  записанную сводную (классы 8.3.27.2342), повторно не прогоняется.
- Маршрут через файловую базу классовые наборы не прогоняет: импорт
  компилирует те же строки тем же компилятором без базы. Его запасной
  прогон добавил бы 7 строк под сравнением за +67 с процессора.
- Когда сводная начнёт записываться, её классовые наборы выпадут из прогона
  сами.

Замер по всем 242 наборам. Уникальные строки — строки, которых больше
ничто в наборе тестов не достигает; «со сравнением» — те из них, что
достигнуты прогонами, чей вывод сравнивается с эталоном.

| Подмножество | Прогонов | Время, с | Уникальных строк | Со сравнением |
|---|---:|---:|---:|---:|
| все наборы, оба маршрута | 469 | 312,4 | 2 880 | — |
| только наборы «всё в одном» | 15 | 34,9 | 2 835 | 969 |
| «всё в одном» и классы отвергнутых сводных, оба маршрута | 307 | 149,1 | 2 844 | 1 995 |
| PR 1: то же, классы только через CF | 161 | 81,7 | 2 837 | 1 988 |

На 4 потоках набор идёт 36 с:

| Маршрут | Прогонов | Отвергнуто целиком | Сравнено вариантов | Равно | Известных расхождений |
|---|---:|---:|---:|---:|---:|
| XML → CF → XML | 157 | 57 | 2 013 | 1 955 | 58 |
| XML → файловая база → XML | 4 | 3 | 337 | 309 | 28 |

Это дороже первого замысла (15 прогонов, 14 с). Зато вывод писателей
сравнивается вдвое шире. Бинарник `integration` целиком (`cargo test`,
машина свободна): master — 148 с, с этим PR — 189 с (+41 с). Бинарник
упирается в процессор, а не в самую долгую проверку.

**Ожидания.** `tests/fixtures/coverage/round-trip.json` перечисляет
известные расхождения:
- отвергнутый набор — файлы, которые называет писатель, с его причиной;
- вариант, который не вернулся, — как именно: первый отличающийся или
  отсутствующий файл, либо первый отвергнутый файл.

649 записей несут номер issue (#545, #546, #548–#551, #594, #595,
#598–#602, #604–#610, #612–#618, #621–#630, #632). 184 записи помечены
`no issue yet`: в основном отказы писателя форм на наборах 8.5.1.1529,
которых не было в аудите #593.

Новое расхождение, новый отказ или прежний отказ по другой причине роняют
тест. Устранённое расхождение тест сообщает, но не роняет, чтобы запись
можно было убрать.

**Чего тест не доказывает.** Достигнутая строка не значит проверенная.
Четыре мутации в строках, которых достигает только этот тест, оставили его
зелёным:
- `load_8_5_1.rs`: номер страницы `"1"` → `"0"`;
- `load_8_5_1.rs`: пустой список сохраняемых ShowTitle;
- `bodies_flowchart.rs`: не пишутся строки схемы;
- `bodies_flowchart.rs`: пропущено повышение до 8.5.

Контрольная мутация в чтении последовательности (`registers_export.rs`,
слоты `Documents`/`RegisterRecords` переставлены) роняет его с точным
сообщением.

**Найденный дефект.** `cf bootstrap --base-free` внешнего отчёта 8.3.27
без каталога `<имя>/` падает с «failed to move …/Reports». Он записан как
расхождение `8.3.27.2342/external/combined-erf`.

## Порядок замера

```text
# время каждого теста (бинарники из cargo test --no-run --message-format json)
RUSTC_BOOTSTRAP=1 <test-binary> -Z unstable-options --format json --report-time

# инструментированная сборка в отдельном target
eval "$(CARGO_TARGET_DIR=<target-cov> cargo llvm-cov show-env --sh)"
cargo test --locked --workspace --exclude ibcmd-rs --no-run
cargo test --locked -p ibcmd-rs --test '*' --no-default-features --no-run
cargo test --locked -p ibcmd-rs --lib --no-default-features --no-run

# кластер: свой профиль, затем покрытые строки
LLVM_PROFILE_FILE=<dir>/%4m.profraw <test-binary> --exact <tests of the cluster>
llvm-profdata merge -sparse <dir>/*.profraw -o <cluster>.profdata
llvm-cov export -format=lcov -instr-profile <cluster>.profdata <test-binary> -object target/debug/ibcmd-rs
```

Уникальные строки кластера — его строки рабочего кода за вычетом объединения
строк всех других кластеров. Для `ibcmd-dump` и `ibcmd-form-body` то же
сделано для каждого теста отдельно.
