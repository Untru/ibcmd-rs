# Выгрузка и загрузка внешних обработок и отчётов (.epf/.erf) без платформы

Дата: 2026-09-28. Ветка: `onecdec/offline-epf-cfe`. Статус: черновик, написан автономно
(пользователь поручил работу на ночь «делай всё что можешь»); требует утреннего ревью.

## 1. Цель и границы

Конечная цель (со слов пользователя): инструмент без платформы 1С, который выгружает
`.cf/.cfe/.epf/.erf` в полную XML-выгрузку (как «Выгрузить в файлы» Конфигуратора),
позволяет править её в VS Code и загружает обратно; позже встраивается в декомпилятор
onecdec вместо `v8dump.py`.

Работа разбита на подпроекты, у каждого свой цикл спецификация → план → реализация:

| # | Подпроект | Почему в этом порядке |
|---|---|---|
| **1** | **.epf/.erf: выгрузка + загрузка** (этот документ) | маленькие контейнеры, полный цикл «туда-обратно» проверяется быстро; в upstream ничего нет |
| 2 | .cfe: точная выгрузка (ObjectBelonging, заимствованные объекты) + загрузка в файл | нужен декомпилятору (ИТК); в upstream только через MSSQL |
| 3 | .cf: закрыть расхождения на нашем корпусе + загрузка (bootstrap: макеты, роли, …) | upstream сам активно чинит точность .cf — берём его наработки |
| 4 | Встраивание в onecdec | после готовности 1–3 |

Вне рамок подпроекта 1: SCSU-декодирование (остаётся через платформу по решению
пользователя), обычные формы (не управляемые), XML-диалект 2.21 (сначала 2.20 = 8.3.27).

## 2. Что уже известно (исследование 2026-09-27/28)

Контейнер `.epf/.erf` — тот же v8-контейнер (Format15), что и `.cf`:

- `root` = `{2,<uuid главного объекта>,}`; `version` = `{{216,0,{<формат хранения>,0}}}`
  (80310/80321/80501 в корпусе); `versions` — таблица GUID версий записей;
- главная запись `<uuid>` = XML-атрибут `uuid` у `<ExternalDataProcessor>`:
  `{1,{<uuid>},1,{<ClassId>,{1,{4,<TypeId>,<ValueId>,{0,{3,{1,0,<ObjectId>},"Имя",{синоним},"",0,0,0…0,0}},<форма по умолч.>,"",<вспом. форма>},N,<коллекции>}}}`;
  ClassId `c3831ec8-d8d5-4f93-8a22-f9bfae07327f` — обработка, `e41aff26-25cf-4bb6-b6c1-3f478a75f374` — отчёт;
- **коллекции записаны ровно как у `DataProcessor` в .cf** (`2bcef0d1` табличные части,
  `3daea016` макеты, `d5b0e5ed` формы, `ec6bb5e5` реквизиты); у внешнего нет команд
  (`45556acb`) и менеджера; заголовок версии 4 вместо 17;
- модуль объекта `<ObjectId>.0`, справка `<ObjectId>.1`; формы `<форма>`/`<форма>.0`;
  макеты `<макет>`/`<макет>.0` — как в .cf;
- `copyinfo` — **таблица ссылок на объекты конфигурации** (GUID → класс + имя), которую
  платформа использует, чтобы выгрузить типы вида `cfg:CatalogRef.Пользователи` без
  конфигурации. Выгрузка без платформы обязана разрешать типы по ней.

В ibcmd-rs (commit c41c1d2): `cf export` читает любой v8-контейнер, но главную запись
внешнего объекта не распознаёт (формы уходят в `CommonForms/`, модуль теряется);
`cf bootstrap` требует ровно один `Configuration.xml` и не умеет макеты. Кодовая база
огромная (≈500 тыс. строк), логика «как у DataProcessor» разбросана по десяткам мест
`owner_kind == "DataProcessor"`.

## 3. Подход

Рассмотрены три варианта:

1. **Адаптер на границе (выбран).** Внутри конвейера внешний объект обрабатывается
   как обычный `DataProcessor`/`Report` одной конфигурации; преобразование делается
   только на входе и выходе: записи контейнера ↔ записи «как в .cf», дерево XML
   `DataProcessors/X/…` ↔ `X/…`, корневой XML `DataProcessor` ↔ `ExternalDataProcessor`.
   Плюсы: переиспользует все правила выгрузки/компиляции обработок и отчётов (формы,
   реквизиты, табличные части, СКД, MXL), минимально трогает upstream-код → легко
   переносится на свежий upstream. Минус: нужна точная таблица соответствия заголовков
   (версия 4 ↔ 17) и XML-свойств — она небольшая и проверяется корпусом.
2. Новый вид `ExternalDataProcessor` сквозь весь конвейер. Чище концептуально, но
   десятки правок в upstream-файлах по 40 тыс. строк → конфликты при каждом обновлении.
3. Отдельный инструмент (Python). Пришлось бы заново писать декодеры форм/СКД/MXL —
   месяцы работы upstream. Отклонён.

## 4. Архитектура

Новый изолированный модуль `src/external/` (upstream-файлы трогаем только точками входа):

| Файл | Ответственность |
|---|---|
| `external/detect.rs` | по записям контейнера определить `ExternalKind::{DataProcessor, Report}`, uuid главной записи, ObjectId |
| `external/header.rs` | разбор/сборка заголовка версии 4 и преобразование «главная запись ↔ запись DataProcessor/Report (версия 17/…)»; отказ (fail-closed) на неизвестной форме |
| `external/copyinfo.rs` | разбор/сборка `copyinfo` → индекс «GUID → класс + имя» для разрешения типов |
| `external/export.rs` | `.epf/.erf` → XML: адаптировать записи, прогнать штатную выгрузку с индексом типов из copyinfo, перенести файлы `DataProcessors/X/*` → `X/*`, превратить корневой XML во внешний |
| `external/build.rs` | XML → `.epf/.erf`: обратное преобразование дерева, компиляция штатными компиляторами обработки/отчёта, форм, модулей, макетов; сборка `root/version/versions/copyinfo`; запись Format15 |
| `external/xml.rs` | преобразование корневого XML (корневой элемент, InternalInfo с ContainedObject, набор свойств, ссылки `DataProcessor.X.*` ↔ `ExternalDataProcessor.X.*`) |

Точки входа: `cf export` сам распознаёт внешний объект; `cf bootstrap` сам распознаёт
корень `ExternalDataProcessor/ExternalReport.xml`. Отдельные подкоманды не нужны.

### Поток выгрузки
1. Прочитать контейнер → записи. `detect` → вид, uuid, ObjectId.
2. `header`: главную запись переписать в запись `DataProcessor` (версия 17) с именем
   записи = ObjectId (так модуль `ObjectId.0` и справка `.1` привязываются штатно);
   недостающие поля заполнить нейтрально, запомнить исходные значения.
3. `copyinfo` → индекс типов; подать его в штатный `type_index`.
4. Штатная выгрузка записей в дерево `DataProcessors/X/…`.
5. `xml`: перенести в `X/…`, корень → `ExternalDataProcessor uuid=<главная запись>` с
   `ContainedObject(ClassId, ObjectId)` и только внешними свойствами.
Результат сравнивается с выгрузкой платформы в **пустой** базе.

### Поток загрузки
Обратный: дерево `X/…` → `DataProcessors/X/…` + синтетическая конфигурация с одним
объектом → штатные компиляторы (bootstrap) → из результата взять записи объекта →
главная запись версии 4, `root`, `version` (формат хранения по профилю), `versions`,
`copyinfo` (из ссылок `cfg:*` в XML: имя → класс; GUID ссылок нужно брать из
`copyinfo` исходника, если он есть в выгрузке, иначе генерировать детерминированно).
Недостающее в bootstrap (макеты MXL/СКД, справка, картинки форм) подключаем из уже
существующих писателей `compiler/bodies/*`.

### Результат пробы адаптера (2026-09-28, выброшенный код `_onecdec/spike_*.py`)

Главная запись переписана в запись `DataProcessor` (версия 17, имя записи = ObjectId,
таблица `versions` поправлена), контейнер отдан штатному `cf export` без
синтетической конфигурации. Итог на 33 первых .epf корпуса: без доработок совпало
337/459 файлов, после граничного переименования `DataProcessor.X → ExternalDataProcessor.X`
— **399/488 (82%)**. Оставшиеся расхождения — конкретные и понятные:

1. модуль объекта `<ObjectId>.0` и справка `<ObjectId>.1` не находят путь (индекс путей модулей);
2. типы-ссылки на конфигурацию выходят как `<v8:TypeId>` — нужно разрешение через `copyinfo`;
3. ссылки справки на собственный объект (`../id<главная запись>/…`) — индексу нужен uuid главной записи;
4. картинки из общей конфигурации в формах (`<Picture><xr:Ref>0:…`) — сверить с эталоном;
5. формы в формате 8.5 внутри .epf (реальный Обфускатор) — общий пробел upstream, не наш.

### copyinfo (расшифровано)

`{4,{N,{<obj>,<obj>,k,{<ClassId>,"Имя"}[,{<ClassId дочернего>,"Имя"}]…}…},{M,{<TypeId>,<obj>,<номер порождённого типа>}…},{…},{0,0},{0}}`.
Номер — индекс в списке порождённых типов класса (Catalog: 0 Object, 1 Ref, …; Enum: 0 Ref, …).
Так `TypeId → cfg:CatalogRef.Пользователи` восстанавливается без конфигурации.

### Результат выгрузки (план 1 выполнен, 2026-09-28)

Clean-room фикстуры (.epf с реквизитом, табличной частью, формой, MXL-макетом,
модулем; .erf со СКД и формой) выгружаются побайтно как у платформы. Корпус
111 объектов: **98,2% файлов побайтно** с эталоном в базе с конфигурацией
(1519/1547); реальные файлы, собранные 8.5 (`setup.epf`, `scsu_decoder.epf`),
совпадают полностью с эталоном 8.5.1 (XML 2.21). Хвост: поля динамических
списков по таблицам конфигурации, пустой MXL, раскладки форм 8.5 (upstream).

### Проба для загрузки: платформа привязывает ссылки по именам copyinfo

В корпусном .epf все 15 uuid объектов/типов конфигурации заменены случайными
(согласованно во всех записях) — выгрузка платформой в базе с конфигурацией
совпала с эталоном во всех ссылках (5/6 файлов; единственная разница — заменённый
по ошибке собственный TypeId объекта). Вывод для загрузки: uuid объектов
конфигурации, которых нет в XML (там только имена), можно генерировать
детерминированно по имени — при открытии в базе с конфигурацией платформа
разрешает их по `copyinfo` (класс + имя). Проба: `_onecdec/probe_copyinfo_rebind.py`.

### Загрузка v1: наложение правок на исходный файл (решение 2026-09-28)

Проба `cf bootstrap` на синтетической конфигурации с обработкой упала на первом
же свойстве (`UnevidencedProperty … FillValue` у реквизита табличной части):
компилятор upstream «с нуля» намеренно принимает только подтверждённое
подмножество, и доводить его — отдельный большой проект (у upstream загрузка
идёт поверх существующих записей через MSSQL). Для сценария пользователя
«выгрузил → правлю в VS Code → загружаю» исходный файл есть всегда, поэтому:

`ibcmd-rs cf load <дерево> <выход> --base <исходный .cf|.epf|.erf>`:
1. выгрузить базу во временный каталог (тем же `cf export`, для внешних — адаптер);
2. сравнить дерево пользователя с выгрузкой базы пофайлово;
3. по отчёту выгрузки (ключ записи → выходные файлы) отобразить изменённые файлы
   в записи хранилища: `Ext/*Module.bsl` (и корневые `Ext/*Module.bsl`
   конфигурации) → текст модуля (`ModuleText`); `Forms/F/Ext/Form/Module.bsl` →
   модуль внутри базового тела формы (`pack_form_body_blob_from_module_text`).
   Текст модуля — только UTF-8 (BOM допустим), иначе отказ с путём;
   `Form.xml` — **отказ** (финальное ревью: упаковщик тела формы переносит только
   часть свойств и молча терял правку, меняя соседние свойства; до проверки
   результата повторной выгрузкой правка Form.xml не поддерживается);
   записи с точкой в начале имени (`.git`, `.vscode`) не сравниваются;
4. наложить штатным `overlay` (`compile_overlay_with_retained_budget` +
   `publish_overlay_new`) на **исходный** контейнер: неизменённое остаётся
   побайтно, `versions` обновляется штатно; главная запись внешнего объекта не
   трогается — обратный адаптер не нужен;
5. любые другие изменения (метаданные, `Form.xml`, макеты, справка,
   добавление/удаление файлов) в v1 — отказ со списком файлов (первые 20 и
   счётчик остальных; fail closed), не молча.

Проверка: `export(load(tree)) == tree` в тестах; приёмка — платформа открывает
результат и её выгрузка равна дереву пользователя. `.cfe` не входит: у него нет
записи `versions`, overlay upstream её требует — это подпроект 2.

### Результат загрузки v1 (план 2, 2026-09-28)

8.3.27.2214 (`_onecdec/verify_load.py`):

  совпадает с отредактированным деревом **104/104** (7 объектов без модулей пропущены);
- сценарий декомпилятора на реальном `obf/1Cv8_обф.cf` (134 МБ): три закрытых

## 5. Критерии готовности

- **Эталон выгрузки — выгрузка платформы в базе с конфигурацией** (`native-<ver>/ext-cfg`),
  а не в пустой базе: в пустой базе платформа теряет информацию (типы-ссылки на
  конфигурацию становятся `xs:string`, 111 файлов корпуса) — для инструмента правки
  и обратной загрузки это неприемлемо. Для реальных .epf без конфигурации эталон —
  выгрузка в пустой базе, и расхождения только в разрешённых нами типах допустимы.
- **Выгрузка:** на корпусе (5 реальных + ~150 сгенерированных .epf/.erf) каждый файл
  выгрузки совпадает побайтно с эталоном; всё несовпадающее — в явном списке известных
  расхождений с причиной.
- **Загрузка:** для каждого файла корпуса `build(export(x))` открывается платформой, и
  её выгрузка совпадает с выгрузкой исходного `x` (семантический круг); побайтного
  совпадения контейнера не требуется (GUID версий случайны).
- **Отказ вместо догадок:** незнакомая форма записи → понятная ошибка, а не молча
  неверный XML (правило upstream).
- Все существующие тесты upstream зелёные.

## 6. Тестирование

- Модульные тесты (TDD) на каждый преобразователь: заголовок 4↔17, copyinfo, XML-корень,
  перенос путей — на маленьких фрагментах из корпуса.
- Интеграционный тест по корпусу: путь в `IBCMD_ONECDEC_CORPUS`, тест пропускается, если
  переменной нет (корпус собран из пользовательской конфигурации, в git не кладём).
- Эталоны: `_onecdec/oracle_dump.py` (выгрузки платформой),
  `_onecdec/gen_external_corpus.py` (рост корпуса из обработок/отчётов конфигурации),
  `_onecdec/cmp.py` (побайтное сравнение деревьев), проверка круга — платформой.

## 7. Риски

- Поле `""` между формами в заголовке версии 4 и точная схема `copyinfo` пока
  не расшифрованы до конца → закрываются корпусом (150+ образцов).
- Ссылки внешнего объекта на конфигурацию без `copyinfo`-GUID при загрузке «с нуля».
- Upstream меняется очень быстро (≈100 коммитов за 3 дня): держим изменения в
  `src/external/` и регулярно переносим ветку на свежий upstream.
- Лицензии у upstream нет: работа ведётся в локальной ветке, ничего не публикуется без
  решения пользователя.
