### Где лежит BaseForm (найдено 2026-09-28)

Тело формы расширения (`<form>.0`, пример — ИТК `04674ad9-….0`, 78 КБ) на верхнем
уровне: `[4, {50,…форма расширения…}, "текст модуля", {4,0,0,0,{#base64:…настройки}},
{0,0}, {0,0}, {0,0}, {0,0}, 1, {4,{50,…базовая форма…},…}, 0]` — поле 8 = 1 (есть
базовая форма), поле 9 — **полноценное вложенное тело базовой формы**. Эталон
выгружен в пустой базе, значит `<BaseForm version="2.20">` целиком берётся отсюда:
тот же писатель форм upstream, применённый к полю 9, с отступом +1 и обёрткой.
Вероятный план: в `form_body.rs` после записи формы, если поле 8 = 1, отрисовать
поле 9 и вставить перед `</Form>`; `callType` — из хвоста кортежа события.

## Загрузка в .cfe

`cf load` (план 2) для .cfe упирается в `overlay_versions_missing`: у контейнера
расширения нет записи `versions`, а предварительная проверка overlay upstream
(`crates/ibcmd-cf/src/overlay.rs`, `versions_index`) её требует. Применение
(`apply_overlay`) уже умеет работать без неё (`if let Some(versions_index)`).
**Сделано (коммит 9112a91):** `OverlayCodec::requires_versions()` (по умолчанию
`true`), кодек загрузки отвечает `false`, когда в базе нет `versions`. Приёмка на
реальном ИТК: 4/4 закрытых модуля заменены декомпилированным текстом, платформа
загрузила расширение, `/CheckModules` — 0 ошибок, текст совпал.

### `xmlns:dcssch` в Form.xml зависит от режима совместимости (найдено 2026-09-28)

Не от того, расширение это или конфигурация. Проба 8.3.27.2214: расширение
`ТестРасширение` + общая форма, `ConfigurationExtensionCompatibilityMode`
Version8_3_11 … Version8_3_18 → корень `<Form>` **без** `xmlns:dcssch`;
Version8_3_19 … Version8_3_26 → с ним. Конфигурация (cfe_base + общая форма):
`CompatibilityMode` Version8_3_10 / Version8_2_16 / (DontUse → Version8_3_8) →
без, Version8_3_19 / Version8_3_27 → с ним; `ConfigurationExtensionCompatibilityMode`
конфигурации на это не влияет. Порог: режим ≥ 8.3.19. У ИТК режим 8.3.10 →
151 форма отличалась только этим. Upstream пишет декларацию всегда
(`format_form_body_xml_with_dcs_profiles`), т.е. ошибка есть и у конфигураций
со старым режимом. Пробы: scratchpad `probe_ext_form.py`, `probe_cfg_form.py`.

### Попутные находки (не исправлены)

- **Конфигурация: `ConfigurationExtensionCompatibilityMode` читается не из того
  поля.** В кортеже `{68,…}` поле 26 = `CompatibilityMode`, поле 43 =
  `ConfigurationExtensionCompatibilityMode` (проба: 80310 / 80327, натив печатает
  Version8_3_10 / Version8_3_27). Upstream берёт поле 26 для обоих.
- **Расширение, собранное 8.3.27, теряет свойства расширения в
  `Configuration.xml`:** нет `ObjectBelonging`, `ConfigurationExtensionPurpose`,
  `KeepMappingToExtendedConfigurationObjectsByIDs`, `NamePrefix` пустой,
  нет `UsePurposes`/`DefaultRoles`, вместо свойств расширения пишутся свойства
  конфигурации (`UpdateCatalogAddress`, хранилища настроек, `CompatibilityMode`).
  То же у ИТК (плюс `xr:PropertyState` у заимствованных модулей). Заимствованный
  `Language`: нет `<InternalInfo/>`, `ObjectBelonging`, `ExtendedConfigurationObject`,
  лишний `<Synonym/>`.

### Решения утра

- Ожидание upstream для пустой колонки начальной страницы (`<RightColumn>…</RightColumn>`)
  заменено на `<RightColumn/>` по выгрузке платформы; старая форма блоба без хвостового
  поля читается, но 8.3.27 её не принимает («Ошибка формата потока») — значит, её пишет
  только компилятор upstream XML→cf (не тронут, наш `cf load` его не вызывает).
- Даты в списке выбора — только у поля ввода и только под нулевой парой
  идентификаторов (то, что наблюдалось).
- Сбой `with_adopted_form_parts` (нечитаемая копия базовой формы) оставлен сбоем этой
  формы с сообщением, а не формой без `<BaseForm>` молча.
- Отказ от ревьюера «не берусь судить»: `Scale` 8.5 в 2.20, `callType` у команд
  заимствованных форм, XML→CF для `<BaseForm>`/`callType` (наша загрузка не принимает
  правки Form.xml и метаданных), пороги 8.5 для `dcssch`/`AnyRef` (подтверждена только
  сторона ниже порога).
