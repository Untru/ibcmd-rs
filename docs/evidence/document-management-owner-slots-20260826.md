## Общая форма дефекта

Почти все находки этого участка — один и тот же дефект: слот записи
владельца, у которого в подавляющем большинстве объектов одно значение, был
приколочен к нему проверкой (`fields.get(N)? != "0" → return None`) или
напечатан литералом в писателе. Объект, пишущий второе значение,
отказывался ЦЕЛИКОМ — не «свойство прочитано неверно», а «файла нет».

Разделять такие слоты умеет только перепись по всему корпусу: физическая
запись объекта против XML, которую платформа пишет для ТОГО ЖЕ объекта.
Ниже каждая перепись приведена с числом наблюдений обоих значений — то есть
разделение доказано, а не просто согласовано.

## Отказы, снятые чтением того, что уже лежит в записи

* **Связи параметров выбора бизнес-процесса.** Реквизиты табличных частей
  разбирались с пустой областью владельца, и слот 14 допускался только
  пустой записью. Запись `BusinessProcess.Исполнение` →
  `ДополнительныеРеквизиты` → `Значение`, слот 14:
  `{5006,1,"Отбор.Владелец",2,{0,<секция>},{0,<реквизит>},0}` — та же
  запись, что пишет план видов характеристик. Область владельца у
  вызывающей стороны была, её просто не передавали.

* **Макеты бизнес-процессов.** Непустая коллекция роли `template` давала
  типизированный отказ. Это обыкновенная коллекция владения; читается общим
  кодом, порядок `<ChildObjects>` снят с байтов: реквизиты, табличные
  части, формы, макеты, команды.

* **Табличные части задач.** Пятая корневая коллекция задачи требовалась
  ПУСТОЙ, с голым `return None` без диагностики. Конверт задачи совпадает с
  конвертом бизнес-процесса и плана обмена: `(1, без Use, с
  LineNumberLength)`, маркер `LineNumber` — `-10`.

## Перепутанные протокольные идентификаторы

`cfg:BusinessProcessObject`, `cfg:TaskObject` и `cfg:ChartOfAccountsObject`
стояли не за своими идентификаторами — по кругу. Дефект не проявлялся,
потому что источники подписки на события пишутся в ОДНОМ каноническом
порядке семей: перестановка трёх имён внутри одного набора давала те же
байты. Разрешают спор подписки, чей `<Source>` называет одну семью:

* `fcd3404e` один в образце двенадцати подписок, и все двенадцать —
  `cfg:BusinessProcessObject`;
* `ОбменДаннымиДО20ДО21ПередЗаписью` несёт `{3e63355c, cf4abea6, fcd3404e}`
  против `{BusinessProcess, Catalog, Task}` — остаётся `3e63355c` = `Task`;
* `ОбработкаПредопределенныхЭлементовПередЗаписью` несёт
  `{238e7e88, 30b100d6, 82a1b659, cf4abea6}` против четырёх имён —
  остаётся `238e7e88` = `ChartOfAccounts`.

Вместе с этим сняты три исключения по имени события и по точному списку
образца: каждое называло ровно то имя, которое даёт общая таблица.
Канонический порядок семей применяется всегда, а не только когда все
источники — наборы типов.
