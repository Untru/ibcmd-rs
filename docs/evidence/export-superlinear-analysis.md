# Где именно наш экспорт сверхлинеен

Задача: `docs/evidence/export-timing-2214-20260824.md` установил факт (`t ~ n^1.45..1.75`
выше ~10 тысяч файлов), но не место. Этот документ — место, числа и одна
применённая правка. Платформа: 8.3.27.2214, хост macOS 15.7.4 arm64,
24.08.2026. Стенд — общая машина; во время части замеров параллельно шёл
экспорт ERP УХ другого агента волны, поэтому абсолютные секунды колеблются
между прогонами на несколько десятков процентов. Относительные числа (доли
фаз, разы) устойчивы и на них строится вывод.

## Метод

1. Временная инструментация `std::time::Instant` вокруг каждой крупной фазы
   `dump_table_rows_with_options_mode` и `export_storage_image_to_source`
   (`src/mssql_dump/mod.rs`), печать в stderr за флагом
   `IBCMD_EXPORT_PROBE` (переменная окружения, инертно без неё). Прогон на
   `sslbase` (9 617 файлов платформы, 7 566 записей хранилища) и `ut`
   (50 898 файлов, 41 699 записей) — доли фаз сравнены между двумя размерами.
2. Профайлер: `samply` не установлен на стенде; использован системный
   `/usr/bin/sample <pid> 20` во время прогона `ut`, с `[profile.release]
   debug = true` в Cargo.toml на время профилирования (снято перед коммитом).
3. По найденной функции — чтение кода, статический разбор сложности,
   целевая точечная правка, затем то же измерение до/после.

Вся инструментация и `debug = true` сняты перед коммитом:
`git diff` от базового коммита содержит только `src/mssql_dump/source_assets.rs`.

## Место №1 (исправлено): полный проход по корпусу на каждый объект

`source_assets_from_metadata_text_inner` (`src/mssql_dump/source_assets.rs:987`)
вызывается **один раз на каждый объект метаданных** (`for row in metadata_texts`)
из двух мест — `source_asset_paths_with_indexes` (`source_assets.rs:600`) и
`source_asset_discovery_misses` (`source_assets.rs:736`). Внутри неё стоял:

```rust
for (body_id, body_row) in rows_by_file_name {   // ВСЕ записи корпуса
    let Ok(row_id) = ConfigRowId::parse(body_id) else { continue };
    if row_id.owner() != uuid || mapped_ids.contains(*body_id) { continue }
    ...
}
```

`rows_by_file_name` — это **все** записи хранилища (весь корпус), не только
дети текущего объекта. Цикл ищет "потерянные" дочерние записи (help-блоки,
предопределённые данные), сканируя весь корпус и отбрасывая всё, что не
принадлежит текущему `uuid`. Вызывается на каждый объект → полный проход по
корпусу внутри цикла по объектам → O(объекты × записи), и оба множителя растут
с размером конфигурации. Ровно паттерн, который бриф предлагал искать.

Проверка арифметикой: sslbase — 7 566 записей × 3 736 объектов ≈ 28,3 млн
итераций; ut — 41 699 × 20 605 ≈ 859 млн, то есть в 30,3 раза больше. Замеренный
рост двух зависимых фаз (26,1× и 25,2×, см. таблицу ниже) — то же самое
подтверждает независимо.

### Правка

`rows_by_file_name` — `BTreeMap<&str, &ConfigRow>`, ключ — `"<uuid-владельца>.<суффикс>"`.
Все записи одного владельца лежат в точном лексикографическом диапазоне
`[uuid+".", uuid+"/")` — `.` (0x2E) и `/` (0x2F) соседние байты, поэтому
диапазон точен: содержит ровно те ключи, чей владелец равен `uuid`, и ничего
больше. Замена полного прохода на `rows_by_file_name.range(...)` даёт
идентичное множество кандидатов за O(log n + число детей объекта) вместо
O(n). Проверка `row_id.owner() != uuid` внутри цикла оставлена как
защитный no-op — поведение не меняется, даже если где-то предположение о
диапазоне окажется неверным. Один блок, `source_assets.rs:1177-1207`,
+16/-1 строка.

## Место №2 (НЕ исправлено — риск выше, чем "локально и безопасно")

После места №1 самая большая оставшаяся доля на `ut` — не `per_row_parallel`
(параллельная запись, 16 потоков, 12,0 с), а **последовательные** фазы
построения индексов по ссылкам: `field_refs` (25,9 с, из них
`build_metadata_field_type_reference_index_from_texts` — 19,3 с),
`object_refs` (9,5 с), и `misc_refs` → `standalone_refs` (9,2 с, при этом на
`sslbase` эта же фаза — 0 мс: она включается только при наличии
`SourceAssetKind::StandaloneContent`-объектов, которых в sslbase просто нет).
Все три — однопоточные (общий CPU% всего экспорта ut держится в районе
230–300 % на 16-ядерной машине именно поэтому: тяжёлая часть работы не
распараллелена, а последовательна и суперлинейна).

### Профиль (`sample`, 20 с окно во время `field_refs`/`object_refs`)

```
3214  innermost_metadata_object_fields_around_header  (mod.rs:28755)
      | scan_1c_braced_value
2230  innermost_metadata_object_fields_around_header + 284
1126  split_1c_braced_fields_bounded → scan_1c_braced_value
1091  split_1c_braced_fields_bounded
 710  split_1c_braced_fields_bounded → scan_1c_braced_value
 684  split_1c_braced_fields_bounded
 176+154 (тот же паттерн повторяется глубже в дереве вызовов)
```

Одна функция и две её прямые подпрограммы доминируют в сэмплах
однопоточной фазы.

### Причина

`innermost_metadata_object_fields_around_header` (`mod.rs:28755`) ищет
"ближайшую охватывающую фигурную скобку с нужным свойством" вокруг позиции
одного вложенного заголовка:

```rust
let mut search_end = marker_start;
while let Some(start) = text[..search_end].rfind('{') {   // назад по ВСЕМ '{' до начала текста
    search_end = start;
    let Some(end) = scan_1c_braced_value(text, start) else { continue };  // O(размер этой скобки)
    if marker_start >= end { continue }                    // не охватывает — отброшена, но уже посчитана
    let Some(fields) = split_1c_braced_fields(text, start) else { continue };
    ...
}
```

Функция вызывается **один раз на каждый вложенный заголовок** (атрибут,
поле, реквизит) внутри объекта — 4 места вызова:
`parse_metadata_child_value_types` (`mod.rs:15866`, эту ветку не трогали),
`parse_metadata_child_value_types_with_builtin` (`mod.rs:15885`, отсюда
`field_refs`), `parse_metadata_tabular_section_properties`, и
`http_service_child_candidates_from_text`. Для каждого заголовка она
сканирует **назад по всем предыдущим скобкам того же объекта**, не
останавливаясь на первой охватывающей — соседи по тексту, не только предки,
проверяются и отбрасываются той же ценой. При H заголовках в объекте текстом
длины L это ближе к O(H·L) на объект, и раз H растёт вместе с L (больше
атрибутов — длиннее текст), суммарно похоже на O(L²) **на один большой
объект**, не на весь корпус сразу. Родственные функции с тем же почерком —
`enclosing_metadata_header_for_code` (`mod.rs:7000`),
`is_offset_inside_metadata_object_code` (`mod.rs:6990`),
`preceding_metadata_header_for_code_with_bounds` (`mod.rs:7042`) — их
использует, среди прочего, `standalone_child_reference`, отсюда рост
`standalone_refs`.

Это объясняет, почему рост выглядит "сверхлинейным по числу файлов", хотя
настоящая причина — сложность **отдельных** объектов: у `ut` (документы,
регистры, справочники ERP) объекты в среднем гораздо шире (больше реквизитов,
табличных частей) чем у `sslbase` (библиотека классов с некрупными объектами).
Число файлов и число атрибутов на объект коррелируют, но не совпадают — вот
откуда нечистый, но устойчиво больший единицы показатель степени (1,7–1,9)
даже после того как место №1 устранено, и почему `standalone_refs` — не
"сверхлинейный", а "включается только на конфигурациях, где объекты этого
вида вообще есть, и там дорог по той же причине".

### Почему не правлю сейчас

1. **Семантика тонкая.** Функция не просто "ближайшая скобка" — она хранит
   `best` и заменяет его только при более узком `end`, отбрасывает кандидатов
   по значению первого поля (`"1"`/`"3"`) и по наличию `uuid` через
   `metadata_header_field_index`. Корректная замена требует не текстового
   поиска, а построения дерева вложенности скобок (стек с родительскими
   указателями, один проход O(L) на объект), и переноса тех же фильтров на
   обход цепочки предков — обход должен идти от ближайшего предка наружу,
   останавливаясь на первом, что проходит фильтры, и это нужно доказать
   эквивалентным текущему `best`-перебору на **всех** конфигурациях, а не
   только на двух измеренных.
2. **Расшарено широко.** Минимум 4 места вызова только для одной функции;
   `scan_1c_braced_value` / `split_1c_braced_fields` (и `_bounded`) —
   низкоуровневые примитивы, вероятно используемые в десятках мест по всему
   37-тысячестрочному `mod.rs`. Правка сюда — не локальная функция, а
   пересмотр общего разбора фигурных скобок 1С-формата, с высокой ценой
   ошибки на файле, где доктрина уже трижды фиксировала тонкие дефекты именно
   в этой части кода (белый список тегов, фиксированная арность — пункт 7
   доктрины).
3. **Цена ошибки высокая, а выигрыш этой правки уже получен.** Место №1 дало
   1,68× на `ut` доказанной безопасной правкой в 16 строк. Место №2 —
   потенциально сопоставимый или больший выигрыш (field_refs+object_refs+
   standalone_refs ≈ 39 с из оставшихся 87 с, 45 %), но ценой переписывания
   общего парсера скобок — это отдельная задача с отдельным циклом
   до/после-паритета на **всех** конфигурациях стенда, не блиц в рамках этой.

### План для последующей волны (не выполнено)

1. Один проход по `text` объекта → `BraceIndex`: для каждой `{` — позиция
   закрывающей (уже есть `scan_1c_braced_value`, просто вызвать один раз на
   скобку верхнего уровня рекурсивно, а не заново на каждый запрос) и индекс
   родителя. Стек, O(L).
2. `innermost_metadata_object_fields_around_header` через `BraceIndex`:
   найти скобку, чей интервал теснее всего охватывает `marker_start` (bsearch
   по началам + подъём по `parent`), затем идти по цепочке предков наружу,
   применяя те же фильтры, вернуть первую подходящую.
3. Тот же `BraceIndex`, переданный (не пересчитанный) в
   `enclosing_metadata_header_for_code` /`is_offset_inside_metadata_object_code`/
   `preceding_metadata_header_for_code_with_bounds` для этого объекта — сейчас
   каждая функция сканирует текст заново на каждый вызов.
4. Гейты те же, что в этой правке (byte-for-byte на sslbase/ut/ssl, тесты,
   bundled9, fmt) — и дополнительно полный `uh` (140 411 файлов), потому что
   именно там доля объектов с широкими реквизитами и табличными частями выше
   всего, а стенд для итерации специально выбирает `sslbase`/`ut` как
   двухпорядковую выборку, не как полное покрытие формата.

## Дополнение 24.08 (вечер): место №2 сужено — обратный перебор переписан, хвост не в нём

Функция `innermost_metadata_object_fields_around_header` переписана: кандидаты
«охватывающих» скобок собираются одним прямым проходом (цепочка предков плюс
`{` внутри строковых литералов — единственные позиции, которые старый
`rfind`-перебор мог принять), выбор повторяет старое правило строгого
уменьшения конца в старом порядке обхода. Эквивалентность доказана побайтово:
собственные до/после-диффы **0/0/0** на sslbase, ssl, ut и uh (140 411 файлов).

Промежуточная версия без строковых кандидатов меняла один файл на uh — и это
вскрыло два факта: (а) старый перебор действительно принимал кандидатов,
начинающихся внутри строковых литералов, то есть точная эквивалентность
требует и их; (б) `CommonForms/ФормаСписка` — **гонка записи** двух форм в
один путь, недетерминированная и при неизменном бинарнике (см.
`open-leads-multi-config.md`, раздел 4).

Замер на тихой машине (все агенты волны завершены):

| конфигурация | до | после |
|---|---:|---:|
| sslbase | 6,29 с | 6,10 с (−3 %) |
