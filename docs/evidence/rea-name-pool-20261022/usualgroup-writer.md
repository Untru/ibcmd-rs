# Писатель XML формы: `UsualGroup` в `mngbase.dll`

Дата: 22.10.2026. Ветка: `feat/rea-form-property-inventory-20261022`.

## Что найдено

В `mngbase.dll` (8.5.1.1529, SHA-256 `a4d97a9b…be0`) найден писатель элемента
`UsualGroup` — функция `0x180726190` (файловое смещение `0x725590`).

Функция создаёт элемент в пространстве имён `http://v8.1c.ru/8.3/xcf/logform`
и затем последовательно пишет атрибуты. Каждый атрибут пишется по числовому
идентификатору, а значение по умолчанию пропускается:

```c
plVar12 = writer->element(L"http://v8.1c.ru/8.3/xcf/logform", L"UsualGroup");

if (get_40(obj) != 4)  write_attribute(writer, 0x1f, get_40(obj));
if (get_50(obj) != 0)  write_attribute(writer, 0x20, get_50(obj));
if (get_60(obj) != 0)  write_attribute(writer, 0x21, get_60(obj));
if (get_70(obj) != 0)  write_attribute(writer, 0x22, get_70(obj));
if (get_80(obj) != 3)  write_attribute(writer, 0x23, get_80(obj));
if (get_90(obj) != 3)  write_attribute(writer, 0x24, get_90(obj));
...
```

То есть **порядок и умолчания заданы кодом**, а не выводятся из выгрузки.
Это и есть искомое правило: таблица «ID → умолчание» в порядке вызовов.

## Что это даёт проекту

1. Порядок свойств в XML — не эвристика, а последовательность ID в коде;
   её можно зафиксировать как таблицу и проверять побайтово.
2. Умолчания — тоже факт из кода: `4`, `3`, `2`, `0` в сравнениях.
3. Следующий шаг — сопоставить ID с XML-именами (`0x1f` → имя атрибута).
   Кандидаты: реестр атрибутов в `config.dll` либо выравнивание с реальной
   выгрузкой формы, где порядок атрибутов совпадает с порядком ID.

## Ограничения

- Разобрана одна функция (`UsualGroup`); `Table`, `Button`, `Field` — отдельные
  писатели, их нужно снять так же.
- Глобальные ID сквозные для всех элементов: один и тот же ID в разных
  писателях означает одно и то же свойство, поэтому таблица «ID → имя»
  строится один раз.
- Псевдокод Ghidra; имена полей объекта (`get_40`, `get_50`) — смещения
  виртуальных методов, а не имена свойств.
