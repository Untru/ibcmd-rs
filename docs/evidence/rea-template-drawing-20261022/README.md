# Шаблон Ганта: `drawing` с объектом `GanttChart`

Дата: 22.10.2026. Последний файл, мешающий полному паритету:
`Reports/Gant1C/Templates/пмГант_Гант/Ext/Template.xml` (1960 из 1961
совпадают).

## Что расходится

В нативном шаблоне есть элемент `<drawing>` с вложенным объектом
`d3p1:GanttChart`; в нашей выгрузке его нет вовсе. Плюс связанные с ним
`formatIndex` и границы ячеек — всего 369 строк различий.

## Структура `<drawing>`

Дочерние элементы в порядке платформы:

```
drawingType          GanttChart
id                   1
formatIndex          61
text                 <v8:item><v8:lang>ru</v8:lang><v8:content>Начало</v8:content></v8:item>
beginRow / beginRowOffset
endRow / endRowOffset
beginColumn / beginColumnOffset
endColumn / endColumnOffset
autoSize             false
pictureSize          Stretch
zOrder               1
object               xsi:type="d3p1:GanttChart"
```

Объект `d3p1:GanttChart` несёт `<d3p1:chart>` с десятками настроек:
`seriesCurId`, `pointsCurId`, `isSeriesDesign`, `realSeriesCount`,
`realExSeriesData` (цвет, линия, маркер), `isPointsDesign`,
`realPointCount`, `curSeries`, `curPoint`, `chartType`, `circleLabelType`,
`labelsDelimiter`, `labelsLocation`, `lbFormat`, `lbpFormat`, `labelsColor`,
`labelsFont` (`AutoFont`), `transparentLabelsBkg`, `labelsBkgColor`,
`labelsBorder` и далее.

## Где это хранится

Проверено на самой записи шаблона (`Config`, строка
`4efcc508-928f-432a-83eb-851a38ef7e7e.0`, распакованный raw-deflate, 53 146
символов):

- подстрок `Gantt`, `drawing`, `seriesCurId`, `d3p1`, `chart` в записи **нет**;
- все 50 блоков `{#base64:…}` — это записи форматов ячеек по ~0.5 КБ
  (`2,1,<uuid>,{9,{"Pattern",…}}`), ни один не содержит настроек диаграммы;
- значит настройки `GanttChart` лежат в **двоичной секции** записи, которую
  `moxel` пока не разбирает, а не в тексте и не в base64-блоках.

`moxel.rs` (писатель шаблонов) вообще не упоминает `drawing`; запись MXL
разбирается на форматы и палитру, а чертёж отбрасывается молча — это и есть
последняя «тихая потеря» в паритете.

### Найденная запись чертежа

По координатам из XML (`endColumnOffset 1029`, колонка 27, строка 12) запись
найдена; она идёт после таблицы форматов:

```
{16,61,{1,1,{"ru","Начало"}},0},   // формат 61 + текст
10,27,0,0,0,27,12,1029,0,1,        // координаты: 27…27, 0…12, смещения 0/1029
e5fdc112-5c84-4a16-9728-72b85692b6e2,  // идентификатор объекта
{
  {19,                             // код типа чертежа (GanttChart)
    {0,
      {11},
      {75,1,0,1,0, …}              // настройки диаграммы
    }
  }
}
```

Рядом лежит `{28,0,nil,13,0,52,1,53,2,…}` — список форматов, на которые
ссылается чертёж (в XML это `formatIndex` и связанные форматы).

Код `19` — единственный кандидат на `drawingType GanttChart`: это
единственный чертёж в записи, он стоит ровно там, где в XML находится
`<drawing>`, а его полезная нагрузка — настройки диаграммы.

## Совместимость с формовым сериализатором подтверждена

Раскладка обёртки в записи шаблона проверена разбором по скобкам: **33
члена**, первый — `19`, второй — `{0,{11},{75,1,0,1,0,…}}`.

Это в точности грамматика ревизии `19`, которую уже реализует
`format_form_gantt_chart_settings_xml` в `mssql_dump/form_body.rs`:

- `wrapper[0] == "19"`, длина `33`;
- `wrapper[1]` — тройка `{0,{11},<данные>}`, где `{11}` проверяется той же
  функцией;
- остальные члены (4, 5, 21, 27, 30, 32 и т.д.) читаются по тем же слотам.

То есть для чертежа шаблона **не нужен новый сериализатор настроек**: можно
передать эту обёртку в существующую функцию и получить готовый XML объекта
`d3p1:GanttChart`. Останется обернуть его в `<drawing>` с координатами из
записи (`10,27,0,0,0,27,12,1029,0,1,<uuid>`) и форматом `formatIndex`.

## Что уже есть и может пригодиться

- `format_form_gantt_chart_settings_xml` — готовый рендер настроек
  (namespace `d3p1`), принимает ровно эту обёртку.
- `parse_moxel_*` уже умеет форматы и палитру; `drawing` — отдельная ветка.

## Почему разбор всё ещё отвергает чертёж

Отладкой установлено:

- запись доходит до диспетчера `parse_moxel_drawing`: `len=14`, `kind="10"`,
  `fields[11] = e5fdc112-…` (uuid GanttChart), `fields[13] = "0"`;
- обёртка `fields[12]` разбирается в один член — `{19,…}`; значит вызов
  `parse_moxel_gantt_chart` происходит;
- возврат идёт не через явные `return None` (инструментирование всех таких
  точек не сработало), а через `?` внутри вспомогательных разборов —
  `parse_gantt_points_data`, `parse_gantt_series_data`,
  `parse_gantt_time_scale` или разбор цвета/линии.

Первое расхождение видно в записи points: наш член 2 начинается
`{1,{3,0,1,0,{2,{8,0,0,0,0,0,{"U"},{1,0},{"U"},0,4294901761},…`, тогда как
`parse_gantt_points_data` ожидает `inner.len() == 8` и `value` из четырёх
членов с конкретным `{4,0,{0},"",-1,-1,1,0,""}`. В 8.5.1.1529 эта часть
записи отличается от корпуса 8.3.27/8.5.1.1150, на котором калиброван
разбор.

Сделано по пути: проверка «автоматического» хвоста цвета расширена на
`{4,4,{0},4}` (так 8.5.1.1529 пишет тот же автоматический цвет, что 8.5.1.1150
писала `{3,4,{0}}`); тесты зелёные.

Следующий шаг — согласовать `parse_gantt_points_data`/`series`/`time_scale`
с раскладкой 8.5.1.1529 (по дампу конкретных членов), после чего чертёж
пойдёт в существующий писатель.

### Продолжение (после проверки точек)

Разобрал points/series по членам: у points `inner` — 8 членов, `value` — 4,
ключевая запись `{8,0,0,0,0,0,{"U"},{1,0},{"U"},0,4294901761}` совпадает с
ожидаемой; у series `inner[4]` = `{3,<та же запись>}`. Расходятся только
автоматические цвета: 8.5.1.1529 пишет `{4,0,{0},0}` и `{4,4,{0},4}` там, где
корпус писал `{3,0,{0}}` и `{3,4,{0}}`.

Введена нормализация `compact_moxel_auto_color_token` (обе записи означают
«авто», платформа не печатает ничего) и применена во всех сравнениях токенов
диаграммы; тесты 4051 зелёные. Этого **недостаточно**: чертёж всё ещё
отвергается, теперь уже внутри `parse_moxel_chart` (после успешного
`points`/`series`).

### Последняя причина (шаг 3 из 78)

Контрольные точки внутри `parse_moxel_chart` показали: разбор останавливается
на версии `75` — в её восьмицветном хвосте семь членов автоматические
(`{4,4,{0},4}`), а **один — стилевой**: `{4,3,{-10},3}`.

Нативный XML печатает его как `<d3p1:chColor>style:FieldBackColor</d3p1:chColor>`
(строка 3090 шаблона). То есть платформа этот цвет **выводит**, а не
отбрасывает.

Две вещи мешают его прочитать:

1. Проверка хвоста версии `75` требует «все восемь автоматические» и иначе
   отказывает всему чертежу.
2. `parse_moxel_chart_color` понимает только 8.3-форму `{3,3,{-10}}`, а
   8.5.1.1529 пишет `{4,3,{-10},3}` — та же ссылка на стиль, другая раскладка
   (пространство 4, вид 3, код, признак).

Дальше: принять стилевые цвета в хвосте (`{4,3,{code},3}` → `style:<имя>` по
той же таблице кодов, что и `{3,3,{code}}`), заполнить `front_colors[4]`
(`chColor`) и проверить, что остальные семь остаются `auto`.
