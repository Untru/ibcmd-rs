# Листья, которые объявляет именованный набор типов

База: `8dcfffd`. Платформа: `/opt/1cv8/8.3.27.2214/ibcmd`.
$D = `/Users/untru/Documents/ChatGPT/ibcmd-stand`.

Продолжение
[`metadata-fill-value-declared-type-20260827.md`](metadata-fill-value-declared-type-20260827.md),
которое закрывает названный там поимённо остаток из пяти файлов ух.

## Что осталось от прошлого пакета

Правило доказано: `{"S",""}` пишется `<FillValue xsi:nil="true"/>`, когда
объявленные листья реквизита ДОКАЗУЕМО исключают строку. Семь файлов из
двенадцати закрылись сразу — у них все листья решаются на месте. Пять
остались, потому что их лист — `ReferenceTypeSet`, то есть ИМЯ набора:

* `DataProcessors/НазначениеПоставщиковНоменклатуреЛота`,
  `InformationRegisters/УсловияПредложенийПоставщиков` — `DefinedType.ЦФО`;
* `DataProcessors/ОтменаИсполненияПлатежныхПозиций` —
  `DefinedType.ДенежнаяСуммаЛюбогоЗнака`;
* `InformationRegisters/ВерсииГрафиковРасчетов` — `DefinedType.ВерсияГрафика`;
* `InformationRegisters/РезультатыКонтроляДокументовПоВидамКонтроля` —
  `Characteristic.ВидыКонтроляДокументов`.

В байтах самого реквизита эти имена неразличимы: `DefinedType.Артикул`
(строка) и `DefinedType.ДенежнаяСуммаЛюбогоЗнака` (число) несут одинаковый
голый `{"Pattern",{"#",<uuid>}}`. Различает их только объявление набора,
и лежит оно в другом объекте метаданных.

## Один индекс, два читателя

`build_defined_type_value_owner_reference_index_from_texts` обходил ровно
те строки и читал ровно те `value_types`, но оставлял только ВЛАДЕЛЬЦЕВ
ссылочных листьев, а сами листья выбрасывал. Индекс переименован в
`build_metadata_type_set_leaf_index_from_texts` и хранит листья; владельцы
выводятся из них там, где нужны. Двух таблиц об одном факте не появилось —
наоборот, из одной таблицы теперь читают оба маршрута: маршрут владельцев
значения измерения регистра сведений и писатель `<FillValue>`.

Индекс покрывает оба вида именованных наборов:

* `cfg:DefinedType.X` — объявленный `<Type>` определяемого типа;
* `cfg:Characteristic.X` — объявленный `<Type>` плана видов характеристик,
  тот самый слот 18 и тот самый разбор шаблона, которыми пользуется
  собственный писатель плана.

## Предшественник читал не тот признак

`row.kind` НИКОГДА не бывает `"DefinedType"`. Определяемый тип — объектный
код `0`, а `metadata_source_for_object_fields` для кода `0` с заголовком в
поле 1 выдаёт `FunctionalOptionsParameter`, `Language` или
`IntegrationService`; определяемый тип держит заголовок в поле 3 и
опознаётся не по `kind`, а тем же способом, каким его опознаёт собственный
писатель — `object_code == Some(0) && is_defined_type_metadata_text(...)`.

Замер это подтверждает: на Документообороте КОРП 3.0.21.3, где 150
определяемых типов, старый предикат давал `defined_type_rows = 0`, то есть
индекс был пуст на КАЖДОЙ конфигурации стенда, а ветка `ReferenceTypeSet`
маршрута владельцев не отвечала ни разу. С правильным предикатом индекс
даёт 153 записи: 150 `cfg:DefinedType.*` и 3 `cfg:Characteristic.*`.

## Разрешение листьев

`metadata_declared_leaves_exclude_string` решает список так: примитив
решается на месте, `Reference` — тоже, а `ReferenceTypeSet` разрешается
через индекс, и на его место подставляются его собственные листья. Имя,
которого индекс не знает (`cfg:AnyIBRef`, безточечные `cfg:*Ref`), и
кольцо имён оставляют список НЕРЕШЁННЫМ, и написание остаётся прежним.
Пустой список тоже не решается. Только решённый список отвечает «строку
исключает» — это по-прежнему fail-closed, как и в прошлом пакете.

## Проводка

Прошлый пакет назвал ценой 231 сигнатуру: параметр вели бы туда же, куда
проведён `object_refs`, — через РАЗБОР. Но решение принимает ПИСАТЕЛЬ, а у
писателя замкнутое множество вызывающих гораздо уже: от
`extract_metadata_source_xml_from_text_row_with_owner_graph_diagnostic`
вниз через одиннадцать `format_*_source_xml` и восемь
`push_*_child_object_xml` — двадцать функций, а не двести тридцать. Индекс
кладётся в `DumpRowContext` рядом с остальными общеконфигурационными
таблицами и оттуда идёт в писателя.

Совместимостные обёртки (`extract_metadata_source_xml*`, которыми
пользуются только тесты) получают пустой индекс: он воспроизводит ровно то
написание, которое эти маршруты давали до чтения листьев.

Заголовочный дочерний объект (`push_metadata_header_child_object_xml`) не
объявляет свойств вовсе, значит не несёт `<FillValue>`, и индекс у него
пустой по построению.
