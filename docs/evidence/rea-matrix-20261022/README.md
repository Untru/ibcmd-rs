# Матрица: бухгалтерия 3.0 (8.5.1.1529)

Вторая конфигурация для проверки общности правил:
`Accounting_3_0_199_13.cf` (750 МБ), база `ibcmd_acc2`, платформа
8.5.1.1529, формат XML 2.21.

## Замер (выгрузка прервалась)

| Показатель | Значение |
|---|---|
| Файлов у нативного | 94 159 |
| Файлов у `ibcmd-rs` | 4 689 |
| Совпали | 4 602 |
| Различаются | 87 |
| Только у нативного | 89 470 |

Нативная выгрузка — 165 с. Наша завершилась с ошибкой на 4 689-м файле:

```
failed to extract spreadsheet template from source asset
Reports\РегламентированныйОтчетБухОтчетностьМП\Templates\

```

То есть выгрузка **останавливается** на шаблоне с неизвестной раскладкой
MOXCEL — это fail-closed, а не молчаливая потеря: 89 470 файлов не записаны
именно из-за этого.

## Вторая находка: заголовки вида `{2,…}`

До остановки модель уступала legacy-конвертеру на строках с заголовком
`{2,{1,0,<uuid>},"Имя",…}`:

```
not an md header: {2,{1,0,<uuid>},"ФормаОтчета2015Кв1_ФормаОтчета",{…
not a Subsystem record: {21,{2,{1,0,<uuid>},"МаршрутыПодписания",…
```

Это не заголовок `{3,…}`, который ожидает общая модель. В бухгалтерии такие
записи есть у форм отчётов и подсистем; в ServiceDesk их не было. Нужно
понять, что это за вариант (вероятно, «заблокированные»/старые объекты) и
научить модель читать его, а не отдавать legacy-конвертеру.

## Прогресс

1. **Языковой дескриптор ревизии 6 починен.** Запись
   `{8,1,6,{"ru","ru",1,1,"ru","Русский","Русский"},…}` хранит язык в короткой
   форме (`count*3+4`) — так же, как ревизии 8 и 9. Условие расширено на
   ревизии `6|8|9`, тест `revisions_8_and_9_read_the_short_language_record`
   дополнен ревизией 6. Выгрузка прошла этот шаблон.
2. **Следующий барьер** — графическая схема:
   `failed to extract graphical scheme from source asset
   Reports\АнализСостоянияНалоговогоУчетаПоУСН\Templates\МакетКарты82\Ext\Template.xml`
   (без подробностей). Выгрузка дошла до 4 713 файлов.

### Графическая схема: что уже сделано

`МакетКарты82` — это 47 декораций (все элементы код `0`), у каждой геометрия
из 12 членов и встроенная картинка. Нативный экспорт рядом с XML пишет
`Ext/Template/Items/Декорация1/Picture.gif` (135 КБ) и
`<Picture><Abs>Picture.gif</Abs></Picture>`.

Исправлено:

- короткая раскладка записи картинки (`{3,3,{0},"",-1,-1,0,{<base64>}}`, 8
  членов вместо 10) — так её пишет 8.5.1.1529;
- формат GIF (`GIF87a`/`GIF89a`) в `flowchart_picture_extension`.

Схема всё ещё отвергается. Точки входа показали другое: элементы доходят до
`parse_flowchart_decoration_graphics`, но payload декорации у этой схемы
**вложен лишним уровнем** — он начинается `{{{7,{3,4,{0}},{3,3,{-22}},…` и
стилевая запись в нём `{7,…}`, а не ожидаемая `{6,…}` с геометрией из 12
членов. Поэтому `outer.len() != 1`/`geometry.len() != 12` и разбор отдаёт
`None`.

Дальше нужно: снять лишний уровень вложенности, разобрать стиль `{7,…}` (это
шрифт/оформление) и сопоставить остальные члены с уже известной геометрией.

|---|---|---|---|

### Раунд 60: почему типы ExchangePlan не регистрируются

Индекс имён строится в `ModelExport::build` по строкам: для каждой строки
`parse_row` → `object_names(kind, tree)` → `index.add(names)`. Строки
ExchangePlan имеют легаси-заголовок `{2,…}`, `parse_row` их не разбирает

  существуют, но только в самом файле, не в индексе;
- регистр, ссылающийся на `ExchangePlanRef.…`, вынужден писать `TypeId`.

Следующий шаг: либо научить `parse_row`/`object_names` легаси-заголовку
`{2,…}` (это же снимает и `not an md header` для сотен объектов), либо
собирать сгенерированные типы из файлов legacy-ветки до построения индекса.

в наборе, видимо, присутствует набор без id).

### Раунд 108: обмен `1 ↔ 2` в правилах root-46

Причина сдвига найдена в таблице правил апгрейда
(`module_blob/form_root_42_rules.rs`):

```
Learned { root: "46", parent: "2", tag: "1", new_tag: "2", … },
Learned { root: "46", parent: "2", tag: "2", new_tag: "1", … },
```

Это правило меняет местами **первый и второй сегмент цепочки** (`parent: "2"` —
запись цепочки, `tag` — её сегмент). Поэтому сырое `{2,{1},{-3}}` после апгрейда
становится `{2,{2},{-3}}`.

Записи реквизитов (`tag: "9"`, другой parent) этим правилом не затрагиваются,
поэтому id реквизита остаётся `1`. Отсюда и расхождение: цепочка ссылается на
«2», а реквизит — «1».

Правка должна быть парной: либо пересчитывать и цепочки, и записи реквизитов,
либо применять правило swap только к формам, где нумерация root-46 действительно
