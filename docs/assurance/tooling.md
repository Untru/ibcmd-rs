# Инструменты разбора (что быстрее REA)

REA-сессии переимпортируют цель на каждый вызов: `mngbase.dll` — около 5
минут на функцию. Для оставшейся работы подготовлено три инструмента,
которые работают без повторного импорта.

## 1. Постоянный проект Ghidra

Создан один раз:

```
analyzeHeadless D:\temp\ghidra-projects mngbase `
  -import "C:\Program Files\1cv8\8.5.1.1529\bin\mngbase.dll" `
  -analysisTimeoutPerFile 1800
```

Импорт занял 285 с, результат сохранён в `D:\temp\ghidra-projects`.

Декомпиляция функции по адресу — без повторного анализа:

```
analyzeHeadless D:\temp\ghidra-projects mngbase `
  -process mngbase.dll -noanalysis `
  -scriptPath tools\rea\ghidra `
  -postScript DecompileAt.java 0x1802ae0c6
```

Скрипт: `tools/rea/ghidra/DecompileAt.java`.

## 2. Извлечение XDTO-пакетов

`tools/rea/extract_xdto_packages.py` вытаскивает все `<package>` из
`*_root.res`: 89 пакетов, 1.7 МБ, без дубликатов. Манифест —
`docs/evidence/platform-xdto-20261022/manifest.json`.

Это самый дешёвый источник фактов о формате: типы, свойства, умолчания,
формы. Для компилятора EDS и MXL он даёт карту допустимого без декомпиляции.

## 3. Матрица паритета

`tools/rea/matrix_parity.py --native <dir> --ours <dir> --out <md>` сравнивает
два дерева по SHA-256 и пишет отчёт: сколько совпало, что различается, чего
не хватает.

Первый прогон на бухгалтерии 3.0: 4 602 из 4 689 записанных файлов совпали,
но выгрузка оборвалась на неизвестной раскладке MOXCEL (см.
`docs/evidence/rea-matrix-20261022`).

## 4. Диф платформенных версий (запланировано)

Почти все последние дефекты — «8.5.1.1529 пишет иначе, чем 8.3.27/8.5.1.1150»
(`{4,3,{code},3}` вместо `{3,3,{code}}`, `{4,4,{0},4}` вместо `{3,4,{0}}`).
Бинарный дифф `mngbase.dll` двух версий покажет такие места пачками; проект
Ghidra для второй версии создаётся тем же способом.

## 5. Динамическая трассировка (опция)

Если понадобится увидеть, какая функция платформы пишет конкретный элемент,
`ibcmd export` можно запустить под WinDbg/x64dbg и поставить точку на
строку-якорь. Это тяжелее и нужно точечно; в текущих задачах хватало
проекта Ghidra и ресурсов.

## 6. Псевдокод вместо угадывания

Где разбор упирается в неочевидную раскладку (легаси-контейнеры, связи
параметров выбора), быстрее перевести декомпилированный код, чем подбирать
правило по данным.

Инструменты:

- `tools/rea/ghidra/FindStringRefs.java` — находит определённые строки,
  содержащие подстроку, и все функции, которые на них ссылаются;
- `tools/rea/ghidra/DecompileAt.java` — псевдокод функции по адресу.

Факт: строки XML-тегов (`ChoiceParameterLinks`) **нет** в `mngbase.dll`; она
лежит в `mngdsgn.dll`, `mngcore.dll`, `backend.dll`, `frntend.dll`, `dcs.dll`,
`dcscore.dll` (UTF-16). Значит писатель форм — `mngdsgn`/`mngcore`, и проект
Ghidra для `mngdsgn` создаётся отдельно.

Порядок: `FindStringRefs.java ChoiceParameterLinks` в проекте `mngdsgn` →
адрес функции → `DecompileAt.java <addr>` → перевод правила в Rust с
проверкой на нативном XML.
