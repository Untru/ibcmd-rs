# F-5 (the live switch and the readiness gate): what was measured on 2026-09-30, and where the work stopped

Worker lab cluster (`docs/apply/worker-lab.md`), marker-free FULL-recovery clone `ibcmd_rs_05_apply_wlab1_20260930` (dropped at the end), the tool at
`feat/0.5-live-worker` (the F-9/F-10 gate included). Lab kit: `scripts/apply-lab/live/` (`obs.ps1`, `build_observer.ps1`, `timeline.ps1`, `marker.ps1`,
`f9_f10.ps1`). The logs were in `F:\ibcmd\lab\05\live\out` (small; the numbers below are copied from them).

## Measured

1. **The gate aborts on an idle cluster, in the old and the new tool.** No user session, no load: every `live` run that got past the gate ended with
   `57234` ("1C SQL connections did not recover ...") after cycle 1 (`f9f10-red.log` and `f9f10-green.log`: `clean`, `sessions`, `accepted`). The gate expects
   back all `1CV83 Server` connections it counted before cycle 1; among them are the two idle ones the working process holds for the infobase (opened by the tool's
   own RAS verification and by the infobase being loaded). An idle process opens no connection until it gets a call, so they never come back.
2. **With two polling thin clients (1 call a second) the whole switch completed** (`mssql-apply-source-change --mode live --interrupt-sessions`, exit 0, tail file with both
   backup sets): the polling calls reconnect the working process within the gate. So the abort is a property of the count, not of load as such.
3. **What each cycle does to sessions** (poll observer = `IbcmdRsObserver.epf`, reads the client-side and the server-side copy of the marker module every second;
   `LIVE-<tag>` is the marker of the promotion):
   - after **cycle 1 only**: a NEW session (COM or a new thin client) sees the new generation on both sides; a WARM poll session is unchanged (both sides old) and
     shows no error -- unless it makes a call while the database is single-user: the thin client then shows the modal "Ошибка СУБД ... native=18456" with
     "Перезапустить / Завершить" (the writer client did, at the first call inside the window), and stops working until it is answered;
   - after **cycle 2**: the warm session's SERVER side moves to the new generation (`client=old server=new`); the client code stays old until the client is restarted
     ("sessions see the new generation after their restart"); the warm client stalled about 12 s around the cycle, without a dialog.
   So the two cycles are what the design said: cycle 1 prepares the generation for new sessions, cycle 2 advances the open ones; the gate between them exists to be
   sure that the working process has reconnected once after cycle 1.
4. **No poke is needed on an idle infobase**: after cycle 1 alone a new COM session already saw the new generation. With no user session there is nothing to wait for.
5. **The writer mode of the observer works**: `40` short transactions (a constant) per tick in 0.8-0.9 s per client.
6. **The BSP "moved or restored" dialog** does not block the observer: it opens as a form beside the observer's own (title `[КОПИЯ]`), buttons "Информационная база
   перемещена" / "Это копия информационной базы"; the observer polls regardless. `obs.ps1` has a generic answer (Enter to the windows of the client after 30 s without a
   journal line), never exercised because the dialog did not block. A real answer would be a UI Automation `Invoke` of "Это копия информационной базы".
7. **A bad end of the day (not understood):** after the completed run (cycle 1, cycle 2) I ran one more cycle 2 by hand within a second, on top of clients still reconnecting;
   afterwards `rac ... session list` and a COM connect did not return, `rmngr` and `rphost` stood still at constant CPU, the database was ONLINE/MULTI_USER with no session.
   The cluster was stopped by killing its processes and purged. Whether three interruptions within seconds hang the working process is open.
8. **The kit's `stop.ps1` calls `rac` without a time limit** (the listing of infobases and sessions before the stop): a hung RAS hangs the stop. Kill the processes
   by hand (`Stop-ClusterProcesses` of `lib.ps1`) or, better, make those `rac` calls bounded. Not done.

## The plan approved by the coordinator (not started in code)

- split the flow: the script does gate + promotion + cycle 1; a Rust-side adaptive readiness phase; cycle 2 as a separate script run, also reachable as a `continue`
  command (`mssql-live-continue`: database ONLINE, the tail file holds exactly one log backup set of the database -- `RESTORE HEADERONLY`; two sets: already complete),
- count USER sessions from RAS (`rac session list` of the infobase, without the tool's own) instead of raw `1CV83 Server` connections: no user session, no wait; the
  sessions that made a call in the last seconds before the cycle (`last-active-at`) are "warm" and are waited for until they have made a call after the window; idle ones
  are not waited for,
- a progress-based wait (a new call or connection extends the deadline) with a configurable ceiling; on a timeout: the promotion and cycle 1 are done, cycle 2 is not,
  the error says so and names `continue`,
- the `rac infobase info` poke only if it is measured to be needed (item 4: not for an idle infobase),
- every `rac` call bounded in time.

## Acceptance still to be shown (coordinator)

on the idle cluster `live` completes; under the writer load 5 of 5 runs complete, or the refusals are clean, with nothing half-done and `continue` finishing the job;
sessions see the new generation after their restart; the native export of our result equals the native apply's (twin: `mssql-stage-source-objects` +
`mssql-activate-staged-main --mode live` on a copy, the platform's `config apply` on a byte-equal copy of the staged state, `source-diff` of the two exports).
