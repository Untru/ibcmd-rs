# Команды ibcmd-rs

Справочник по командам текущих исходников `master`. Проект в стадии активной доработки:
рабочим для повседневного использования он станет к версии 1.0, ход работ —
в [майлстоунах](https://github.com/Untru/ibcmd-rs/milestones). Команды,
которые пишут в базу, запускайте только на копиях баз.

**Доступность в выпусках.** `cf bootstrap --base-free` добавлен в исходники
`master` после [PR #422](https://github.com/Untru/ibcmd-rs/pull/422) (#351).
Для этого режима нужна сборка соответствующего checkout исходников.
В опубликованных архивах [v0.4.0](https://github.com/Untru/ibcmd-rs/releases/tag/v0.4.0)
у `cf bootstrap` такого ключа нет; описание режима ниже не относится к этим архивам.
Независимая сборка расширений `.cfe` с этим ключом и без него также
описывает текущие исходники, а не выпущенный v0.4.0.

Утилитой можно пользоваться двумя способами:

1. **[Синтаксис штатного `ibcmd`](#1-синтаксис-штатного-ibcmd)**:
   `ibcmd infobase config export|import|apply|save`. Это основной способ:
   утилита подменяет `ibcmd.exe` для выгрузки, загрузки и применения
   конфигурации и для её сохранения в файл `.cf`.
2. **[Собственные команды `ibcmd-rs`](#3-основные-команды-ibcmd-rs)**: те же
   выгрузка и загрузка с подробными параметрами, сравнение выгрузок, а также
   [исследовательские команды](#4-остальные-команды).

Полный список параметров любой команды печатает сама утилита:
`ibcmd-rs <команда> --help` (у синтаксиса `ibcmd` справка на русском:
`ibcmd infobase --help`).

## 1. Синтаксис штатного `ibcmd`

Скопируйте `ibcmd-rs.exe` под именем `ibcmd.exe` в отдельную папку, и
выгрузка, загрузка, применение конфигурации и её сохранение в файл `.cf`
запускаются теми же командами, что у штатного `ibcmd`. Штатный `ibcmd.exe`
платформы не удаляйте: `infobase create` и применение, которому нужна
реструктуризация вне [перечня S1](#применение-конфигурации), выполняет он.

### Выгрузка конфигурации в XML

```
ibcmd infobase config export [параметры] <каталог>
```

Каталог должен быть пустым или отсутствовать, как у штатного `ibcmd`;
выгрузка с `--base` или `--sync` обновляет каталог с предыдущей выгрузкой
([ниже](#инкрементальная-выгрузка---base---sync)).

Выгружается основная конфигурация, как у штатного `ibcmd`: если после загрузки
(`infobase config import`) в ConfigSave лежит законченная подготовка —
строка `versions` без маркеров `commit` и строк `*.new`, — объекты, для которых
в ConfigSave есть строки, выгружаются из них, остальные из Config, а
`ConfigDumpInfo.xml` строится по `versions` подготовки. Пока подготовка не
применена (`infobase config apply` очищает ConfigSave), выгрузка отличается от
содержимого Config. Без законченной подготовки выгружается Config, и об этом
сказано в стандартном потоке ошибок. Строки, которых нет в `versions`
(остатки удалённых онлайн-обновлением объектов и модулей), в выгрузку не
попадают.

### Загрузка XML в базу

```
ibcmd infobase config import [параметры] <каталог>
```

Загрузка записывает конфигурацию в таблицу ConfigSave; применяет её
`ibcmd infobase config apply` (ниже) или штатный. Если в базе нет
конфигурации этого дерева (база только что создана `ibcmd infobase create`),
каждая строка собирается из XML, отдельного ключа не нужно.

### Применение конфигурации

```
ibcmd infobase config apply [--force] [--dynamic=<режим>] [--session-terminate=<режим>] [параметры]
```

Переносит загруженную конфигурацию (ConfigSave) в действующую (Config)
монопольно, одной транзакцией: при сбое база остаётся как была. Судья
реструктуризации всегда один: проверка `mssql-apply-check`, а за ней
собственная реструктуризация S1 (`--allow-restructure s1` у
`mssql-config-apply`; здесь параметра нет, согласие даёт резервная копия).

- **Не нужна реструктуризация** (изменены модули, формы, макеты, картинки,
  справка любых объектов, безвредные свойства описаний, добавлены формы и
  макеты существующих объектов, удалены формы, макеты или модули):
  применяется, резервная копия не нужна. Удаление формы или макета убирает
  и записи о нём в служебных строках Params.
- **Нужна реструктуризация из перечня S1** на справочниках и документах
  (добавить, удалить реквизит, увеличить длину строки, переключить
  индексирование реквизита, добавить табличную часть, реквизит табличной
  части, справочник или документ): применяется в той же транзакции, но только с
  `--recovery-backup=<файл>` или `--i-have-a-backup`. Без них ответ по-русски
  называет оба параметра, код 1, база не тронута.
- **Нужна другая реструктуризация** (или нужно что-то, чего это применение не
  делает): ничего не меняет и отвечает `требуется штатный config apply:
  <причины>` с кодом 1: выполните штатный `ibcmd infobase config apply`.

Проверить заранее, не применяя: `ibcmd-rs mssql-apply-check --database <база>`
(`--s1` покажет, что из этого сделает S1).

| Параметр | Как обрабатывается |
|---|---|
| `--dynamic=auto` (по умолчанию), `disable`, `prompt` | Выполняются одинаково: монопольное применение. Штатный `ibcmd`, запущенный на базе (`--dbms=...`), тоже не спрашивает и не обновляет динамически, когда ничто не мешает монопольной блокировке. Если сеансы мешают, отказ (см. ниже) остаётся отказом и в динамическое обновление не превращается; для `auto` и `prompt` он заканчивается строкой `можно применить динамически: --dynamic=force`, когда конфигурация подошла бы. |
| `--dynamic=force` | Динамическое обновление небольшой конфигурации (строки нескольких общих модулей и общих форм и служебные строки, не более 128 строк): поколение публикуется рядом с действующим, сеансы не отключаются, монопольный доступ не нужен; следующее монопольное применение сворачивает поколения. Остальное не применяется: `требуется штатный config apply: <причины>`, код 1. Загрузка `ibcmd infobase config import` этой утилиты подходит (она загружает только изменённые строки), если в базе нет невыполненного динамического обновления; если оно есть, загрузка перечисляет его строки в `deleted`, и такую загрузку применяет только монопольное применение. Только платформа 8.3.27.2214. [docs/apply/dropin-dynamic.md](apply/dropin-dynamic.md) |
| `--force`, `-F` | Принимается: предупреждений, которые нужно подтверждать, это применение не выдаёт. |
| `--session-terminate=disable` (по умолчанию) | Если к базе подключены другие сеансы, отказ в словах штатного `ibcmd` (`Ошибка исключительной блокировки информационной базы.` и список соединений), код −1. Эта проверка строже штатной: штатный `ibcmd`, запущенный на базе, сеансов не видит и применяет, а в режиме `--pid`/`--remote` отменяет применение с предупреждением и кодом 0. Скрипт не должен принять «не применено» за успех. |
| `--session-terminate=force`, `prompt` | Пока никого нет, принимаются. Если сеансы есть, отказ (код 1): ibcmd-rs сеансы не завершает. |
| `--session-terminate-message` | Принимается, не используется. |
| `--extension`, `-e` | SQL-расширение: монопольное применение на точных 8.3.27.2214 и 8.5.1.1150. Нужны параметры привязки RAS; см. [маршрут расширений](extensions/parity.md#sql-extension-import-and-apply-on-exact-builds). |
| `--pid`, `--remote` | Не поддерживаются (код 1). |
| `--sqlcmd` | Для основной конфигурации не поддерживается (код 1). |
| `--recovery-backup=<файл>` | Только у `ibcmd-rs`. Согласие на реструктуризацию S1 и путь назад: перед транзакцией применение делает `BACKUP DATABASE ... WITH COPY_ONLY, COMPRESSION` в этот файл (путь, куда может писать служба SQL Server; файл не должен существовать, иначе код −1 до записи) и называет его в отчёте. Для загрузки без реструктуризации не нужен. |
| `--i-have-a-backup` | Только у `ibcmd-rs`. То же согласие, но копию делаете вы; записывается в отчёте. Если указаны оба параметра, действует файл. |
| `--exclusivity=<sql\|assumed>` | Только у `ibcmd-rs`. `sql` (по умолчанию): сеансы смотрит SQL Server, нужно право `VIEW SERVER STATE`; `assumed`: сеансы не проверяются, берите его, когда у логина СУБД нет этого права или соединение держит лишь пул рабочего процесса, а пользователей в базе нет. |

Рассчитано на загрузку `ibcmd infobase config import` этой утилиты; загрузка
штатного `ibcmd` принимается, только если проверка разобрала каждую её строку,
иначе код 1. Платформа 8.5: применение без реструктуризации работает (новые
формы и макеты на 8.5 отклоняются), реструктуризация S1 проверена на БСП 8.5 так же, как на 8.3.27 (`--platform=8.5.1`) и на ERP УХ 8.3.27 (таблицы пусты).
Коды: 0 применено или нечего применять; 1 «требуется штатный config apply» (или
`config repair`), отказ без резервной копии, не поддерживаемый параметр; 2
ошибка командной строки; −1 сбой (другие сеансы, нет права `VIEW SERVER STATE`,
ошибка SQL Server). Подробности, сообщения и измерения штатной команды:
[docs/apply/dropin-apply.md](apply/dropin-apply.md); раздел
[README «Применение конфигурации»](../README.md#применение-конфигурации).

Если конфигурация в базе уже есть, загрузка берёт строки базы и правит их по
дереву, а то, что в дереве отличается от базы, собирает из дерева: реквизиты,
табличные части, значения перечислений, свойства объектов, состав подсистем
(и вложенных), свойства конфигурации, новые объекты (справочник, форма,
макет), предопределённые элементы. Объекты, которых в дереве больше нет
(форма, макет, объект целиком), она перечисляет в строке `deleted`, как
штатная загрузка, вместе со строками ещё не применённого динамического
обновления. Строки, которые дерево не меняло, остаются строками базы, со
всем, чего в XML нет (счётчики схем бизнес-процессов, признак «использовать
всегда» у констант). Строки записываются с датами платформы (на 2000 лет
вперёд), строка больше 10 000 000 байт - частями, как у штатной загрузки.
Что меняется, определяет сравнение дерева с описаниями объектов базы
(`mssql-apply-check --tree`); подробности: `docs/import/override.md`.

Чтобы загрузка не теряла изменения молча, перед записью в ConfigSave утилита
выгружает моделью конфигурацию, какой она станет после загрузки, и сравнивает
каждый файл с деревом (XML по элементам, а не по пробелам; модули без учёта
концов строк). Расхождение отменяет загрузку: код возврата -1, в сообщении
перечислены файлы и что в них не совпало, ConfigSave остаётся таким, каким
был. Проверка добавляет к загрузке выгрузку конфигурации в памяти (БСП:
десятки секунд; ERP УХ: около двух минут). Так же
проверяется загрузка, собранная из XML (`--base-free`, пустая база): на неё
проверка добавляет только выгрузку. `--no-verify` пропускает проверку.

Загрузка отменяется до записи в ConfigSave (код -1), если дерево неполное (на
объект ссылаются, а файла нет) или объект не удаётся собрать из дерева:
сообщение по-русски называет каждый такой объект и причину. Удаление
отдельного файла объекта, который остаётся (модуль, картинка), пока не
переносится: проверка это видит и отменяет загрузку.

### Загрузка отдельных файлов (`import files`)

```
ibcmd infobase config import files --base-dir=<каталог> [--partial] [--no-check] [параметры] <файл> ...
```

Загружает только перечисленные файлы, например изменённые по `git diff`:
пути файлов указываются относительно `--base-dir`. В ConfigSave
записываются строки, которые собираются из этих файлов, и служебные `root`,
`version`, `versions`; остальные строки конфигурации остаются такими, какие
они в базе. Так же поступает штатная загрузка: `import files --partial` одного
описания справочника записывает четыре строки (описание, `root`, `version`,
`versions`). Применяет загруженное `ibcmd infobase config apply`, как после
обычной загрузки.

Каждый файл относится к объекту, которому принадлежит: файл описания
(`Catalogs/Товары.xml`) — к самому объекту, файл из его каталога — к
ближайшему объекту выше (`Catalogs/Товары/Ext/ObjectModule.bsl` — к
`Catalogs/Товары.xml`, `Catalogs/Товары/Forms/ФормаЭлемента/Ext/Form/Module.bsl`
— к форме `Catalogs/Товары/Forms/ФормаЭлемента.xml`), файлы корневого `Ext` —
к конфигурации. Что записывается:

- файл описания объекта загружает объект целиком, как штатная загрузка: его
  описание и все его файлы, которые есть в каталоге, вместе с вложенными
  объектами (`Catalogs/Валюты.xml` — модули, справку и формы справочника;
  правка неперечисленного модуля тоже попадает в загрузку);
- модуль, форма (`Form.xml` или `Form/Module.bsl`), макет, справка, права
  роли, предопределённые данные и другие файлы `Ext` — строка, которая из них
  собирается. Описание объекта при этом остаётся строкой базы (штатная
  загрузка перезаписывает его теми же байтами).

Как ведёт себя штатный `ibcmd` 8.5.1.1529 в каждом случае, записано в
[docs/import/import-files.md](import/import-files.md).

Объект собирается из строк базы и файлов каталога, поэтому:

| Параметр, условие | Как обрабатывается |
|---|---|
| `--base-dir=<каталог>` | Обязателен. Файл вне каталога (в том числе через `..`) не загружается, код −1. |
| `--partial` | «Разрешить частичный набор файлов объектов метаданных». Файл из списка, которого нет в каталоге, пропускается (если не осталось ни одного — успех, ConfigSave не меняется); тела объекта, загружаемого целиком, которых нет в каталоге, остаются строками базы. Без `--partial` штатный `ibcmd` такие строки удаляет; ibcmd-rs удалять не умеет и отказывает (код 1), если в базе есть такое тело. Каталог может быть неполным и без `--partial`; достаточно перечисленных файлов и файлов описания их объектов (для модуля формы — `Forms/<форма>.xml`, сам `Form.xml` не нужен). |
| `--no-check` | Не проверять перед записью. По умолчанию, как у обычной загрузки, утилита выгружает моделью конфигурацию, какой она станет, и сравнивает с каталогом перечисленные файлы (только их); расхождение отменяет загрузку, код −1. `--no-verify` ibcmd-rs делает то же, `--verify` подтверждает проверку. |
| файла нет в каталоге | С `--partial` пропускается, как у штатного `ibcmd`. Без него отказ, код 1: штатный удалил бы строку файла, удаление частичной загрузкой пока не переносится. |
| в ConfigSave уже есть подготовленная загрузка | Отказ, код 1: штатный `ibcmd` добавляет к ней загружаемые файлы, а ibcmd-rs записывает ConfigSave заново. Примените загрузку (`config apply`) или загрузите каталог целиком. |
| `Configuration.xml` в списке | Отказ, код 1: штатный `ibcmd` в этом случае загружает конфигурацию целиком; загрузите каталог командой `infobase config import`. |
| новый объект (его нет в базе) | Отказ, код 1: для него нужен `Configuration.xml`. |
| нет файла описания объекта или файл не относится ни к одному объекту (`ConfigDumpInfo.xml`) | Отказ, код 1, до подключения к базе. |
| из файла не собирается ни одна строка | Отказ, код 1, ConfigSave не меняется. |
| `--base-free`, `--out`, `--extension` | Не поддерживаются (код 1). |

Сообщения — как у штатного `ibcmd`: `[INFO] Импорт файлов конфигурации из
XML...`, `[INFO] Импорт файлов конфигурации из XML успешно завершен`, при
ошибке строки `[ERROR] Загрузка невозможна: …` и `[ERROR] Импорт файлов
конфигурации из XML завершен с ошибкой`. Смысл параметров снят со штатного
`ibcmd` 8.5.1.1529 ([docs/import/import-files.md](import/import-files.md)).
Проверено без базы: тест `tests/import_files.rs` загружает правку модуля и
описания из `.cf` платформы (`--script-only` по строкам из каталога, см.
`mssql-stage-source-objects --file`) и выгружает результат. На SQL Server
(БСП 8.5, две базы из одного `.cf`) выгрузка того, что подготовили штатный
`import files` и ibcmd-rs, совпадает во всех 9 156 файлах для модуля и для
описания справочника.

### Сохранение конфигурации в файл .cf

```
ibcmd infobase config save [--db] [параметры] <файл.cf>
```

Строки конфигурации записываются в файл как есть, без XML: каждая строка
таблицы становится элементом контейнера с теми же сжатыми байтами, строка,
которую база хранит частями (`PartNo`), — одним элементом. Без `--db`
сохраняется основная конфигурация, та же, что выгружает `infobase config
export`: законченная подготовка из ConfigSave поверх Config (тогда в файл
попадает и её строка `deleted`), а без подготовки — Config. С `--db` —
конфигурация базы данных, только таблица Config. Строки онлайн-обновления
(`_dynupdate_`) сохраняются под своими обычными именами, служебная строка
`DynamicallyUpdated` в файл не попадает.

Файл — контейнер Format15 того же вида, что пишет `cf bootstrap --base-free`
в сборке исходников после #422 ([доступность команды](#файлы-cf-и-конвертация))
(такой файл штатная платформа 8.3.27 загружает): элементы по порядку имён,
страницы по 512 байт, в заголовке файла число элементов, в заголовках
элементов нет времени. Штатная платформа раскладывает свой файл иначе (у
конфигурации в режиме совместимости 8.3.18 и новее — Format16 за своей
преамбулой, в режиме 8.3.10 — Format15; время сохранения в заголовках
элементов, свой порядок и размер страниц), поэтому файлы побайтно не
совпадают, а содержимое совпадает: `cf export` обоих даёт одно и
то же дерево файл в файл. Что именно различается:
[evidence/cf-config-save.md](evidence/cf-config-save.md).

Существующий файл заменяется, когда новый записан и проверен (прочитан
заново и сверен поэлементно); до этого старый файл остаётся целым. Отказ с
кодом −1 и сообщением, если в таблице Config остались строки незавершённой
операции (`commit`, `deleted`, `*.new` и подобные: сначала выполните `ibcmd
infobase config repair`), если в конфигурации нет строки `root`, `version` или
`versions`, если строка не является целым потоком raw deflate.

Штатной платформой пока не проверены загрузка сохранённого файла (`config
load`) и совпадение её выгрузки с выгрузкой исходной базы. Сохранение
расширения (`--extension`) не поддерживается (код 1).

### Загрузка конфигурации из файла .cf

```
ibcmd infobase config load [параметры] <файл.cf>
```

Элементы файла записываются как есть в подготовку загрузки (ConfigSave):
по строке на элемент, с теми же сжатыми байтами, плюс строка `deleted` со
списком строк Config, которых в файле нет. Применяет загрузку штатный
`config apply`. Работает для файловой базы (`--db-path`), PostgreSQL и
SQL Server. Проверено на SQL Server 2025: `.cf` БСП, загруженный поверх
маленькой конфигурации и применённый штатным `config apply` 8.5.1, штатный
`config export` выгружает тождественно исходникам БСП.

### Подключение к базе

| Параметр | Что задаёт |
|---|---|
| `--db-path=<каталог>`, `--database-path` | Файловая информационная база: каталог с `1Cv8.1CD` (или сам файл). Для `config export`, `config import`, `config save` и `config load`; вместе с `--dbms`, `--db-server`, `--db-name` не указывается. См. [Файловые базы](#файловые-базы). |
| `--dbms=MSSQLServer` | Тип СУБД: `MSSQLServer`; для `config export`, `config import` и `config load` также `PostgreSQL` (см. [PostgreSQL](#postgresql)). |
| `--db-server=<сервер>`, `--database-server` | Сервер: `server`, `server\instance`, `server/instance` (как пишет штатный `ibcmd`), `server,port`. По умолчанию — из настроек, иначе `localhost`. |
| `--db-name=<база>`, `--database-name` | Имя базы данных. |
| `--db-user=<логин>`, `--database-user` | Логин SQL Server. Без него — вход Windows. |
| `--db-pwd=<пароль>`, `--database-password` | Пароль логина SQL Server. |
| `-W`, `--request-db-pwd`, `--request-database-password` | Прочитать пароль из стандартного ввода (первая строка). |
| `-c <файл>`, `--config=<файл>` | Файл настроек штатного `ibcmd` (YAML, который пишет `ibcmd server config init`). Из его раздела `database:` берутся СУБД, сервер, база, логин и пароль, не заданные параметрами. |
| `--data=<каталог>`, `-d` | Каталог данных сервера; загрузка оставляет служебные файлы в его подкаталоге `temp`. |
| `--temp=<каталог>`, `-t` | Каталог временных файлов. |
| `--user`, `-u`, `--password`, `-P` | Пользователь информационной базы. Принимаются и не нужны: утилита работает с таблицами напрямую. |
| `--system`, `--lock`, `--users-data`, `--session-data` и другие `--*-data` | Принимаются для совместимости и не используются. |

Оба написания имён (`--db-server` и `--database-server`) и обе формы значения
(`--x=значение` и `--x значение`) равноправны.

### PostgreSQL

`config export`, `config import` и `config load` работают с базой на PostgreSQL через свой
клиент, без платформы и без библиотек PostgreSQL:

```
ibcmd infobase config export --dbms=PostgreSQL --db-server=pg01 --db-name=demo --db-user=postgres /srv/export/demo
ibcmd infobase config import --dbms=PostgreSQL --db-server=pg01 --db-name=demo --db-user=postgres /srv/export/demo
```

- `--db-server`: `host`, `host:port` или `host port=N` (порт по умолчанию 5432).
- Пароль (`--db-pwd`, `IBCMD_DB_PSW`) нужен, только если его спрашивает сервер:
  поддерживаются вход без пароля, cleartext, MD5 и SCRAM-SHA-256. TLS нет.
- Выгружается таблица `config` с законченной подготовкой из `configsave`,
  как для SQL Server.
- Загрузка подготавливает в `configsave` всю конфигурацию, как штатная
  загрузка: строки, собранные из XML, или строки базы с перенесёнными
  правками дерева, и строку `deleted`. Запись идёт одной транзакцией.
  Сеансы базы при этом не проверяются и база не блокируется: подготовка
  строится по `config` до записи в `configsave`, поэтому на время загрузки
  с базой никто не должен работать и никакая другая операция с
  конфигурацией (загрузка, применение, обновление) не должна выполняться.
  Применяет загрузку штатный `ibcmd infobase config apply`. Перед записью
  подготовка проверяется выгрузкой (`--no-verify` отключает проверку).
- `--base`/`--sync` работают, как для SQL Server. Расширения, `import files`
  и остальные команды на PostgreSQL не поддерживаются. Формат и замеры:
  [docs/evidence/postgres-storage-20261022.md](evidence/postgres-storage-20261022.md).

### Файловые базы

`--db-path` указывает файловую базу формата 8.3.8 (`1Cv8.1CD`): платформа и
сервер СУБД не нужны.

```
ibcmd infobase config export --db-path=/srv/ib/demo /srv/export/demo
ibcmd infobase config export --db-path=/srv/ib/demo --extension=МоёРасширение /srv/export/extension
ibcmd infobase config import --db-path=/srv/ib/demo /srv/export/demo
ibcmd infobase config save --db-path=/srv/ib/demo /srv/export/demo.cf
```

- **Сохранение в .cf** (`config save`) пишет строки, которые публикует
  выгрузка: `CONFIG` с законченной подготовкой из `CONFIGSAVE`; с `--db` —
  один `CONFIG`. Базу не изменяет.

- **Выгрузка** читает таблицу `CONFIG`, а законченную подготовку загрузки в
  `CONFIGSAVE` публикует вместо строк с теми же именами — как для SQL Server.
  Открытую платформой базу выгружать можно (проверено в Linux; в Windows
  база открывается без разделения записи, и открытая платформой база не
  выгружается).
- **Загрузка** записывает в `CONFIGSAVE` всю конфигурацию, как штатная
  загрузка в файловую базу: собранную из XML, если в `CONFIG` нет этой
  конфигурации, иначе — строки базы с перенесёнными правками дерева (как `cf
  load`), и строку `deleted` с исчезнувшими строками. Применяет загрузку
  штатный `ibcmd infobase config apply`. Перед записью конфигурация
  проверяется выгрузкой (ключ `--no-verify` отключает проверку).
- База должна быть закрыта: открытую платформой или сервером `ibsrv` базу
  загрузка не трогает и сразу отказывает. Пока идёт загрузка (от чтения базы
  до записи), платформа базу не откроет. Запись идёт в копию файла; на Unix
  сохраняются права, владелец и группа. На Windows данные копируются только
  при совпадении владельца, группы и списка разрешений DACL; различие
  останавливает запись до копирования. SACL и метки безопасности эта проверка
  не охватывает. Прежний файл остаётся рядом как
  `1Cv8.1CD.ibcmd-rs.bak` (хранится одна, последняя копия). Остатки
  `1Cv8.1CD.ibcmd-rs.tmp` или `1Cv8.1CD.ibcmd-rs.bak.new` останавливают
  следующую загрузку. Не удаляйте их вслепую: остановите работающую запись,
  проверьте identity каталога и файлов и сохраните нужные поколения для
  восстановления. Если публикация базы прошла, а обновление backup завершилось
  ошибкой, новая база уже записана, прежний `.bak` сохранён, а `.bak.new`
  содержит базу до записи; ошибка требует проверки восстановления до повтора,
  а не означает отмену или отсутствие изменений. Если сохранить владельца
  и права нельзя, загрузка отказывает.
- Загрузка пишет базы с локалью `en_US_POSIX` и `ru_RU` (так их создаёт
  `ibcmd infobase create` в английском и русском окружении): ключи индекса
  зависят от локали, другие не измерены, и такую базу загрузка не трогает.
  Выгрузка работает с любой локалью.
- База с незавершённым динамическим обновлением (строки `*_dynupdate_*` в
  `CONFIG`) не загружается: ключ индекса таких имён не измерен. Завершите
  обновление штатной платформой.
- Имена строк вне проверенного набора символов (`0-9 A-Z a-z - . / _`, длина
  до 43) загрузка не пишет, а отказывает: ключ индекса таких имён не измерен.
- **Расширение** выгружается по имени через `--extension`: измерен профиль
  8.3.27.2214 / XML 2.20. Читается активный CAS-образ или подготовленная
  стадия выбранного расширения; остальные расширения в дерево не попадают.
  Платформа не запускается, база не меняется. Неизвестный профиль реестра,
  повреждённый CAS, неполная стадия и next-generation реестр отклоняются до
  публикации результата. `--base`, `--sync` и экспорт всех расширений этим
  маршрутом не поддерживаются.
- Применение, сохранение (`config save`), `import files` и загрузку расширений
  файловой базы пока выполняет штатный `ibcmd` (ibcmd-rs отказывает с кодом 1).
- Версию платформы файловой базы можно задать в настройках записью базы без
  сервера, где имя — маска пути к каталогу базы.

**Вход SQL Server.** Без `--db-user` утилита входит от имени пользователя
Windows. Для логина SQL Server:

```
ibcmd infobase config export --dbms=MSSQLServer --db-server=sql01 ^
  --db-name=MyBase --db-user=sa --db-pwd=Secret C:\export\MyBase
```

Чтобы пароль не попадал в историю команд, вместо `--db-pwd` задайте его:
- переменной окружения `IBCMD_DB_PSW`;
- через стандартный ввод с `-W`: `echo Secret| ibcmd ... -W C:\export\MyBase`;
- в разделе `database:` файла `--config`.

Если логин указан, а пароля нет нигде, утилита отказывает с подсказкой.

Полная запись файловой базы поддерживается на Unix и Windows. На Unix
временный файл, резервные копии, публикация и очистка привязаны к дескриптору
родительского каталога. На Windows открытые дескрипторы предков блокируют их
переименование и удаление; reparse points отклоняются, идентичность файла
проверяется по открытому дескриптору. Частичная загрузка `import files` пока
требует Unix. Другие ОС отказывают до записи; выгрузка остаётся доступной.
Замена предка после проверки не перенаправляет операции в подставной каталог.
На Unix advisory lock не защищает от процесса того же UID, меняющего
конечные имена файлов без соблюдения блокировки:
проверка identity и rename не являются одной операцией filesystem CAS.
После переименования предка путь в отчёте/recovery error может устареть;
восстановление должно проверить identity каталога и файлов, а не доверять
новому содержимому прежнего абсолютного пути.

### Параметры выгрузки

| Параметр | Что задаёт |
|---|---|
| `--extension=<имя>`, `-e <имя>` | Выгрузить расширение конфигурации с этим именем, а не конфигурацию. Дерево такое же, как у штатного `ibcmd`: выгружается подготовленное к применению состояние расширения, если оно есть, иначе применённое. Неизвестное имя и расширение, которое не удаётся записать точно, дают ошибку. Как и конфигурация, расширение пишется только в пустой каталог. Проверено на четырёх расширениях БСП 8.3.27 и расширениях БСП 8.5 (см. [extensions/parity.md](extensions/parity.md)). |
| `--threads=<n>`, `-T <n>` | Число потоков выгрузки: по умолчанию — число ядер, но не больше 16; явно — до 64. |
| `--force` | Принимается. Непустой каталог, как и у штатного `ibcmd`, не перезаписывается (кроме выгрузки с `--base` или `--sync`). |
| `--ignore-unresolved-refs` | Принимается для совместимости. |
| `--base=<файл>`, `-b <файл>` | Только изменённые/новые строки и ConfigDumpInfo. При отсутствии изменений ничего не записывается; удаление/переименование требует полной выгрузки (rc255). |
| `--sync` | Обновить существующую выгрузку по её ConfigDumpInfo. Удаление/переименование требует полной выгрузки (rc255). Вместе с `--base` не допускается (rc2). |

### Инкрементальная выгрузка custom API (`--base`, `--sync`)

```
ibcmd-rs infobase-config-export --dbms=MSSQLServer --db-server=sql01 --db-name=MyBase ^
  --base=C:\export\MyBase\ConfigDumpInfo.xml --sync C:\export\MyBase
```

Следующие правила сохраняют контракт custom API `infobase-config-export` и
`mssql-dump-config`. Native CLI отличается: см. Native export queries (#362)
ниже. Что изменилось, утилита определяет по версиям строк конфигурации: строка `versions` таблицы Config хранит версию
каждой строки конфигурации, а `ConfigDumpInfo.xml` выгрузки перечисляет их
(`<Metadata name="…" id="…" configVersion="…">`; вложенные `<Metadata>` —
реквизиты и команды объекта — отдельных версий не имеют).

- **`--base`.** Строка, которую файл перечисляет с той же версией и тем же
  именем, не конвертируется, и ни один её файл не записывается. Остальные
  строки (изменённые, новые и не перечисленные в `ConfigDumpInfo.xml`, например
  тела родительских конфигураций поставки) выгружаются так же, как полной
  выгрузкой, а `ConfigDumpInfo.xml` записывается для всей конфигурации. Если
  со времени `--base` переименован объект или его часть (реквизит, табличная
  часть, команда — всё, что перечисляет `ConfigDumpInfo.xml`), выгружается вся
  конфигурация: строки ссылаются на объект по идентификатору, поэтому версии
  строк объектов, которые называют переименованный (`Configuration.xml`,
  состав подсистем, формы), могут не измениться, а их файлы меняются. Так же —
  если `ConfigDumpInfo.xml` записан в другом формате XML (2.20 против 2.21).
  Файл `--base` может быть `ConfigDumpInfo.xml` самого каталога: он читается
  до выгрузки.
- **`--sync`.** После выгрузки из каталога удаляются файлы, которых нет в
  полной выгрузке: файлы удалённых объектов, файлы под старым именем
  переименованного объекта, файлы, которых изменённый объект больше не даёт
  (удалённый модуль формы), и посторонние файлы в каталогах объектов
  метаданных. Затрагиваются только `Configuration.xml`, `ConfigDumpInfo.xml`,
  `Ext\` и каталоги видов объектов (`Catalogs\`, `Documents\`, …); каталоги
  и файлы с точкой в начале имени (`.git`) и всё прочее в корне каталога
  (`README.md`) не трогаются. В каталоге неизменённого объекта файл, который
  не принадлежит ни одной строке `ConfigDumpInfo.xml`, остаётся: по версиям
  его не отличить.
- **`--base` и `--sync` вместе** — обновление выгрузки после каждого изменения:
  каталог совпадает с полной выгрузкой, а записываются только изменённые
  объекты. Без `--base` (`--sync` один) выгружается вся конфигурация, и
  каталог становится полной выгрузкой.

Имя, которого `ConfigDumpInfo.xml` не перечисляет (предопределённый элемент,
названный в файле другого объекта), может измениться без смены версии этого
объекта; такой файл остаётся прежним до полной выгрузки (без `--base`).
Расширение (`--extension`) выгружается только полностью: `--base` и `--sync` с ним
отклоняются (код 1). Отчёт `--report` содержит раздел `incremental`: сколько
записей изменено и не изменено, сколько файлов записано и какие удалены.

| `--source-version=<2.20\|2.21>` | Прежнее указание формата XML; вместо него — `--platform`. |

### Что пока не поддерживается

Остальные команды и режимы штатного `ibcmd` разбираются и отвечают
сообщением «… не поддерживается в этой версии ibcmd-rs (планируется в
следующих)» с кодом 1; штатный `ibcmd` вместо них не запускается:

- режимы `server`, `eventlog`, `config`, `extension`, `mobile-app`,
  `mobile-client`, `session`, `lock`, `binary-data-storage`;
- команды `infobase create`, `dump`, `restore`, `clear`, `replicate`;
- `infobase config check`, `reset`, `repair`,
  `support`, `data-separation`, `extension`, `generation-id`, `sign`;
- `infobase config export all-extensions` и
  `infobase config import all-extensions`;
- параметры выгрузки `--file`, `--archive`, а также `--base` и `--sync`
  вместе с `--extension`; загрузки `--out`; `--extension` у
  `import files` и `config load`; применения основной конфигурации
  с `--sqlcmd`; сохранения `--extension`;
  общие `--pid`, `--remote`;
- применение и загрузка расширений файловых баз (`--db-path`);
  частичная загрузка `import files` из файловой базы на Windows;
  СУБД кроме `MSSQLServer` и `PostgreSQL` (у PostgreSQL поддержаны
  `config export`, `config import` и `config load`).

### Вывод и коды возврата

При успехе утилита печатает то же, что штатный `ibcmd`:

```
[INFO] Экспорт конфигурации в XML...
[INFO] Экспорт конфигурации в XML успешно завершен
```

При ошибке — строки `[ERROR] …` в stderr, последняя
`[ERROR] … завершен с ошибкой`. У применения:

```
[INFO] Обновление конфигурации базы данных...
[INFO] Создано поколение конфигурации: <поколение>
[INFO] Обновление конфигурации базы данных успешно завершено
```

Если применять нечего — `[INFO] Обновление конфигурации базы данных не
требуется` (код 0). Отказ «нужен штатный config apply» — одна строка
`[ERROR] требуется штатный config apply: …` и код 1. У сохранения в файл
(строки штатного `config save` не измерены, заголовок — название команды из
`ibcmd help infobase`):

```
[INFO] Выгрузка конфигурации...
[INFO] Выгрузка конфигурации успешно завершена
```

| Код | Когда |
|---|---|
| 0 | успех |
| 2 | ошибка в командной строке: неизвестный параметр, нет значения, неполная команда, неизвестная СУБД (как у штатного) |
| −1 | операция завершилась с ошибкой (как у штатного; в bash видно как 255) |
| 1 | команда или параметр не поддерживаются в этой версии `ibcmd-rs` |

`ibcmd -v` (и `--version`) печатает версию утилиты, `ibcmd help` — список
режимов.

## 2. Версия платформы, настройки и переменные окружения

### Версия платформы

Версия платформы определяет формат XML:

| Платформа | Формат XML |
|---|---|
| `8.3.27` (сборки `8.3.27.1989`, `8.3.27.2214`) | `2.20` |
| `8.5.1` (сборки `8.5.1.1150`, `8.5.1.1529`) | `2.21` |

Сборки одного выпуска могут различаться в мелочах записи XML: `8.5.1.1529`
пишет `<ButtonImportance>Main</ButtonImportance>` у кнопки по умолчанию, у
которой в записи нет собственной важности, а `8.5.1.1150` не пишет. Выпуск
`8.5.1` без сборки ведёт себя как `8.5.1.1150`; для `8.5.1.1529` сборку нужно
назвать (`--platform 8.5.1.1529`).

Неизвестная версия отклоняется со списком известных. Если `--platform` не
указан, платформа берётся по порядку:

1. запись `[[database]]` для этой базы в `ibcmd-rs.toml`;
2. переменная `IBCMD_RS_PLATFORM`;
3. `platform` в `ibcmd-rs.toml`;
4. каталог утилиты `...\1cv8\<версия>\bin`; при загрузке — `version` в
   `Configuration.xml` дерева; при выгрузке режим совместимости 8.5 означает
   8.5.1;
5. иначе 8.3.27 с предупреждением.

При загрузке утилита проверяет, что формат дерева совпадает с платформой
базы, и отказывает до записи, если нет.

### Файл `ibcmd-rs.toml`

Читается рядом с утилитой, в `%APPDATA%\ibcmd-rs\` и в текущей папке (более
поздний побеждает) или один файл из переменной `IBCMD_RS_CONFIG`:

```toml
platform = "8.3.27.2214"        # для баз, которых нет в списке
db-server = "sql01"             # сервер по умолчанию
db-user = "reader"              # логин по умолчанию (пароль здесь не хранится)
restructure-limit-rows = 10000000      # предел собственной реструктуризации, строки (необязательно)
restructure-limit-bytes = "2GB"        # то же, байты: число или строка с единицей (необязательно)

[[database]]
name = "erp_prod"               # имя базы или маска со *
platform = "8.3.27.2214"

[[database]]
server = "sql02"                # необязательно: без него — любой сервер
name = "bsp_*"
platform = "8.5.1.1150"

[[database]]
name = "demo"
platform = "8.3.27"
rows-dir = "rows/demo"          # необязательно: строки Config из папки, без SQL Server
```

Ошибка в файле или неизвестный ключ — отказ с путём и номером строки.

`rows-dir` нужен серверу для редактора ([`serve --stdio`](#serve---stdio--сервер-для-редактора-кода)):
таблица Config такой базы читается из папки файлов `<FileName>__part<N>.bin`,
как у `mssql-dump-config --rows-dir`; относительный путь отсчитывается от
папки файла настроек. Командам выгрузки и загрузки ключ ничего не меняет.

`ibcmd-rs settings show [--db-server <сервер>] [--db-name <база>]
[--config <файл>] [--platform <версия>] [--json]` показывает итоговые
значения и откуда взято каждое; пароль не печатается.

### Переменные окружения

| Переменная | Что задаёт |
|---|---|
| `IBCMD_RS_PLATFORM` | Платформа по умолчанию (`8.3.27`, `8.5.1`, сборка). |
| `IBCMD_RS_DB_SERVER` | Сервер SQL Server по умолчанию. |
| `IBCMD_RS_DB_USER` | Логин SQL Server по умолчанию. |
| `IBCMD_DB_PSW` | Пароль SQL Server. |
| `IBCMD_RS_CONFIG` | Путь к единственному файлу настроек вместо поиска `ibcmd-rs.toml`. |
| `IBCMD_RS_RESTRUCTURE_LIMIT_ROWS` | Предел собственной реструктуризации по строкам (см. ниже). |
| `IBCMD_RS_RESTRUCTURE_LIMIT_BYTES` | Предел собственной реструктуризации по байтам записи (см. ниже). |
| `IBCMD_RS_SQL_CONNECTIONS` | Число соединений с SQL Server (по умолчанию 4, не больше 64). |
| `IBCMD_RS_MSSQL_COMPATIBILITY` | Явный режим совместимости встроенного SQL-клиента: только `2012`. Проверяет фактическую версию сервера (major 11); на иной версии отказывает до выполнения команды. |
| `IBCMD_RS_MSSQL_ENCRYPTION` | Только при совместимости `2012` разрешает ослабить режим встроенного SQL-клиента: `required` (по умолчанию), `login-only` или `disabled`. Выбор фиксируется при создании клиента; автоматического перехода на более слабый режим нет. |
| `IBCMD_RS_WORKERS` | Число потоков выгрузки (по умолчанию — число ядер, но не больше 16; явно — до 64). |
| `IBCMD_RS_VERBOSE=1` | Выгрузка в синтаксисе `ibcmd` печатает в stderr и свои служебные сводки (по умолчанию — только строки штатного `ibcmd`). |
| `IBCMD_RS_LEGACY_EXPORT=1` | Выгружать описания объектов прежними конвертерами (как до 0.2). |
| `IBCMD_RS_STAGE_TIMING=1` | Загрузка печатает время своих шагов, в том числе запросов к SQL Server. |

`IBCMD_RS_MSSQL_COMPATIBILITY=2012` включает отдельный путь для SQL Server 2012.
После подключения первым запросом проверяется фактический `ProductVersion`:
допускается только major 11. Уровень совместимости базы 110 на новом сервере
не подходит. Без этой переменной сохраняется прежний путь работы. Пустое,
неизвестное или не являющееся Unicode значение отклоняется до подключения.

`IBCMD_RS_MSSQL_ENCRYPTION=required` требует TLS для соединения целиком.
`login-only` запрашивает шифрование только входа (сервер может потребовать
шифрование всего соединения); этот режим также требует совместимого TLS.
`disabled` объявляет отсутствие поддержки TLS и передаёт без TLS в том числе
данные входа. Это явный выбор для доверенного изолированного стенда, а не
автоматический обход ошибки TLS. Сервер с обязательным шифрованием может
отклонить такой вход. Пустое, неизвестное или не являющееся Unicode значение
отклоняется до подключения. Без `IBCMD_RS_MSSQL_COMPATIBILITY=2012`
значения `login-only` и `disabled` отклоняются до подключения. Оба выбора фиксируются при создании клиента.
Переменные не настраивают внешние `sqlcmd`/`bcp`.

Только в режиме совместимости `2012` на встроенном SQL-клиенте чтение
количества строк конфигурации, статистики хранилища и имён динамических обновлений для полного `config import` не
требует `FOR JSON PATH`: результаты читаются типизированными строками.
Остальные версии и обычный режим сохраняют прежние JSON-запросы. Это не
подтверждает поддержку собственных `config apply`, activation или всех
исследовательских команд на SQL Server 2012. Проверка соответствия подготовки
дереву XML и транзакционная запись `ConfigSave` сохраняются. На время подготовки
и записи по-прежнему требуется исключить другие изменения конфигурации.

### Предел собственной реструктуризации (S1-J, #406)

Собственная реструктуризация (`mssql-config-apply --allow-restructure s1`, `mssql-restructure`) копирует
перестраиваемые таблицы в одной транзакции, и её журнал растёт вместе с таблицами. Выше предела этап
отклоняется и отправляется в штатный `ibcmd infobase config apply` (он фиксирует изменения по шагам); в
базу ничего не записывается. Предел считается по **сумме** перестраиваемых таблиц этапа:

- **строки**: сумма строк (по умолчанию 10 000 000);
- **байты записи**: данные таблиц дважды (загрузка в кучу и кластерный индекс поверх неё) плюс остальные
  индексы, то есть примерно то, что перестройка запишет в журнал при полной модели восстановления
  (по умолчанию 2 GiB; вывод и измерения: `docs/apply/restructure-size-limit.md`).

Порядок: параметры `--restructure-limit-rows <N>` и `--restructure-limit-bytes <размер>` команд
`mssql-config-apply` и `mssql-restructure` → переменные `IBCMD_RS_RESTRUCTURE_LIMIT_ROWS` и
`IBCMD_RS_RESTRUCTURE_LIMIT_BYTES` → ключи `restructure-limit-rows` и `restructure-limit-bytes` в
`ibcmd-rs.toml` → значение по умолчанию; строки и байты выбираются независимо. Размер: число байтов или число
с единицей, каждая единица степень 1024 (`4GB`, `4 GiB`, `512MB`, `1.5g`); в `ibcmd-rs.toml` число или
строка (`restructure-limit-bytes = "4GB"`). У `ibcmd infobase config apply` нового параметра нет: предел он
берёт только из переменных и файла. Повышенный предел не снимает требование резервной копии:
`--i-have-a-backup` или `--recovery-backup` по-прежнему обязательны. Отчёт применения (`structure.size_check`)
и `ibcmd-rs settings show` показывают предел и откуда он взят.

Порядок для подключения: параметр команды → файл `--settings` →
переменные окружения → `ibcmd-rs.toml` → раздел `database:` штатного
`--config` → значение по умолчанию. Пароль: `--db-pwd` или `-W` →
переменная `IBCMD_DB_PSW` (или названная в `--db-pwd-env`) → `--settings`
→ раздел `database:` штатного `--config`.

### Подключение к SQL Server

Утилита подключается к SQL Server сама, по протоколу TDS; `sqlcmd` и `bcp`
не нужны.

- **Сеть.** Только TCP. Для `np:` и `lpc:` укажите `--sqlcmd`.
- **Шифрование** включено, сертификат сервера принимается без проверки, как у
  `sqlcmd -C`.
- **Linux.** Вход Windows доступен только в Windows; в Linux нужен логин SQL
  Server.

## 3. Основные команды `ibcmd-rs`

Эти команды проверены на БСП и ERP УХ (платформы 8.3.27 и 8.5): результат
совпадает со штатной выгрузкой. Логин SQL Server у них задают `--sql-user`
и `--sql-pwd` (или переменная `IBCMD_DB_PSW`), сервер — `--server`.

### `mssql-dump-config` — выгрузка конфигурации

```
ibcmd-rs mssql-dump-config --database MyBase --extract-metadata-xml ^
  --extract-module-text --no-binary-rows -o C:\export\MyBase
```

| Параметр | Что задаёт |
|---|---|
| `--server <сервер>` | Сервер SQL Server (по умолчанию `localhost`). |
| `--database <база>` | База данных. |
| `--sql-user <логин>` | Логин SQL Server; без него — вход Windows. |
| `--sql-pwd <пароль>`, `--sql-pwd-env <имя>` | Пароль или переменная с ним (по умолчанию `IBCMD_DB_PSW`). |
| `-o, --output-dir <каталог>` | Каталог выгрузки. |
| `--overwrite` | Разрешить писать в непустой каталог. |
| `--extract-metadata-xml` | Выгрузить описания объектов в XML (нужно для полного дерева). |
| `--extract-module-text` | Выгрузить тексты модулей (нужно для полного дерева). |
| `--no-binary-rows` | Не сохранять сырые строки таблицы Config (быстрее). |
| `--platform <версия>` | Версия платформы, то есть формат XML. |
| `--include-config-save` | Выгружать и несохранённые изменения из ConfigSave. |
| `--main-configuration` | Выгрузить основную конфигурацию, как `infobase config export`: строки законченной подготовки из ConfigSave вместо строк Config с теми же именами и `versions` подготовки (по умолчанию — только таблица Config). Не сочетается с `--include-config-save` и `--rows-dir`. |
| `--file-name <имя>`, `--file-name-list <файл>` | Выгрузить только указанные строки Config (по `FileName`). |
| `--object <полное имя>` | Выгрузить только этот объект (`Catalog.Банки`, `Catalog.Банки.Form.ФормаЭлемента`, `Configuration`): его строки и строки его форм, макетов, перерасчётов, вложенных подсистем. Можно повторять. Файлы объекта такие же, как в полной выгрузке; `ConfigDumpInfo.xml` не пишется. |
| `--rows-dir <каталог>` | Читать строки Config из файлов `<FileName>__part<N>.bin` без сервера. |
| `--file-infobase <каталог>` | Читать строки Config (и законченную подготовку в ConfigSave) из файловой базы `1Cv8.1CD` без сервера и платформы. |
| `--base <файл>`, `--sync` | Инкрементальная выгрузка, как у `infobase config export` ([выше](#инкрементальная-выгрузка---base---sync)). Нужны `--extract-metadata-xml --extract-module-text --no-binary-rows`; не сочетаются с `--overwrite`, `--file-name`, `--include-config-save` и строгими проверками `--require-complete-*`. Работают и с `--rows-dir`. В отчёте — раздел `incremental`. |
| `--legacy-export` | Прежние конвертеры описаний объектов. |
| `--sqlcmd <путь>`, `--bcp-executable <путь>` | Работать через `sqlcmd` и `bcp`, как версия 0.2. |
| `--runtime-journal <файл>` | Журнал запросов к SQL Server в JSON (хэши запросов, без текста). |
| `--inflate`, `--require-complete-root-metadata`, `--require-complete-source-assets`, `--collect-all-source-asset-diagnostics` | Исследовательские: распаковка строк и строгие проверки выгрузки. |

Кроме дерева XML в каталоге появляется служебный `manifest.json`.

### `mssql-stage-source-objects` — загрузка конфигурации

```
ibcmd-rs mssql-stage-source-objects --database MyBase ^
  --source-root C:\export\MyBase --replace-config-save --allow-non-lab
```

После загрузки конфигурацию применяет штатный `ibcmd infobase config
apply`.

| Параметр | Что задаёт |
|---|---|
| `--server`, `--database`, `--sql-user`, `--sql-pwd`, `--sql-pwd-env` | Подключение, как у выгрузки. |
| `--source-root <каталог>` | Дерево XML. |
| `--replace-config-save` | Обязательное подтверждение: заменить содержимое ConfigSave. |
| `--allow-non-lab` | Обязательное подтверждение записи в базу. |
| `--base-free` | Загрузка в пустую базу: все строки собираются из XML, из базы ничего не читается. |
| `--verify` | Перед записью в ConfigSave выгрузить моделью получающуюся конфигурацию и сравнить каждый файл с деревом; расхождение отменяет загрузку, ConfigSave не меняется. Загрузка `infobase config import` делает это сама. |
| `--platform <версия>` | Версия платформы; формат дерева должен ей соответствовать. |
| `--path-prefix <путь>` | Загрузить только часть дерева (можно повторять). |
| `--file <путь>` | Загрузить только строки, которые собираются из этого файла дерева (путь относительно `--source-root`, можно повторять): загрузка `infobase config import files`. Объект файла собирается из строк базы, остальные его строки остаются строками базы; `--verify` сравнивает перечисленные файлы. Не сочетается с `--path-prefix` и `--base-free`. Без базы: `--script-only` и переменная `IBCMD_RS_BASE_ROWS_DIR` с каталогом строк Config (`<FileName>__part0.bin`). |
| `--script-only` | Только подготовить SQL-скрипты, ничего не записывая. |
| `--script-output <путь>` | Куда писать SQL-скрипты. |
| `--per-row` | Построчная загрузка вместо пакетной (быстрее для нескольких объектов). |
| `--bulk` | Пакетная загрузка (по умолчанию). |
| `--batch-size <n>` | Объектов в одном пакете SQL. |
| `--sqlcmd <путь>`, `--bcp-executable <путь>` | Работать через `sqlcmd` и `bcp`, как версия 0.2. |

### `source-diff` — сравнение двух деревьев XML

```
ibcmd-rs source-diff -o diff.json C:\export\native C:\export\ours
```

Сравнивает файлы двух деревьев по пути и содержимому. В отчёте — итоги
(`unchanged`, `different`, `left_only`, `right_only`) и список расхождений.
`--path-prefix <путь>` ограничивает сравнение частью дерева; без `-o`
отчёт печатается в stdout.

### `cf export` и `cf load` — файлы `.cf`, `.cfe`, `.epf`, `.erf` ↔ XML без базы

Выгрузить файл конфигурации, расширения, внешней обработки или отчёта в
XML конфигуратора, поправить (например, в VS Code) и собрать новый файл с
правками. Ни база, ни платформа 1С не нужны. Штатному `ibcmd` для этого
нужна информационная база: сначала загрузить в неё `.cf`, потом выгрузить.

```
ibcmd-rs cf export C:\cf\MyConf.cf C:\src\MyConf --index
rem ... правки в C:\src\MyConf ...
ibcmd-rs cf load C:\src\MyConf C:\cf\MyConf-new.cf --base C:\cf\MyConf.cf
```

| Команда и параметр | Что задаёт |
|---|---|
| `cf export <файл> <каталог>` | Выгрузить `.cf`/`.cfe`/`.epf`/`.erf` в дерево XML. Тип файла определяется сам. |
| `cf export --platform <версия>` | Формат XML: `8.3.x` — `2.20`, `8.5.x` — `2.21`. `.cf` и `.cfe`, сохранённые платформой 8.5, выгружаются в `2.21`. |
| `cf export --overwrite` | Разрешить писать в непустой каталог. |
| `cf export --index` | Записать `.ibcmd/index.tsv` — хэши файлов и версии записей. С индексом `cf load` не выгружает исходный файл заново и видит правки быстрее. |
| `cf export --fail-on-opaque` | Отказать с ненулевым кодом и JSON `ok=false`, если хотя бы одна запись хранилища осталась `opaque`. Полный отчёт сохраняет количество, имена и причины по каждой записи. Без флага прежнее поведение сохраняется. |
| `cf export --update` | Довести проиндексированное дерево до новой версии того же файла, переписав только изменившееся. Дерево без индекса или с незагруженными правками не трогается (отказ с именами файлов). Каталоги с точкой (`.git`) не трогаются. |
| `cf load <дерево> <новый файл> --base <исходный файл>` | Собрать новый файл с правками дерева. Существующий файл не перезаписывается. |
| `cf load --platform <версия>` | Версия платформы, для которой написан XML дерева. |

`--fail-on-opaque --update` всегда проверяет **полный текущий образ**, даже если
файл совпадает с индексом или обычное обновление могло бы быть инкрементальным.
При отказе существующее дерево, его индекс и собственные файлы остаются прежними.
Новый индекс публикуется только после успешной проверки. Обычный экспорт при
отказе может оставить частичное дерево без нового индекса; подробности находятся
в `export.storage.entries`. Неизвестные контейнеры не исключаются по имени.
Нулевое число `opaque` означает прохождение этой проверки записей, но само по себе
не доказывает полноту `ChildObjects` или соответствие всей конфигурации штатной
платформе.

Для `.cfe` полный новый образ можно собрать и без исходного файла:

```
ibcmd-rs cf bootstrap F:\src\MyExtension F:\cf\MyExtension.cfe --platform 8.5.1.1150
ibcmd-rs cf bootstrap F:\src\MyExtension F:\cf\MyExtension-base-free.cfe --platform 8.5.1.1150 --base-free
ibcmd-rs cf export F:\cf\MyExtension.cfe F:\src\MyExtension-edit --platform 8.5.1.1150 --index --fail-on-opaque
rem ... правки XML, BSL и Version в F:\src\MyExtension-edit ...
ibcmd-rs cf load F:\src\MyExtension-edit F:\cf\MyExtension-new.cfe --base F:\cf\MyExtension.cfe --platform 8.5.1.1150
```

Обе формы `cf bootstrap` для расширения используют один независимый
сборщик. Он читает полное дерево с `Configuration.xml`, сохраняет свойства
заимствованных объектов и собирает CFE с новым манифестом `configinfo`;
исходный CFE, побочные двоичные записи и запуск штатного компилятора не нужны.
Перед публикацией результат выгружается обратно и побайтово сравнивается
с исходниками. Неизвестные контролируемые свойства и несовпадение файлов
дают отказ без публикации. Новый выходной файл должен иметь расширение `.cfe`.

Файловая выгрузка CFE соответствует `ibcmd config export --file`: она
не пишет `ConfigDumpInfo.xml`. SQL-выгрузка `config export --extension`
и `mssql-dump-extension` пишет этот файл из манифеста CAS. Это разные
эталоны; отсутствие `ConfigDumpInfo.xml` у файлового CFE не является потерей.
Подробности и размеры исследуемых деревьев —
[extensions/parity.md](extensions/parity.md#source-only-cfe-files).

Как работает `cf load`:

- при правке текста обычного модуля сохраняются его исходные `info` и
  заголовки внутренних элементов; модуль формы заменяется внутри исходного тела формы;
- остальное (описания объектов, формы, макеты, справка, новые и удалённые
  объекты) компилируется штатным для `ibcmd-rs` компилятором загрузки,
  запущенным без базы: строками базы служат записи исходного файла;
- из результата берутся только записи изменённых файлов, прочие переносятся
  из исходного файла без изменений;
- для CFE пересчитываются SHA1 изменённых упакованных строк в `configinfo`;
- новый файл выгружается обратно и сверяется с деревом; при расхождении файл
  не пишется, в ошибке перечислены файлы.

Для CFE явно заданный `--target-profile` должен использовать тот же диалект
XML, что выбранный `--platform`/`--source-version`; преобразование CFE между
диалектами отклоняется до записи файла. Без явного профиля он выбирается
по версии источника.

Для предупреждения о смене базового CFE сохраняйте происхождение дерева
через `cf export --index`: нативная файловая выгрузка CFE не содержит
`ConfigDumpInfo.xml`, а индекс хранит исходные версии записей.

Эти операции создают файлы и не активируют расширение в базе. Ограничения
SQL-загрузки и активации определяются отдельно:
[точные 8.3.27.2214 и 8.5.1.1150](extensions/parity.md#sql-extension-import-and-apply-on-exact-builds).

Проверено: выгрузка БСП и ERP УХ (8.3.27.2214) совпадает со штатной
выгрузкой той же конфигурации файл в файл (ERP УХ — 140 709 файлов).
Файл, собранный `cf load` из выгрузки ERP УХ с правками модуля, описаний
объектов (синоним, новый реквизит) и формы, штатная платформа загружает, а
её выгрузка совпадает с отредактированным деревом.

### `serve --stdio` — сервер для редактора кода

```
ibcmd-rs serve --stdio
```

Долгоживущий процесс для редактора кода (VS Code, Cursor, VSCodium), один на
окно: дерево объектов базы, выгрузка и загрузка выбранных объектов, сверка
папки исходников с базой, файл объекта так, как его выгрузила бы база. Обмен —
JSON-RPC 2.0 через stdin и stdout с кадрами `Content-Length`, как у языковых
серверов; сеть и порты не нужны. Протокол (методы, уведомления, ошибки,
совместимость версий): [openspec/changes/add-editor-server/design.md](../openspec/changes/add-editor-server/design.md).

- Базы — записи `[[database]]` файла `ibcmd-rs.toml` (в том числе файла в
  папке проекта редактора) и те, что редактор назовёт при запуске. База
  может быть папкой строк Config (`rows-dir`): тогда SQL Server не нужен, но
  загрузка и проверка ConfigSave недоступны.
- Пароль SQL Server редактор хранит у себя и передаёт серверу в памяти; в
  аргументы, файлы и журналы он не попадает. Без него берётся `IBCMD_DB_PSW`.
- Сервер держит соединения с базой и кэш дерева и выгруженных объектов;
  кэш сбрасывается, когда в базе меняется строка `versions`. Долгий запрос
  можно отменить.
- Сервер вызывает те же функции, что и команды: всё, что делает редактор,
  можно сделать из командной строки (`objects`, `mssql-dump-config --object`,
  `mssql-stage-source-objects --path-prefix`, `mssql-apply-check`).

### `objects` — объекты конфигурации по одному

То, что делает сервер для редактора, из командной строки. Источник —
`--rows-dir <папка>` или `--server`, `--database`, `--sql-user`,
`--sql-pwd`/`--sql-pwd-env` и `--platform`, как у `mssql-dump-config`.

| Команда | Что делает |
|---|---|
| `objects tree [--node <узел>]` | Дети узла дерева в JSON: без `--node` — конфигурация, `Configuration` — виды объектов, `Configuration/Catalogs` — справочники, `Catalog.Банки` — группы его форм и макетов, `Catalog.Банки/Forms` — формы. |
| `objects status --source-dir <папка> [--object <имя>]...` | Сверка базы и папки исходников файл за файлом (JSON): `same`, `modified` (с перечнем изменённых, недостающих и лишних файлов), `notExported`, `notInBase`. Без `--object` — вся конфигурация. |
| `objects read --path <путь> [-o <файл>]` | Файл объекта (`CommonModules/X/Ext/Module.bsl`) так, как его выгрузила бы база; на диск ничего не пишется. |
| `objects export --target-dir <папка> --object <имя>...` | Выгрузить объекты в папку исходников: файлы объекта пишутся заново, его файлы, которых выгрузка больше не пишет, удаляются, остальное в папке не трогается. |

### `settings show` — итоговые настройки

Печатает, какие сервер, логин, платформу возьмёт команда для базы и откуда
взято каждое значение. Параметры: `--db-server`, `--db-name`, `--config`,
`--platform`, `--json`. См. [раздел 2](#файл-ibcmd-rstoml).

### `compatibility` — таблица возможностей

Печатает в JSON, какие операции реализованы и для каких форматов и версий
(`-o <файл>` — записать в файл).

Исследовательские и лабораторные команды: ими получены и проверены

Команды, которые пишут в базу, требуют подтверждений `--replace-config-save`

### Файлы CF и конвертация

Режим `cf bootstrap --base-free --platform <версия>` в таблице ниже доступен
в сборке исходников `master` после [PR #422](https://github.com/Untru/ibcmd-rs/pull/422).
В скачанном v0.4.0 он отсутствует. Доступные параметры конкретной сборки
показывает `ibcmd-rs cf bootstrap --help`.

Для обычной конфигурации `.cf` без `--base-free` команда использует прежний
bootstrap-компилятор с ограниченным набором семейств и вариантов метаданных.
Этот путь сохранён для поддерживаемых им деревьев. При `bootstrap_compile_failed` отчёт
сохраняет отдельные ошибки с именем файла и нарушенным правилом. Для полного
native XML-дерева соберите исходники после #422 и попробуйте
`ibcmd-rs cf bootstrap --base-free --platform <версия> <каталог-XML> <файл.cf>`.
Это выбирает другой компилятор; ошибки неподдерживаемых или повреждённых
исходников по-прежнему отклоняют сборку без публикации файла.

Расширение определяется по `Configuration.xml` и собирается в `.cfe`
отдельным независимым сборщиком: `cf bootstrap <дерево> <новый.cfe> --platform <версия>`
и та же команда с `--base-free` эквивалентны.
К расширениям не относится выбор старого компилятора обычной конфигурации.
Примеры и проверка обратной выгрузки — [выше](#cf-export-и-cf-load--файлы-cf-cfe-epf-erf--xml-без-базы).
Внешняя обработка или отчёт собирается только с `--base-free`:
`cf bootstrap --base-free --platform 8.3.27 <дерево или корневой .xml> <новый.epf|.erf>`.
Сборщик берёт встроенный пакет, собранный 8.3.27.2214, даёт ему
идентификаторы дерева и загружает в него дерево тем же путём, что `cf load
--base`. Затем выгружает результат обратно для проверки и записывает шаги
путей данных форм в `copyinfo`. Без этих шагов 8.3.27.2214 при загрузке
отбрасывает `<DataPath>` формы. Дерево со ссылками на объекты конфигурации
отклоняется, и в ошибке перечислены ссылки. Ссылкой считается:
- тип `cfg:…Ref.<Имя>`;
- путь `<Вид>.<Имя>` как целое значение элемента или атрибута.

Такие деревья собирайте через `cf load --base`.

Отклоняется и форма, путь данных которой делает шаг, не измеренный для
`copyinfo`:
- член объекта платформы: компоновщик настроек
  (`Объект.КомпоновщикНастроек.Settings.Filter`, в том числе почти любая форма
  внешнего отчёта, связанная с `Отчет.КомпоновщикНастроек`), стандартный
  период (`Период.StartDate`), список значений, диаграмма Ганта;
- маркер итога или числа строк табличной части;
- дополнительная колонка вне дерева значений.

Без записи такого шага платформа при загрузке отбросит `<DataPath>`.

Корневой `.xml` можно передать вместо каталога, но собирается весь его
каталог: рядом не должно быть других объектов. Также отклоняются XML 8.5
(2.21), `--target-profile`, `--revision`, `--storage-version`, `--page-size`
и `--reserved`: контейнер всегда тот, что пишет 8.3.27.2214.

| Команда | Что делает |
|---|---|
| `cf inspect` | Краткая опись содержимого архива CF в JSON. |
| `cf verify` | Проверка структуры CF, выбранных частей и контрольных сумм SHA-256. |
| `cf extract` | Извлечь один элемент хранилища CF в отдельный каталог. |
| `cf export` | Выгрузить `.cf`, `.cfe`, `.epf` или `.erf` в дерево XML без платформы; `--index`, `--update` — см. [раздел 3](#cf-export-и-cf-load--файлы-cf-cfe-epf-erf--xml-без-базы). |
| `cf overlay` | Наложить выбранные файлы XML на базовый CF и собрать новый CF. |
| `cf load` | Собрать новый файл с правками дерева XML — см. [раздел 3](#cf-export-и-cf-load--файлы-cf-cfe-epf-erf--xml-без-базы). |
| `cf bootstrap` | Собрать новый CF или CFE из полного дерева XML без базы и платформы. Для CFE с `--base-free` и без него используется один независимый сборщик (см. выше). Следующее описание относится к обычной конфигурации CF. С `--base-free --platform <версия>` дерево собирается теми же правилами, что загрузка в пустую базу (`8.3.x` — XML `2.20`, `8.5.x` — `2.21`), в контейнер Format15. Для 8.5 конфигурация хранится в разметке 8.5 (формы `{59,…}`, кортеж конфигурации `{76,…}`), если режим совместимости 8.5 или формы дерева выгружены из разметки 8.5; иначе — в разметке 8.3.27, как ERP УХ 8.5. Строка `version` перечисляет возможности платформы, которые использует конфигурация (цвета палитры). Проверено на `.cf`, сохранённом 8.5.1.1529: выгрузка собранного файла совпадает с деревом файл в файл, записи совпадают с записями платформы, кроме новых идентификаторов `versions` и хвоста строки конфигурации (`docs/evidence/cf-platform-8.5.md`); загрузка такого файла штатной платформой 8.5 не проверена. |
| `mssql-save-config` | То же, что `ibcmd infobase config save`: конфигурация в файл `.cf` прямо из строк, без XML. Подключение — как у `mssql-dump-config` (`--server`, `--database`, `--sql-user`, `--sql-pwd`, `--sqlcmd`), или без сервера: `--rows-dir <каталог>` читает строки Config из файлов `<FileName>__part<N>.bin` (части одной строки склеиваются). `--db` — только Config; `--overwrite` — заменить существующий файл. Печатает отчёт JSON: число элементов, строк из ConfigSave, строк онлайн-обновления и строк из нескольких частей. |
| `mssql-load-config` | Офлайновая половина `config load`: разбирает `.cf` в строки, которые загрузка записывает в ConfigSave (по строке на элемент, с теми же сжатыми байтами; строка больше 10 000 000 байт — частями), и пишет файл строк bcp и два скрипта пакетной загрузки, как `mssql-stage-source-objects --script-only`. Нужны `--database` и `--script-only`; `--script-output` — куда писать. В базу ничего не пишет; файл без `root`, `version`, `versions` или с повреждённым элементом отклоняется. |
| `convert` | Конвертация целиком: XML ↔ CF и XML ↔ EDT между указанными профилями версий (`--source-format`, `--target-format`, `--source-profile`, `--target-profile`). Для `--target-profile platform-8.5.1.1150` CF собирается как `cf bootstrap --base-free` (Format15). Проверенные маршруты — `ibcmd-rs compatibility`. |

Для EDT 2025.2.3 укажите профиль `edt-2025.2.3-xml-2.21` (Runtime-Version
8.5.1) либо `edt-2025.2.3-xml-2.20` (8.3.27), а для XML — соответствующий
`xml-2.21` либо `xml-2.20`. Установленный EDT для конвертации не требуется.

```powershell
ibcmd-rs convert native-xml edt-project --source-format xml --target-format edt --source-profile xml-2.21 --target-profile edt-2025.2.3-xml-2.21
ibcmd-rs convert edt-project returned-xml --source-format edt --target-format xml --source-profile edt-2025.2.3-xml-2.21 --target-profile xml-2.21
```

Назначение должно быть новым каталогом. `--dry-run` выполняет чтение, проверку
и подготовку результата без публикации; `--report <файл>` сохраняет JSON-отчёт
с этапами и учётом исходных файлов. Разные версии XML требуют отдельной
подтверждённой миграции и здесь отклоняются.

При XML → EDT каталог `.ibcmd-provenance` сохраняет исходную запись XML для
точного обратного прохода, включая `ConfigDumpInfo.xml`. Если проект изменён,
обратная конвертация сообщает об устаревшем происхождении. Для преобразования
изменённого проекта удалите этот каталог: результат будет собран из текущих
метаданных и ресурсов EDT. Неизвестные файлы или настройки отклоняются с
указанием пути. Подробнее: [границы адаптера](edt/morph1c-adoption.md) и
[лабораторная сверка](edt/oracle.md).

Сведения о поставке (`Ext/ParentConfigurations.bin`) EDT 2026.1 хранит в
проекте как `src/Configuration/Configuration.distr`. При EDT → XML такой файл
становится `ParentConfigurations.bin` с элементами в порядке `.distr`, как в
экспорте самого EDT. Порядок исходной выгрузки EDT не хранит, поэтому от
штатного файла результат отличается только порядком элементов. При обратном
проходе снова пишется `.distr`. Принимаются конфигурации без поставщика и с
одним поставщиком, а также режимы объектов, встреченные в настоящих проектах;
файл другого вида отклоняется. Из XML конвертер по-прежнему пишет
`ParentConfigurations.bin`.

### Расширения конфигурации

| Команда | Что делает |
|---|---|
| `mssql-extension-list` | Список расширений базы. |

### Изменения в работающей базе (смена поколения)

| Команда | Что делает |
|---|---|

Режим `exclusive` выполняет `mssql-config-apply` (встроенный клиент SQL): строки `_dynupdate_` прежних онлайн-обновлений сворачиваются в обычные, как у штатного apply (#408); `live`, `worker` и `exclusive` с `--sqlcmd` на базе с такими строками отказывают до записи. ### Native export queries (#362)

`ibcmd-rs infobase config export info [--out=<directory>]` reads the published
main configuration through the same filedb/SQL view as full export. Stdout is
ConfigDumpInfo XML without a BOM; `--out` requires an existing directory and
writes BOM-prefixed `ConfigDumpInfo.xml` there. Inventory generation skips the
object-body conversion batches; preparing its shared indexes may read bodies.

`... export status --base=<ConfigDumpInfo.xml> [--out=<file>] [--short]`
compares stored versions, independently of the custom editor's byte-diff status.
Unchanged stdout is empty. Changed entries are `added: <name>` or
`modified: <name>` (`A:` / `M:` with `--short`). A removed or renamed reference
requires `modified: all`. Output files contain a UTF-8 BOM, even with no changes.

`... export objects --out=<directory> [--recursive] <full-names...>` exports
only selected descriptors and their own bodies. Owned forms/templates and the
Configuration's top-level children are included with `--recursive`.
ConfigDumpInfo is not included. Output paths containing links/reparse points
are rejected; unknown objects are resolved before any output files are written.
Extensions and archives remain explicitly unsupported on these new commands.

Native 8.5.1.1592 measurements supersede the earlier unmeasured drop-in claims
above: `--base` and `--sync` are mutually exclusive (rc2). Unchanged `--base`
creates no output directory; unchanged `--sync` preserves file mtimes. Native
`--sync` requires an existing export directory and reads its ConfigDumpInfo.
Both forms refuse deletion/rename with rc255 and require a full export.
The custom `infobase-config-export` / `mssql-dump-config` API retains its
existing combined base+sync and full-fallback/pruning behavior.

Own minimal native snapshots and exact expected bytes are in
`tests/fixtures/native-export-commands/manifest.json`. They contain no ERP data.


### SQL-загрузка и применение расширений

`infobase config import/apply --extension=<имя>` работают с уже установленным
активным расширением на точных 8.3.27.2214 и 8.5.1.1150. Загрузка проверяет
полное предлагаемое дерево; применение требует отсутствия клиентских сеансов.
Нужны `--cluster-id` и `--infobase-id`, а `--rac` и `--ras-endpoint` задают
нужный сервер администрирования. Существующие механизмы проверки связывают
SQL-базу с выбранной базой кластера и сборкой платформы. Изменения структуры
таблиц этим маршрутом не применяются. Примеры и измеренные границы:
[extensions/parity.md](extensions/parity.md#sql-extension-import-and-apply-on-exact-builds).
